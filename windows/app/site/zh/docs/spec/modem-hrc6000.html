HR_C6000 as a DMR modem

Facts about driving the Hongrui HR_C6000 as a DMR Tier II modem on a board with an STM32 host. Pins and the MCU side are on the board's hardware page (feature-matrix.md lists the boards); the modem-neutral behavior a DMR stack needs is in dmr-modem.md. This file is register-level: what to write, when, and what the chip reports.

Full register reference: hrc6000-registers.md

Sources: the HR_C6000 user manual (Hongrui; register chapter and the "Layer 2" application chapter) and on-air measurements with an SDR watching (bit exact decode of every burst). Values marked "(unexplained)" are init values the manual does not explain; keep them. Values marked "(unverified)" have not been confirmed on our hardware.

All three interrupt lines share one NVIC priority. On the STM32 radios it is 5, which is more urgent than the USB and other EXTI lines at 6 (numerically lower is more urgent). Thread-level SPI traffic must not re-enter the handlers. A thread that touches the modem masks the three EXTI lines and waits until any running handler has finished before it starts its own transfers.

1.1 U_SPI framing

Each transaction is CS low, a command byte, an address, data bytes, CS high. Bytes are MSB first. The bit-banged master sets MOSI, drives CLK low, then high (data sampled on the rising edge; CLK idles high). Reads sample MISO after the falling edge, before the rising edge.

Byte Meaning
Command bit 7: 1 = read, 0 = write. bit 6: 1 = 11-bit (extended) address. bits 2-0: page
Address 8-bit address; with bit 6 set, two bytes: low 8 bits first, then bits 10-8 in the low 3 bits of the second byte
Data one or more bytes; the address auto-increments while CS stays low

A read sends the command and address, then clocks dummy bytes (0xFF) while reading. The driver uses burst writes of up to 128 data bytes and burst reads of up to 96.

Page Contents Used for
1 auxiliary parameters (sync patterns, DTMF tone table at extended addresses 0x11A-0x129, unexplained values) init, sync pattern, tones
2 data RAM: a write fills the TX RAM, a read returns the RX RAM ("1.2K RAM" in the manual) LC, CSBK, data header / block payloads
3 vocoder frame buffer 128 bytes of 0x7F to flush it; on V_SPI, the 27-byte AMBE frame
4 system parameter table (the main registers) everything else

The manual's command table lists page 2 as the RX ("receive end") RAM and page 6 as the TX ("write end") RAM. On air, writes to page 2 land in the TX RAM and are sent bit exact. Page 6 has not been tried.

TX RAM layout (the manual):

Address Contents

1.2 Clock

The PLL settings used match the manual's 29.4912 MHz crystal row (crystal frequency on the boards unverified): PLL output 49.152 MHz, system clock 9.8304 MHz, codec clock 12.288 MHz, CLKOUT 24.576 MHz.

3.1 Entering DMR (after FM, or at every DMR channel change)

0x01=0xF0, 0x45 / 0x46 = the DMR modulation pair from calibration, 0x10=0x6E, 0xE0=0xC9, 0xE4=0x20+DMR mic gain, 0x26=0xFD. Then restart the receiver (section 5.1). In operation 0x10 is 0x6E, not the 0x6B written at init.

3.2 Flushing stale vocoder audio

Set the RX gain to -15 dB (any lower and the flush doesn't take), 0x06=0x22, 128 x 0x7F to page 3, 0x06=0x20, restore the RX gain.

4. Interrupts

4.1 Timeslot interrupt (every 30 ms)

The interrupt comes at each slot boundary once the chip has timing. Passive timing (0x40=0xC3) derives the timing from received bursts. When the signal goes away, it keeps counting from the last sync. Corrections within 1.25 ms are applied in real time. Active timing (0x40=0xE3) generates the timing locally. The interrupt stops only when TxEn and RxEn are both cleared.

At every timeslot interrupt the MCU decides the next slot and writes 0x41. For TX it also writes the payload and 0x50. These writes must land before the slot after the next starts. In the manual's timing, the chip starts framing the next slot's burst at t1, and the MCU must write its data in the window t2 before t1. The driver writes everything at the start of the timeslot handler, and the burst goes out in the following slot. A late setup slips the burst by one slot (30 ms) or by a frame (60 ms). While transmitting, the slot between our bursts gets 0x00. An SFR writes 0x50 there instead, because it hears its inbound slot in that slot (hrc6000_dmr_tx_listen, sfr.md 3).

The CACH TC bit (0x52 bit 2) can be read here. The chip refreshes it only in slots being received. It is the TC of the slot that just ended, not the one starting (5.3).

4.2 System interrupt

Read 0x82 (flags) and 0x52 (CC / CACH) first, handle each set flag, then write the value read back to 0x83.

0x82 bit Meaning (DMR) Sub-status Use
7 send request rejected (channel busy and the access policy is polite) none the transmission didn't go out
6 TX start 0x84: 7 voice, 6 OACSU, 5 encryption key update, 4 vocoder config done, 3 data, 2 partial retransmission, 1 retransmission, 0 vocoder init read and ignored
5 TX end 0x86: 7 service complete, 6 fragment-length ack sent, 5 OACSU timeout, 4 layer 2 "last moment to set up the next slot", 3 confirmed fragment sent, 2 short LC received, 1 BS activation timeout read and ignored
4 post access (late entry) none a voice call already in progress has been acquired from its embedded signaling: start receiving as if a header had been heard
3 received data ("control frame parsed") 0x51 a burst was decoded: section 6
2 received information (layer 3 service data) 0x90 read and ignored
1 voice abnormal exit 0x98 voice sync lost on slot 0 (bit 1) or slot 1 (bit 2): replace the next voice frame of that slot with silence
0 physical layer receive none not used

The mask 0x81=0x19 enables bits 4, 3 and 0. Bit 7 (send rejected) still shows set in 0x82 when 0x82 is read on another interrupt. The SFR debug build counts these. So 0x82 shows more flags than the mask lets interrupt. Whether bit 7 raises the line by itself is unverified.

Two interrupts per voice burst. A voice burst produces one received-data interrupt for its EMB (SyncClass 0) and one for the burst. A voice handler takes a burst number 1..6 at most once per 45 ms. It drops a second report that comes within 45 ms of the last voice burst taken.

The same status reported again one slot later. In direct mode the chip can report a burst a second time at the next timeslot interrupt, with the same status and payload. The driver drops a report of the same kind (and, for data, the same payload) within 45 ms as a repeat. Idle bursts with BS sync are exempt: a base station sends a burst in every slot, and every idle burst has the same bits, so on a carrier idle on both slots each slot's idle looks like a repeat of the one before. Dropped, the carrier looked silent and a trunked call's hang of idles timed out.

Timing of a burst report. For a burst received in step with the chip's slot timing, the received-data interrupt comes 3-5 ms after the timeslot interrupt (2-10 ms observed). A delay of 25-30 ms means the chip's timing is out of step with the sender, because it locked to noise or to another station. The receiver should then be resynchronized.

4.3 RF TX interrupt

The interrupt comes before each burst the chip is about to send. The handler keys the PA and switches the RF chip to TX. On a board without the RF RX interrupt the MCU ends each TX burst itself. At the next timeslot interrupt, if the PA has been on for more than 20 ms, the MCU turns it off and puts the RF chip back in RX. After the last burst of a transmission, a one-shot 29 ms timer does the same. Keying takes the PA enables high and writes AT1846S register 0x30 = 0x60C6 (digital TX). Un-keying takes them low and writes 0x30 = 0x7026 (25 kHz) or 0x6026 (12.5 kHz). A board may key a fixed delay after the interrupt (a timer, 1 ms on one board) and switch from RX straight to TX or through idle; its hardware page has the sequences.

On such a board the RF chip's "transmitting" state therefore goes on and off burst by burst. Code that needs to know whether a transmission is in progress must use the modem slot state (section 7.5), not the PA.

4.4 Lost interrupts

The three lines are edge triggered. A system line still low after its handler (a flag set again, or one whose edge was missed) gives no further edge, so no later request interrupts. The STM32F4 glue (platform/stm32f4/hrc/dmr_glue.c) recovers and counts (hal_dmr_modem_t.health, the debug link's dmr.modem_* keys):

Count Found Recovery
stalls no timeslot interrupt for 200 ms while transmitting (the engine's tx_stalls; a stall while receiving is not counted) the transmission ends, the receiver restarts
stuck the system line low with no edge pending: at a timeslot interrupt (EXTI pending bit clear), or at the task's 10 ms poll (still low 5 us later with no handler run) the timeslot handler services it, or the task pends the handler; counted once per low stretch

Entering DMR with the line already low (a flag from FM) pends the handler at once and is not counted. The first loss keeps four words: 0x82, EXTI_PR, the interrupt port's IDR, and the three lines' NVIC enable, pending and active bits (bits 0-2, 8-10, 16-18).

5. Receive

5.1 Restarting the receiver

0x40=0xC3, then 0x41=0x20, 0x41=0x00, 0x41=0x20, 0x41=0x50. (The manual's recipe: if the received CC doesn't match, write 0x20 to drop the sync and search again.) Used after leaving TX in direct mode, after a call ends, after color-code changes, and on any loss of state.

5.2 Per burst (received-data interrupt)

Read 0x51 and 0x5F (and 0x52 already read):

Field From Notes
sync class 0x51 bits 1-0 0 none (EMB report), 1 voice, 2 data, 3 RC
data type / voice burst 0x51 bits 7-4 data: the ETSI data type 0..15. voice: low 3 bits 1..6 = A..F
CRC error 0x51 bit 2 for voice it reflects the EMB / embedded checks; for data the burst CRC
PI 0x51 bit 3 the privacy indicator; bursts with it set are dropped by the voice path
color code 0x52 bits 7-4
sync type 0x5F bits 1-0 MS / BS / TS1 direct / TS2 direct

Payloads: page 2 from 0x00. 12 bytes for an LC (voice header, terminator, or the embedded LC once assembled), CSBK, MBC, data header and rate 1/2 blocks; 18 bytes for rate 3/4 (the chip decodes the trellis code); 24 bytes for rate 1. Voice: 27 bytes from page 3 on V_SPI (three 72-bit AMBE+2 frames with their FEC, as the codec expects).

  • Mode from sync type: BS sync means a repeater; anything else is direct mode. The receiver follows it unless the channel forces direct mode (and always stays direct for SFR).

  • Data blocks have no CRC of their own (the packet CRC-32 covers them): take rate 1/2, 3/4 and 1 blocks even when the CRC flag is set, and flag them. Drop CSBK, MBC and data headers with a CRC error.

  • Data on our slot only: through a repeater, accept a data burst only when the slot number (from the TC bit) is ours and it differs from the previous burst's slot (a second report in the same slot is a duplicate). In direct mode, accept the bursts of the slot the receiver is locked to.

  • Voice numbers by the frame count. A class 0 report's number (0x51 bits 6-4) is not always its burst's: on the bench about one call in two had a burst reported with the number of the burst before it or one further back, with no frame missed. Within a superframe in progress on the slot, with the timeslot interrupts running, the driver numbers each voice burst from the last one taken plus the frames counted since (two ticks a frame) and counts a disagreeing report (sx in the v0 diagnostics line). A report with the last burst's number and the same voice is stale and dropped; with new voice it is the next burst. Burst A keeps its voice sync. Without the timing, or where the count would land on A, the chip's number is used.

  • The LC registers are sticky. Page 2 keeps the previous call's LC until the new one is decoded. On a new reception, the first LC read may be the last call's. Either wait for two superframes (burst A seen twice after the slot lock) before trusting it, or capture page 2 when the reception starts and accept an LC only when it differs from that capture, or after more than one superframe of voice. The driver takes an unchanged LC at the burst A after the reception's first whole superframe (A-F of this reception, F with no CRC error), by then written to page 2 (next item): the same talker again. HIL 2026-11-14 on the HR_C5000: waiting for the second F, a late entry with the last call's LC played 8 bursts instead of 12. The driver captures page 2 at the first report of a quiet period (a status report before any burst is taken, for a late entry), else at the first burst.

  • The voice header's LC and the terminator's LC are read at their bursts; during voice, the embedded LC appears in page 2 once the chip has assembled it from bursts B-E. Working conclusion from HIL 2026-10-10 (c8c9b23): not yet at F's first report (the EMB one): a new LC was first seen there at the second F. So until a reception has its LC the driver also reads page 2 at the next burst A, at F's repeated report and at the post-access interrupt (an LC that differs there is handed over with the next voice burst).

  • Page 2 isn't per slot. With a call on each slot it holds what the chip assembled last, of either call, so at one call's F it can hold the other's. The driver keeps each slot's call LC (a voice LC, FLCO 0 or 3, from its header or terminator, or the embedded LC it handed over) and checks each embedded LC it would hand over for a burst on a slot:

    Page 2 holds Handed over
    This slot's open call's LC Yes, even when the other slot's call has the same LC (a group on both slots)
    The other slot's call's LC, while that call may go on No, unless this slot has no call of its own and 8 of its F reads in a row showed only that LC (then it is this call's too: a group on both slots, or the other call over unseen)
    Another voice LC, the other slot idle Yes: this slot's next talker (no header, a terminator missed)
    Another voice LC, the other slot's call maybe going on No while this slot's call goes on (voice within the last superframe): its talker can't change without a gap, and a mix of both calls stays in page 2 for as long as both talk (bench). Otherwise only when read again a superframe later, so such a call gets its LC about 360 ms later. Page 2 held a mix of both calls' LCs (bench: a source and talk group neither call had, from 2.2 s into the call on every run); the embedded LC has only a 5-bit checksum, so about 1 mix in 32 passes it
    A talker alias or GPS block (other FLCOs) Only when the other slot isn't busy. Never kept as a slot's call LC

    A slot is busy for 2.2 s (6 superframes) after its header, voice or LC was last taken, or its LC last seen in page 2. Page 2 doesn't keep a call busy once its terminator was heard, nor when the driver takes that slot's voice (both slots heard on a chip without the tick voice read). Bursts with no slot number are left alone. Counter lc_other_slot (what would have been handed over, held back).

    Limits: the two slots' superframes share a period, so page 2 at this slot's F holds the same call's LC nearly every time. A call joined by late entry beside another call whose own LC isn't found at A, F's repeat or the post-access interrupt within 8 superframes (a weak signal, CRC errors) takes the other call's LC: its caller and talk group show (and the talk group filter uses them) until its own LC comes. Before this rule it took the other call's LC at once. A call with the other slot's LC gets its embedded LC only after those 8 superframes (2.9 s). A talker change with no header and no gap while the other slot's call may go on keeps the first talker's LC until the voice pauses.

  • LC trace (for the bench): every look at page 2 until the reception's LC is handed over is logged, with the ticks since the capture, the voice bursts taken and page 2's source ID. (the last reception).

  • Talker alias and GPS embedded data (FLCO 4-8) appear in the same page 2 location as the embedded LC.

5.3 Timeslot tracking (repeater signals)

The TC bit of the CACH alternates 0/1 slot by slot. At each timeslot interrupt the driver toggles its own slot number and compares it with the received TC. The TC read there belongs to the slot that just ended, so the slot starting is the other one (HRC6000_DMR_TC_IS_SLOT_NOW 0). Read as the slot starting, a subscriber through a full duplex repeater was one slot off both ways: it heard outbound TS2 as TS1 and transmitted its TS1 under outbound TS2 (bench, 2026-10-27). Read right, a subscriber on TSx receives outbound TSx and transmits under it: the aligned timing of ETSI TS 102 361-1 5.1.1, table 5.1. The AT for TSx comes in the CACH before the other outbound slot (dmr-modem.md 1.6, split-duplex.md 5.2).

The driver toggles its slot number at every timeslot interrupt, received or not, and compares only after a received slot. Locked to one slot, the chip receives one slot in two, and a transmission skips the compare altogether: toggled only at a compare, the number fell out of step and resynced onto the wrong slot mid-call.

Parameter Value
agreements needed for "stable" more than 4 consecutive
"locked" stable, then the first slot whose number is not the wanted one; from then on receive one slot in two
disagreements before resync more than 3 (each disagreement also takes one agreement away)

Once locked, write 0x41=0x50 before our slot and 0x41=0x00 before the other. The CACH is then not refreshed in the other slot, so the TC compare is only meaningful before the lock. The driver compares only when the slot that ended and the one before it were both received (gotchas 1.10): after a slot not received the TC read is junk (43% agreement on the bench), and those reads used to resync a good lock. Once locked, the number is kept by the toggle alone until the reception ends (5.5).

In direct mode there is no CACH: lock to the slot of the first good burst (its number is meaningless) and receive one slot in two from then on.

5.4 Color code acquisition (when the user's CC filter is off)

Reconfiguration keeps any-CC listening. The receive code stays in 0x1F while an aligned start waits for its slot. Before the first TX slot, the driver writes the channel's transmit code; after TX it restores the receive code. A receive filter or reconfiguration during TX takes effect when TX finishes: the receiver restarts then (5.1), in place of a direct transmission's end hold.

The chip only deframes bursts whose CC matches 0x1F unless 0x41 bit 3 (CC_Match_Ctrl) is set.

HR_C6000: with the filter off, every receive write to 0x41 sets bit 3 (0x58 in place of 0x50), so the chip deframes every call whatever its CC. The driver only notes the CC seen in 0x52 (two matches within 200 ms), for the next transmission; it doesn't rewrite 0x1F or restart the receiver. Restarting on a CC change lost the first call after the change: its headers always, its voice in most tries. With bit 3 set, the first call after a change decodes in full, through a repeater and in direct mode with each call on another CC.

HR_C5000 (bit 3 not confirmed on this chip): follow an unknown CC. At each system interrupt with an SNR margin of at least 5 dB, compare 0x52's CC with the last one seen (within 200 ms). On every second match write the new CC to 0x1F and rewrite 0x40=0xC3 (through a repeater also the 0x41 resync sequence: 0x20, 0x00, 0x20, 0x50), then wait 3 ms (a busy wait in the interrupt: faster rewrites crashed the radio). After 8 matches the CC is held. Release the hold after 5 s of no received audio while idle.

A call in a CC other than 0x1F's raises no system interrupt on the HR_C5000, so the follow above never starts for it, and 0x41 bit 3 made no difference in a test. The timeslot ticks still come while a signal is present. At each tick while idle and receiving, 0x52 bits 7-4 read the call's CC on the call's slot phase and other values on the other phase. So the driver counts 0x52's CC per slot phase (cc_tick_follow). After 3 equal reads on one phase that differ from 0x1F's CC, it writes that CC to 0x1F and restarts the receiver, as for any CC change. It skips this when the CC is held, during TX, while a restart is pending and for 4 ticks after one.

The driver chooses by the chip description's cc_any_rx.

5.4a CACH short LC

The chip assembles the CACH short LC from four CACHs and leaves it in page 2 0x2B-0x2F: 36 bits, MSB first, the 28 short LC bits then the CRC-8; the low 4 bits of 0x2F are unused (hrc6000-registers.md 2.2). While receiving both slots of a BS signal (rx_lock_slot(0), a trunked control channel) and idle, the driver reads it at each timeslot interrupt after a received slot and reports it (DMR_EV_SHORT_LC) when the bytes change. It doesn't wait for 0x86 bit 2 (short LC received): that flag comes with the TX-end interrupt (0x82 bit 5), which the mask leaves off. The chip descriptor's slc_rx_addr gives the location; a chip without one reports none. On air a TSCC gives about 8 short LCs a second, about 0.15% with a bad CRC.

5.6 Late entry

The post-access interrupt (0x82 bit 4) comes when the chip acquires a voice call in progress from its embedded signaling. If idle, with the CC held and matching: write 0x41=0x50 and start receiving as for a header. Skip voice until two bursts A have passed, unless the source ID is already known and isn't our own. The LC comes from page 2 once the embedded LC is complete (subject to the sticky-LC rule above). The driver reads page 2 at the interrupt and keeps an LC that differs from the capture for the next voice burst (counted as lc2 p=, traced as P). On the HR_C5000 the interrupt comes once per superframe, just after burst E (bench trace), and starts the decoder, so it comes before the reception. An LC read then that differs from the last capture is kept for the reception's first burst (traced pk): the capture that follows holds that same LC, and the sticky rule would make it wait for the next A. On the HR_C6000, on the bench (a call joined at burst C of its second superframe), it came before the next F in most runs and the LC was taken there; on a weak signal it came one superframe later in 2 of 9 runs, page 2 still held the old LC at F, and the call played from the superframe after that.

Joining at burst A. With no header and no superframe in progress on its slot, a voice sync report (burst A) is held, not played: it can be noise or the tail of another slot's call. It is taken when the next frame (2 ticks later) brings a class 0 report for burst B; otherwise it is dropped (counter rx_lone) and the class 0 reports that follow count as rx_no_call until the next A. The B check differs by mode:

Receiving B is
One color code (0x41 bit 3 clear) a class 0 report numbered 1
Any color code (bit 3 set, 5.4) a class 0 report numbered 1, or any class 0 report one frame after the A with voice other than A's (a stale repeat of A's report has A's voice). For a call in a code other than 0x1F's, the chip keeps the voice number of the last call it decoded in full (bench: B-F all reported as F), and the driver can't tell which code the call is in, so the number isn't checked; the frame count numbers the rest (5.2)

Before the second rule, a scan with digital monitor on passed any call in another color code that it reached after the header: the A was dropped as lone and B-F as no-call, superframe after superframe, and the stop timed out.

Resuming a call. A call that stopped with no terminator and comes back has the sticky LC problem in its worst form: the LC in page 2 is the call's own, so the sticky rule waits for the A after the first whole superframe. That page 2 still shows the call's LC proves nothing: it would show the same if another caller had started. The post-access interrupt does prove it, read twice:

Rule Why
Two post-access reads, 8-13 ticks apart, both show the LC of a slot's call that is open (no terminator) with voice in the last 50 ticks (1.5 s) Each read is an LC the chip assembled from what is on air. One read isn't enough: nothing on air shows page 2 is written by the time the interrupt comes, and gotchas 1.4a shows it can lag
Any read showing another LC clears the count That LC follows the normal rules, so another caller is never played or named as the old call
A terminator closes the call The same LC after it is a new call, with the sticky rule
An identical LC from a new transmission Treated as the same call. Same source and destination, so the name shown is right

This takes back about one superframe of the wait, not all of it (traced Pr, counted as lc2 r=). Taking the first read would save another 300 ms, but needs an on-air run with a second caller in the gap. The call stack counts the call once (rx_calls_resumed, dmr-modem.md 2.4).

5.7 Audio buffering

Decode the 27 bytes as three 20 ms frames. If, between two bursts A, fewer than 5 other voice bursts arrived, insert one frame of silence so the playback buffer recovers instead of stuttering. If the PCM buffer is nearly full (fewer than 3 free 20 ms buffers), skip decoding the next 6 frames. After a voice-abnormal interrupt on our slot, play silence for the next frame. AMBE silence frame (9 bytes, repeated three times per burst): B9 E8 81 52 61 73 00 2A 6B.

6. Transmit

6.1 Burst set-up

For each burst, in the timeslot interrupt before its slot:

Burst Writes
Voice LC header LC (12 bytes, section 6.4) to page 2 0x00; 0x41=0x80; 0x50=0x10
Voice A..F AMBE (27 bytes) to page 3 on V_SPI; 0x41=0x80; 0x50 = 0x08 | (n << 4), n = 0..5. The chip adds the voice sync on A and the EMB + embedded LC fragments on B-F from the LC in page 2
Terminator with LC LC to page 2 if it changed; silence AMBE to page 3; 0x41=0x80; 0x50=0x20
CSBK / data header / data block / any data type payload (12, 18 or 24 bytes) to page 2 0x00; 0x41=0x80; 0x50 = DT << 4 (LCSS 0)
Slot not ours 0x41=0x00

CRC: with 0x40 bit 3 (CRC_MCU_Control) clear the chip computes the CRC (masked per data type) for headers, CSBKs and LCs; with it set the 96 info bits are sent exactly as written (the MCU supplies the CRC; bad CRCs go out as given). Change bit 3 only when the next burst needs a different setting (read-modify-write of 0x40). The chip still does the FEC (BPTC, trellis), slot type and sync in both cases. Restore bit 3 to 0 at the end of the transmission: rewriting 0x40=0xC3 does it. Bit 3 seems to affect the receiver's deframer too: inbound headers decoded while the chip was framing a burst with bit 3 set came out bad.

The idle message has its own place in the TX RAM: page 2 from 0x18. Writing it there keeps the LC at 0x00 for voice bursts that follow.

6.2 Starting a transmission

Common: 0x21=0xA2 (polite to own CC, clear the encode buffer), 0x22=0x86 (start encode, I2S).

  • Direct mode: from idle, with the modem interrupts masked: 0x21, 0x22 as above, unmask, then 0x40=0xE3 (active timing). The timeslot interrupts start on the chip's own timing; the next one starts the burst sequence.
  • Through a repeater, already receiving it (its hang time or a call): stay in passive timing; when the slot tracking is stable with no disagreement and the slot that just started is the other one, lock to ours, write 0x21=0xA2, 0x22=0x86, 0x41=0x00, and start the sequence at the next timeslot interrupt.
  • Through a repeater, nothing heard: wake it (section 6.5) first.
  • Data: as voice, but the sequence sends the queued bursts instead of headers and voice.

Polite access: with 0x21=0xA2 the chip refuses to send while our CC is busy on the channel (send-rejected interrupt). A transmission that must go out in a busy channel (an SFR repeat, a reply in a repeater's hang time on a single frequency) writes 0x20=0x00 and 0x21=0x02 (impolite).

So a transmission is 3 voice LC headers in our slot (180 ms of lead-in), then whole superframes, then the terminator. It always ends at a superframe boundary: PTT release takes effect only before burst A.

Encoding: each 40 ms of PCM (two 20 ms buffers) gives one 9-byte AMBE frame; the voice burst takes three. Encode in a 1 ms-tick task ahead of the timeslot interrupt; a 4-burst ring of encoded frames is enough. The AMBE codec code is a binary blob supplied per radio (codec-placement.md); its glue must not be compiled with optimization that changes its inline assembly (it crashed DMR TX at -Os).

6.4 LC content

12 bytes to page 2: FLCO (0x00 group, 0x03 private), FID, service options, destination ID (3 bytes), source ID (3 bytes), 3 bytes 0. The chip computes the RS(12,9) parity unless CRC_MCU_Control is set. For privacy, the FID and service options carry the privacy bit (see dmr-modem.md).

Talker alias: during the first superframe of each pair, page 2 holds the call LC; in the other, one talker alias block, cycling header (FLCO 4) and blocks 1-3 (FLCO 5-7), 7 bytes of text each (the header carries the format and length in byte 2 and 6 characters), and FLCO 8 for GPS (7 bytes: longitude as 25-bit two's complement scaled 2^25/360, latitude 24-bit scaled 2^24/180). The chip spreads the 72-bit embedded LC over bursts B-E.

6.5 Repeater wake-up (BS activation)

  1. Write page 2: B8 00 00 00 00 00 00 + source ID (3 bytes) + 00 00 (BS_Dwn_Act CSBK, LB=1, BS address 0), 0x50=0x30 (CSBK), 0x41=0x80, 0x40=0xE3 (active timing). One CSBK in our slot.
  2. Next timeslot interrupt: arm the 29 ms PA-off timer, restart the receiver (passive).
  3. Wait for the repeater: the received TC must toggle correctly more than 3 times in a row. Then treat it as the "already receiving the repeater" case above.
  4. No answer in 600 ms (the retry period): send the CSBK again, up to the codeplug's wake attempt count, then fail.

6.6 Data transmission

A list of up to 64 bursts (CSBKs, headers, blocks) goes out one burst per slot on our slot, with an idle slot between (our slot only), starting from the first "our slot" step of the sequence (no voice headers, no terminator). After the last burst, the end steps 10-11 restore passive timing / the receiver and clear CRC_MCU_Control. Timeout: 10 s plus 60 ms per burst (covers a repeater wake-up). A received-data interrupt for a data burst is queued (8 deep is enough; the packet CRC catches overflow) and handled outside the interrupt.

End of a transmission. The transmission is over at the timeslot interrupt where our next slot comes with nothing queued and the end asked for, if the last burst's PA has dropped and the slot starting is not a TX slot. Waiting for the interrupt after that one left the slot after our last burst closed (0x41 = 0) with the RF still on the carrier. An answer can start as our last burst ends (on the SDR bench, an MS simulator's link ACK to confirmed data; its report came 4.5 ms after the next timeslot interrupt). That answer was missed on every try.

In direct mode the end then holds the receiver instead of restarting it: 0x40 = 0xC3 (passive timing from our active one), 0x41 = receive, and the software state reset as at a restart. A burst taken holds the receiver as any reception does. With nothing taken, the restart (reason "tx end") comes from the poll 8 ms after the next timeslot interrupt, once that slot's report is no longer due (a restart at the interrupt itself lost it), or 35 ms after the last interrupt if they stop. An answer a slot later, off our timing by a few ms, is taken after the restart: the held timing gave only late class 0 reports for it. Through a repeater, or after a transmission that set up no burst, the restart comes at once. Diagnostics: rs ... h counts the holds.

6.7 Which slot to transmit in

Through a repeater: the channel's timeslot, from the CACH. In direct mode the chip's own timing defines the slots and the "our slot" phase is the one the sequence starts in. Single-frequency repeater users transmit in the other slot than the one heard: when keyed while hearing the repeater, start the sequence from the step that sets up the slot heard, so the first burst lands in the opposite slot.

7. Timing quirks found on air

  1. "Transmitting" must come from the modem slot state. The PA and the RF chip's TX mode toggle every burst (section 4.3), and putting the RF chip in RX between bursts clears any "transmitting" flag that follows it. A status reported from that flag dipped to idle for one poll mid-call, and stopping the transmission on it cut the call. Report "transmitting" from the first header's set-up to the end of the terminator's slot (steps 1-11 above, plus the data states).
  2. The terminator's slot is step 11, not step 10. Treating step 11 as "already finished" ended every call before its terminator was on air (24 of 24 calls lost their end on the SDR). Only after step 11 is the transmission over.
  3. Ending a call (PTT release or a host's end of call) must not stop the RF. Only clear the "transmission enabled" request (as a PTT release does) and let the sequence finish the superframe and the terminator. Switch the RF to receive only once the modem slot state is idle. If a voice frame handed to the modem hasn't been sent yet, wait for it, or the modem sends silence in its place.
  4. No startup silence. Feeding silence frames before the first real voice delayed every call by 360 ms per superframe of silence. Start with the real first frame; the 3 headers are the lead-in.
  5. A host's end of call (terminator) ends the call once the voice buffer is empty, or 360 ms after the last voice with none.
  6. Every voice burst number arrives with the voice bit set (0x9..0xE): matching 1..6 exactly drops every burst.
  7. A second received-data interrupt per voice burst (the EMB report): de-duplicate within 45 ms.
  8. While the chip transmits, its reports about bursts it hears are unreliable: the CRC flag, CC and sync type, the data type (a second report per slot with another type), and the info bits of headers and terminators (bytes 5-11). Every CSBK and data header heard while sending failed its CRC by 11-23 bits spread over the burst. A deferred re-read of 0x51 at the next timeslot interrupt often reads 0x00. Treat what is heard while transmitting as suspect (an SFR holds data calls until it stops sending).
  9. Bursts in step: a received-data interrupt 3-5 ms after the timeslot interrupt means the sender is in step; 25-30 ms means out of step: resynchronize the receiver (section 5.1).
  10. The color-code probe busy-waits 3 ms in the interrupt after rewriting 0x40; don't run it while transmitting.
  11. SPI contention: the U_SPI is shared by interrupt and thread code with a simple in-use flag; a transfer attempted while another is running is refused (counted on SFR builds). Mask the modem interrupts around thread-level transfers.
  12. Retuning the instant "transmitting" clears is safe once (1)-(3) hold: measured 0.70-0.73 s after the host writes its terminator (buffered voice + the rest of the superframe + the terminator), never before the terminator is on air.

FM RX: 0x60=0x00, 0xE0=0x89, 0x10=0x80, 0x34=0x3C, 0x81=0x19, 0x85=0x00, 0x26=0xFD. Audio feed-through 0x36=0x02 (0x00 mutes); 0x10 back to 0x6E for DMR.

Codec in FM mode: with 0x10 bit 7 set (FM) the codec's line out carries the chip's own FM receive audio, and 0x36 bit 1 switches it on (the manual: in FM mode, receive opens the voice channel's codec switch). I2S PCM (beeps, prompts) doesn't reach the line out then, with the bit set or clear. A board whose FM audio comes from elsewhere puts 0x10 back to DMR after the FM receive rows (hrc6000_fm_rx_pcm()), so PCM plays in FM receive as it does in DMR.

Tones (0xA1 mode): 0x80 off, 0x88 CTCSS, 0x84 DCS, 0x82 DTMF, as traced. The manual's register table differs: 0xA1 is fm_mod, bit 7 is reserved and must be 0, bit 6 MSK, and its appendix selects CTCSS with 0x08, CDCSS 0x04, DTMF 0x02, 2-tone 0x10, 5-tone 0x20. With bit 7 set (the init's 0x80) a board that feeds the chip a 450 kHz IF never gets a DMR sync, though the chip's RSSI (0x43 / 0x44) follows the signal; hrc6000_tones_off() writes 0x00 after the power-on init. The other boards receive with 0x80 and haven't been tried with 0x00.

  • CTCSS TX: 0xA1=0x88, 0xA8 = tone index. RX: 0xA1=0x88, 0xA7=0x10 (threshold), 0xD3=0x07 / 0xD2=0xD0 (sampling depth 2000 = 250 ms at 8 kHz), 0xD4 = tone index. Detected: 0x93 bit 0.
  • DCS TX: 0xA1=0x84, 0xA2 = 0x00 inverted / 0x08 normal, 0xAB = code bits 7-0, 0xAC = code bit 8. RX: 0xA1=0x84, 0xA2 = 0x04 inverted / 0x00 normal, 0xD4 = code bits 7-0, 0xD3 = (code bit 8 << 4) + 0x03, 0xD2=0x20 (depth 800 = 100 ms).
  • DTMF TX: save 0xA1, 0xA0 and 0xD1; 0xA1=0x82, 0xA0 = deviation, 0xA4=0xFA (tone time), 0xA3=0x19 (gap, 2 ms units), 0xD1=0x01 (one code), 0xAF = code << 4, 0x60=0x00 then 0x80 to send. Restore the three registers after (the high bits of 0xD1 matter). Seen on air: 0xA4 = 0xFA is 500 ms, not continuous; one code is at most 510 ms and ends in about 20 ms of silence (hrc6000-registers.md 7.6).
  • Tone table (page 1, extended addresses, value = f x 65536 / 32000, low byte first): 0x11A/0x11B 697 Hz (0x0593), 0x11C/D 770 (0x0629), 0x11E/F 852 (0x06D1), 0x120/1 941 (0x0787), 0x122/3 1209 (0x09AC), 0x124/5 1336 (0x0AB0), 0x126/7 1477 (0x0BD1), 0x128/9 1633 (0x0D10). Any DTMF pair: put its values in the 697 and 1209 entries and send DTMF "1"; restore the entries after.
  • A single tone (1750 Hz burst, roger beep, AFSK; hrc6000_tx_pair): 2-tone mode (0xA1 = 0x10, bit 7 kept), every entry 0x11A-0x123 set to the tone, 0xA4 = 0xA5 = 0xA6 = 0xFF, 0xA3 = 0, code "A-B" (0xAF = 0x0A, 0xAE = 0xB0): one gapless tone of at least 25.5 s. The driver starts the sequence again before it runs out (hrc6000-registers.md 7.8).

9.1 Continuous BS outbound (split duplex TX half)

drivers/modem/hrc6000/hrc6000_bs.c (CONFIG_HOTSPOT_SPLIT, split-duplex.md 5.4) takes the chip over from the slot engine while the split duplex TX half runs; the engine's three ISRs, its watchdog, halt and is_transmitting hand over to it while e->bs is set. Start: color code, page 1 0x04 = BS data sync, 0x20 = 0x00, 0x21 impolite, 0x22 = 0x86, 0x41 = 0x00, then 0x40 = 0xE3 (own timing: the timeslot interrupt runs free every 30 ms). Every timeslot interrupt while keyed sets up the next slot from that slot's queue (or the idle message on page 2 0x18, counted as an underrun): the MCU CRC bit of 0x40 per burst kind, the payload (voice on page 3, LC / data on page 2 0x00), 0x41 = 0x80 and 0x50. Page 2 0x00 is shared by both slots, so a slot's embedded LC is written back before its voice A-E whenever the other slot's header or data overwrote it. The first burst after a key-up is an outbound TS1 slot (outbound slot = ((tick - base) & 1) ? TS1 : TS2). The PA is keyed once: at the RF TX interrupt, or at the first slot's set-up when that interrupt came before it, and a key the board could not do is tried again at the next slot. It is dropped at the first timeslot interrupt after the unkey, or by the watchdog when no timeslot interrupt came for 200 ms. Stop: 0x10 / 0x11 back to 0x6E / 0x80, MS sync, 0x40 = 0xC3, the slot engine restarts the receiver.

The CACH: the manual has the MCU give the BS downstream CACH's AT and TC in 0x52 (written) and the short LC in TX RAM 0x24-0x28, and the chip encode it. On air (2026-10-12) the layer 2 CACH stays all zero whatever is written there, in every 0x10 / 0x11 / 0x50 combination tried (9.2). What works is the physical layer mode (0x10 = 0x66, LayerMode 00), which the manual documents only for receive: the chip then modulates TX RAM page 2 as given, 288 bits per slot (24 CACH, 264 burst, MSB of the first byte first), from 0x00-0x23 and 0x24-0x47 in alternate slots, and takes its half at the slot start. The slot interrupt, 0x41 = 0x80 and the PA keying work as in layer 2. The driver writes each slot's frame (bsOutboundRawSlot) to both halves, since which half is which slot isn't known, and nothing to 0x50, 0x52 or the vocoder. Variant 1 keeps the layer 2 framing (0x52 and the short LC written for every burst) for comparison; 255 adds up to four raw page 4 pairs at key-up. Host test: tests/host/hrc6000BsTest.c.

The key-up (our framing). In this mode the chip raises the RF TX interrupt once per key-up, anywhere in the slot (5.8 to 30.1 ms after the timeslot interrupt in three key-ups), not ahead of each slot, and it sends TX RAM whenever the PA is up. So the PA can come up in the slot before the first frame, or inside the first frames. Three rules keep that off the air as harm:

Rule Why
At the key and while it waits for the TS1 slot, both halves hold an idle TS2 burst with the default CACH (LCSS last, no short LC) the slot before the first frame otherwise sent whatever TX RAM last held: an out-of-sequence CACH
The first two slots set up get the default CACH, not the core's a CACH clipped by the rising PA can decode as LCSS first; with the core's fragments after it, the decoder assembled a short LC with a bad CRC (about one key-up in three). The next fragment now breaks the sequence. The first short LC comes 60 ms later
A board whose key-up is slower than the CACH times it from the slot clock (stm32_hrc_dmr_bs_boundary_us) full power after the slot's sync and ahead of the next CACH

On the SDR bench, 10 key-ups of 10 s each: no bad short LC, TC alternating, against a bad short LC in two of four before.

Restarting the slot timer (ALIGN, split-duplex.md 3.8; bench 2026-10-21): 0x41 = 0x00, 0x40 = 0xC3, 0x41 = 0x20, 0x00, 0x20, 0x00 (the 5.1 sync drop), then 0x40 = 0xE3 at the chosen time. The first timeslot interrupt comes 1.18-1.24 ms after that write and every 30 ms from it, and none comes during the wait. Clearing TxEn and RxEn (0x40 = 0x03) or 0xC3 then 0xE3 without the sync drop stopped the timer only sometimes: interrupts kept coming during the wait and the old phase came back. The driver takes no interrupt while it waits and gives the requested slot to the boundary the time since the write names (a slot per 30 ms, from 15 ms on); the diagnostics line bs shows the restarts (rs), interrupts during waits (ri) and the first three after the last write (r1-r3, µs).

The layer mode for the whole session. 0x10 (the physical layer mode of our framing) is written at the start, ahead of 0x40 = 0xE3, and back to 0x6E at the stop, never at a key-up. Written at the first keyed slot, it moved the timeslot interrupt: the next one came 12.9 or 19.1 ms after the last, and every one after kept 30 ms from it. The clock was then 12-17 ms off the ALIGN grid for the whole call, and the 15 ms same-slot filter counted one slot too many or too few, so the call went out in the other grid slot (4 of 4 calls). With the mode set from the start, keyed interrupts stay within 0.6 ms of the grid (4 of 4). In this mode the restart's first interrupt comes 22-30 ms after the write instead of 1.2 ms, numbered as the slot after the one named for the write. Writing 0x10 = 0x66 just before or just after the 0xE3 write, or in layer 2 for the stop and sync drop, changed nothing (25-30 ms); switched at the new clock's first boundary, the next interrupts came 64-89 ms after the write. So one restart lands up to a few ms off at random, and learning the delay doesn't help: the core snaps again until a landing is inside the aligned bound (split-duplex.md 3.8), and an ALIGN to a grid the clock is already on restarts nothing.

No slewing. The manual lists no slot length trim, so the driver offers no bs_slew and INFO capability bit 2 stays clear: a keyed TX half reports its drift (ALIGN flag 10) and is re-aligned by a restart at the next unkey.

10. Physical layer pipe

10.2 Receive

Set-up: 0x41 = 0x00, 0x10 = 0x02, the pattern in aux 1:0x47-0x4C, 0x5F = 0xF0, 0x40 = 0x40, 0x41 = 0x40 (soft records). 0x36 = 0 for the whole session, so nothing of the receiver reaches the codec's line out.

  • The correlator holds one pattern (aux 1:0x47-0x4C, write only, 48 bits as the dibits go on air; the DMR value is D5D7F77FD757). Only one of the comparators frames at a time, so the profile's first suitable 24-symbol sync goes there. Each inner symbol in the pattern weakens the match: 4 of 24 found about two syncs in three, 8 none at the threshold aux 1:0x54 = 0x78. Lowering the threshold to 0x50 finds them but triggers on noise.
  • A record is 144 symbols (30 ms), read as 288 bytes from page 2 0x30 when the system interrupt shows 0x82 bit 0, 2.4 ms after the timeslot interrupt. 0x51 bits 1-0 = 2 when the correlator fired in it, else 0; 0x5F bits 1-0 say which comparator.
  • Two bytes per symbol: bits 5-0 of the first are the level, 6-bit two's complement; the second only repeats the slice. The hard bits the chip slices are 5-20 times worse than slicing the levels, so the driver slices its own.
  • The record's order depends on 0x51 (chip symbol ranges, in air order):
0x51 bits 1-0 Air order
2 (sync) 0-11, 46-94, 12-16, 22-45, 17-21, 95-143: the pattern starts at air symbol 66
0 0-11, 36-89, 12-35, 90-143
  • Levels are about 11 counts per kHz of deviation (outer about ±22 at 1944 Hz), with an offset of a few counts that follows the carrier's. The counts per kHz are the board's receiver's: one board gave 1.4 times as many, which put the inner symbols at the slicer's threshold (5 % symbol errors). So the driver takes the outer level from each detected sync, as half the distance between the means of its +3 and -3 symbols: at once on a new signal, a quarter of the way per sync while in step. 11 counts per kHz is the start value, and a sync that reads under half or over twice of it is ignored. The driver removes a slow average of the offset and scales the outer level to AIR_SOFT_OUTER; hard symbols are sliced at 0 and two thirds of it. With that the symbol error rate on a clean C4FM signal is under 0.1 %.
  • A record is always the 144 symbols before its boundary, and the chip moves the boundary by whole symbols at a sync. After a signal's first sync the next record comes 128 symbols later and repeats 16; the first sync found in step comes 160 symbols after the record before it, and 16 are lost. The first 4 to 12 symbols of both records are not the signal's. The driver places every record by its boundary's time. Repeated symbols are dropped (a chunk shorter than 144). Up to 192 lost symbols are delivered as chunks of erasures (soft 0, sync_at -1), so a framer loses those symbols and not its frame: that covers the 16, a re-arm's hole (124 symbols with a sync every 6 records) and one record lost. A step of one symbol is within the interrupt's jitter and is left alone.
  • Nothing is delivered before the first sync. After one, records keep coming for 0.7-0.9 s, and about 2 s after a signal ends. With the pattern every 288, 864 or 1728 symbols nothing was lost.
  • The chip's timing takes a step of 0.5 ms and not one of 1 ms: after that it delivers records on its own timing and never fires again. The driver re-arms it after K records in a row without a sync (K = the sync spacing in records
    • 1): 0x41 = 0x60, then 0x40 40 ms later. It is back about 0.24 s later, and a re-arm with no signal is harmless.
  • t_us of symbol 0 = the timeslot interrupt before the record - 30 ms + half a symbol. The delay from the air to that clock is not measured (time_accuracy_us 3000).
  • Chunk flags: GAP on the first chunk after open, rx_restart or a transmission, when more symbols were lost than erasures stand in for, and when the task was behind and a record was dropped; FREE_RUN when more records than the sync spacing passed without a sync. rssi_dbm is 0.

10.3 Transmit

Set-up at tx_begin: 0x41 = 0x00, 0x10 = 0x66, 0x20 = 0x00, 0x21 = 0x02 (impolite), 0x22 = 0x86, the profile's idle in both TX RAM halves, then 0x40 = 0xE3 (own timing). The first timeslot interrupt comes up to 30 ms later (the receive set-up's slot clock runs on; about 28.7 ms after a stop with 0x40 = 0x03), then every 30 ms.

  • The chip sends TX RAM page 2 0x00-0x23 and 0x24-0x47 in alternate slots, 288 bits each, first bit 7 of the first byte, and reads a half while it sends it: a half written at the timeslot interrupt that starts its slot loses about its first 32 bits. So each interrupt writes only the half the next slot reads, and 0x41 = 0x80. Counting the timeslot interrupts from the 0xE3 write (the first is 1), slot n + 1 is set up at interrupt n and reads 0x00 when n is odd: the first slot set up reads 0x00. Off air this held in every key-up, with the first interrupt anywhere from 2 to 29 ms after the write, and after transmissions of an odd and an even number of slots. A chunk written to the other half goes out in the slot then starting, its first 32 bits those of the chunk two slots before. 0x42 does not tell the halves apart: it reads 0xA0 at every interrupt of a transmission after the first.
  • The modulator sends TX RAM only in a transmit slot. In any other slot it rests about 3 kHz below the channel: a PA keyed in slot 1 sent that as a bare carrier, and the step onto the channel fell under the first chunk's symbols (a C4FM receiver then lost the first unit). So interrupt 1 sets slot 2 up with idle, the PA is keyed at interrupt 2 as that slot starts, and the first chunk goes out in slot 3. The PA is held for the whole transmission.
  • In this mode the RF TX interrupt comes once per key-up, anywhere in the slot. It keys nothing before slot 2 starts; after that it only tries again a key the board could not do.
  • A slot boundary to that slot on air: 2.2 ms. AIR_EV_TX_STARTED gives the first chunk's first symbol by that.
  • Each chunk taken from the queue gives AIR_EV_TX_SPACE (events in a row are one), so the core refills the queue before it runs dry.
  • An empty queue mid-transmission sends idle and gives one AIR_EV_TX_UNDERRUN. The last chunk is padded with idle, one idle slot follows it, and the PA drops at the next timeslot interrupt, so about 28 ms of idle follow the last symbol. Then AIR_EV_TX_DONE, the deviation pair back and the receive set-up. With no timeslot interrupt for 200 ms the transmission is dropped the same way.
  • Deviation: Mod1 (0x46) moves the outer deviation linearly, about 23.8 Hz per step, through zero; Mod2 (0x45) must keep its ratio to Mod1 (about 0.51). tx_begin reads the pair the board set for the channel (calibrated for 1944 Hz) and scales both by target / 1944: from 0x52 / 0x2A, 1800 Hz is 0x4C / 0x27 and 2400 Hz 0x65 / 0x34. Above Mod1 0x65 is not checked. For C4FM the target is the deviation / 0.946: the chip's pulse is DMR's, and a C4FM receiver reads 0.946 of its outer level (measured off air from the SDR bench's I/Q: 0.903 gave 1873-1900 Hz for 1800 Hz, 104-106 %; 0.946 gives 1783-1793 Hz). 0x04 moves the carrier (about +24 Hz per step); 0x47 and 0x48 do nothing here.

10.6 Receive through the FM copy

For a profile the correlator can't take, on a board whose RF chip gives the chip the unfiltered discriminator in its DMR set-up (stm32_hrc_dmr_board_t.air_tap). The chip's FM receive RAM is a copy of what its FM demodulator hears; the driver feeds the core's soft modem (core/air/air_softmodem.c, air-interface.md) from it. Transmit stays 10.3, so a profile the chip can't send gets no fit at all.

Set-up (copy_on): 0x41 = 0x00, 0x36 = 0x00, 0x60 = 0x00, 0x34 = 0x00 (every receive audio filter off), 0x10 = 0x80 (FM), 0x81 with bit 1 set (the FM receive RAM's interrupt), 0x83 = 0xFF. 0x34 and 0x81 are read first and written back at close.

  • The RAM is page 2 0x030: two halves of 256 samples, 16 bits big endian, 8 kHz. 0x82 bit 1 comes when a half is full, every 32 ms. With 0x10 back at its DMR value the RAM stops filling, so the chip stays in FM for the whole session.
  • The interrupt does not say which half. The driver reads each half's last sample at every interrupt: the half whose last sample changed is the full one. When both or neither changed (a steady input) it is the other half than the last one (half_fixes counts the times the RAM disagreed with that order).
  • The interrupt copies the full half into a ring of two halves, stamped with its time (the last sample is the interrupt's, the first 255 samples earlier). A half that finds the ring full is dropped (overruns), and the half after it starts the soft modem over, as does the first half after open, rx_restart or a transmission.
  • The task runs the soft modem on each half. Its state lies in the halted slot engine's transmit queue, at the first address aligned for it (the queue is bytes; an unaligned state faults).
  • The band is 0 to 3400 Hz. The counts per kHz are not known (rx_counts_per_khz 0): the soft modem takes the level from each sync. Positive is above the carrier.
  • For a transmission the chip leaves FM for the set-up of 10.3, and rx_setup after it is copy_on again.
  • The same ring is the board's hal_baseband_t receive tap while no session is open (stm32_hrc_baseband).
  • rx_load counts the soft modem's time for a session that receives this way and reports false for one the correlator serves.

The codec's PCM stream to the MCU runs on in this set-up (a beep's blocks come at the same rate as in DMR), and decoded voice goes to the codec's DAC as in DMR. Checked on air: NXDN calls at 4800 and 9600 bit/s from a bench transmitter, every frame decoded and every voice frame of a speech recording decoded by the vocoder, none counted bad (test_nxdn_rx_from_bench, test_nxdn_rx_speech); a DMR call received right after sessions of both kinds. Not checked: the level at the speaker by ear or by measurement (decoded voice is judged by its PCM peak), the sensitivity, the receive delay for t_us.

10.7 The HR_C5000

The HR_C5000 user manual has the same physical layer mode: 0x10 LayerMode (bits 4-3) = 00, the 0x82 bit 0 interrupt for physical layer receive only, the 30 ms timeslot interrupt in the physical layer and data link modes, and 36 bytes of physical layer data in page 2 (addresses 0-35). The slot engine already drives the same 0x40 and 0x41 slot control on both chips. So the provider runs on it unchanged, and the chip description (hrc_chip_t) gives what differs:

HR_C6000 HR_C5000 Where
0x5F sync type (sync_reg) written 0xF0 at rx_setup not written: the comparators run as reset left them rx_setup
Transmission start (tx_begin) the chip's own: 0x20 = 0, 0x21 = access, 0x22 = 0x86 (encoder start) the access policy alone (0x20 = 0, 0x21 = 0x02): the vocoder runs on the MCU hrc6000_air_tx_begin
0x10 after close (mode_per_channel) 0x6E the chip's dmr_mode; the engine writes the channel's value again when it runs hrc6000_air_close, hrc6000_dmr_run
FM copy (10.6) yes none documented: no air_tap, so the correlator profiles only the board
Physical layer receive (air_tx_only) yes none found (below): the fit drops AIR_FIT_RX, AIR_FIT_SOFT and AIR_FIT_NEEDS_SYNC, and an open session doesn't write the correlator pattern hrc6000_air_fit_tap, hrc6000_air_open

On the radio, transmit works: the provider keys P25 and NXDN from the TX RAM halves as on the HR_C6000. Receive doesn't: in an open session with the receiver on, 0x82 stays 0 and the chip gives no physical layer record (airp.records=0, view air in debuglink.md). Writing 0x40 (0x40, 0x43, 0xC0, 0xC3), 0x41 (0x40, 0x41, 0x50, 0x60, 0xC0) or 0x81 (0x01, 0x19, 0xFF) by CHIP_REG during the session changed nothing, and 0x81 reads back 0 after a write. Writing the pattern into the transmit sync field (aux 0x04-0x09) as well didn't help either. Until a setting that starts the record clock is found, a radio with this chip transmits the correlator profiles and can't receive them. The chip description says so (air_tx_only): the provider reports those profiles as transmit only. P25 needs receive, so the radio doesn't offer it; NXDN stays for transmit, and scan skips a channel the radio can't hear. A board that gives the provider an FM copy (air_tap) still receives through the soft modem.

Not confirmed on the HR_C5000, because the manual is an early draft and leaves these out:

  • 0x40 = 0x40 / 0x41 = 0x40 for soft records, and the record format at page 2 0x30 (144 levels of 6 bits).
  • The correlator pattern at aux 1:0x47-0x4C (the provider writes it at open and the MS pattern back at close).
  • The second TX RAM half at page 2 0x24: the manual gives 36 bytes.
  • 0x36 = 0 at open (on this chip 0x36 also carries the I2S clock set-up).
  • The 0x45 / 0x46 two-point pair and its scale with deviation.

Nothing of 10.5 has been checked on this chip; its fits stay AIR_FIT_UNTESTED.

Open: what starts the physical layer record clock on this chip (11).

11. Open questions

  • Page 6 (manual: TX RAM) vs page 2 for TX: page 2 works; page 6 untested.
  • The meaning of the unexplained init values (0x10=0xF3 / 0x6B during init, the 0x11-0x3C bulk block, the page 1 tables).
  • Whether the post-access interrupt is reliable for data calls (it is a voice mechanism in the manual).
  • Crystal frequency on the boards (the PLL values match 29.4912 MHz).
  • HR_C5000 physical layer receive (10.7): no record interrupt in any setting tried.
  • Passive full duplex (manual 5.4.4) for a true SFR / repeater: not tried.
  • The BS outbound's key-up (9.1): timed from the slot clock, full power still lands inside the first frames in about half the key-ups, so the timeslot interrupt's place against the slot on air seems to vary between key-ups. The first burst off air can then carry a clipped CACH (harmless by the rules in 9.1).
