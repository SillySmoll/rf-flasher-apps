Adding a Radio

A new radio is a new boards/<b>/ directory, drivers for any chip the tree doesn't have yet, and a platform if its SoC is new. The core doesn't change. If it seems to need a change, the difference belongs in board_t or a hal_* interface instead, used through a field that other radios leave at its default.

Before writing code, the facts go into a hardware spec, docs/spec/hardware-<b>.md, written by the spec side under the clean-room rules. Use the hardware spec of a radio on the same platform (hardware-<id>.md, radios.md) as the model: MCU and memory map, pins, chips, keys, display, power, bootloader and image format, calibration, codec location. Start from the radio's entry in radios.md: its chip list and which RadioFoundry drivers it can reuse.

The files

A board's files list only how it differs from its platform. The platform's defaults are in platform/<p>/: platform.mk (compiler, part defines, HAL modules), config.mk (feature defaults), common.ld (the sections) and FreeRTOSConfig.h. Glue that every radio with the same part on that SoC shares is in a subdirectory the board lists in BOARD_DIRS. The board then keeps only its wiring and what its chips leave to it.

Subdirectory For
platform/stm32f4/hrc an HR_C6000 or HR_C5000: DMR glue, I2S audio, the chip's ports, the stock codec host
platform/stm32f4/spi_flash the data flash on SPI NOR, with its security registers. A flash that shares its bus with another device takes the board's bus lock (bus_take, bus_give) instead of the driver's own mutex
platform/stm32f4/fsmc_keypad a key matrix on the LCD data lines
platform/stm32f4/gps_uart a GPS module on a USART

The board's own files:

File Contents
boards/<b>/board.mk PLATFORM, APP_BASE (where the image starts: the first byte the bootloader runs), BOARD_DIRS (the board directory and each driver it uses) and any MCU_DEFS of its own. STM32: MCU (the part, which picks the CMSIS define and start-up file) and HSE_VALUE (the crystal in Hz); optional BOARD_HAL_MODULES (HAL modules beyond the platform's, such as hal_i2c)
boards/<b>/board.toml The board registry entry: identity, status, flashing, codec route, the site's data. tools/boards.py check validates it against board.mk, the linker script and board_t. Every key is in The board registry. Copy a neighbor on the same platform
boards/<b>/config.mk Feature defaults where this radio differs from platform/<p>/config.mk, with ?= (for example CONFIG_USB ?= n on a radio without USB, CONFIG_DISPLAY_INSET), each with the reason. Also BOARD_UNSUPPORTED (switches its hardware can't do, one a line with the reason: BOARD_UNSUPPORTED += AM_RX # no air band receiver), BOARD_NOT_WRITTEN (the same form: the hardware can, the driver or glue isn't written yet, with CONFIG_X ?= n; ci.sh's maximal build leaves both lists off, the rule), BOARD_REQUIRED (switches it can't build without; ci.sh skips their no- build) and MAXIMAL_VARS (make variables for that build, e.g. LTO=1)
boards/<b>/memory.ld The memory map: the codec symbols, then MEMORY (the application's FLASH region from __app_start, which the Makefile defines from APP_BASE, and the RAM regions), then INCLUDE common.ld, the platform's sections. Keep the region's end below the codec. Keep the application out of every flash sector the codec touches (not only the codec bytes), so rfoundry can update the firmware without erasing the codec. The flashing tools read the region and the codec symbols from it, and derive the erasable sectors and the protected range (release.md)
boards/<b>/freertos_board.h Optional: RTOS settings that differ from platform/<p>/FreeRTOSConfig.h (the heap size, for example), read before its defaults
boards/<b>/board.c The board_t descriptor, the key map, bands, power level names
boards/<b>/pins.h, <b>.h Pin assignments and the board's private declarations. The registry reads the pins the flash stub uses from pins.h ([flash.stub] in The board registry)
boards/<b>/*_<b>.c One file per interface: radio, DMR, audio, vocoder, display, input, flash, power, calibration, diagnostics, USB

A board family

Radios that are one board design with different data (other key positions, panel types, power tables, a battery divider) share their board code in boards/<family>/, which each radio lists in BOARD_DIRS. The family directory holds the interface files (*_<prefix>.c), the family's header and a pin map, and declares what it reads from each radio: a variant table and the key matrix, defined in the radio's own board.c. Each radio's directory keeps board.mk, config.mk, board.toml, memory.ld, a pins.h that includes the family's (and changes what differs), board.c and the files that really differ (USB identity, vocoder profiles). Differences the build can't detect, such as a higher power version with swapped pins, are a BUILD_OPTIONS choice in board.mk.

The registry and the tools treat the family directories a board's BOARD_DIRS lists as that board's sources: the board_t name, the flash map, the key enum for the web control page and the stub's pins are found there, and tools/check_generic.py lets the family's files name the radios that build them. The family's host tests are in boards/<family>/tests/. radios.md says which radios share a family.

Look at the boards on your platform for a model (tools/boards.py list --platform <p>; their chips are in radios.md).

board_t

hal/board.h defines it. The fields:

Field Fill with
name The model as shown in About and the hotspot's description
caps CAP_KEYPAD, CAP_ENCODER, CAP_GPS, CAP_DMR, CAP_VOLUME_POT, CAP_AM_RX, CAP_BCAST_FM, CAP_NO_BATTERY (a mobile on a fixed supply: no battery UI, no battery monitor; leave battery_mv and battery_pct NULL, and set hal_power_t.supply_mv if the radio measures its DC input: radio-features.md, battery)
bands, band_count Receive ranges, each with tx true where transmit is allowed
power_count, power_names, power_default Power levels as short labels, lowest first, and the default index
power_bands, power_band_count Optional: the labels per band, where a level gives a different power on each band (a top level of 45 W on one band, 50 W on the other). Same power_count on every band; a frequency in no entry uses power_names
display, input, keymap, keymap_len Display and key interfaces, and the key map (below)
radio, dmr, audio, vocoder RF chip, DMR modem (NULL on an FM-only radio), audio path, codec hosting
power, flash Battery and power switch, external flash
host_port, cps, netif The link to a computer (NULL if none), CPS and USB network hooks
system, diag_line, diag_reset Optional: chip identity and reboot modes, a diagnostics page
battery_low_mv, battery_critical_mv Battery warning levels; 0 for none
audio_tap, bcast, afsk Optional: audio path taps, a broadcast FM receiver, APRS AFSK transmit and receive audio
air, baseband Optional: the modem chip's air interface provider for the modes the core frames itself (P25, NXDN; air-interface.md 3), and the sample taps the soft modem receives through (section 6). The platform's DMR glue exports both (stm32_hrc_air and stm32_hrc_baseband, hrc_air and hrc_baseband); point the board at them. Without air, list P25, P25_TRUNK and NXDN in BOARD_NOT_WRITTEN
gps With CAP_GPS: the GPS receiver (hal_gps.h): whether the module was heard, and its power for Settings > Location > GPS. The platform drivers export one (stm32_gps, hrc_gps); the board gives them its UART and a power hook

Optional hooks may be NULL; the core checks them.

The key map

Each keymap_entry_t (hal/hal_input.h) maps one bit of the board's key scan to logical actions:

Field Meaning
bit The key's bit in hal_input_t.scan()
short_action, long_action input_action_t for a press and a hold
raw_edges Report down and up instead of press and hold (PTT, monitor)
repeat Repeat while held (Up, Down)

Map keys to the logical actions of input_action_t (ACT_SELECT, ACT_BACK, ACT_QUICK, ACT_CONTEXT, ACT_USER_1 to ACT_USER_4, ACT_MONITOR, ACT_TALK_TARGET, ...) so the five key rules of docs/ux/principles.md hold on the new radio. A radio without a keypad or with fewer keys must still reach every task; docs/spec/ui.md section 3 says how. Give some key ACT_EMERGENCY if the radio has one.

The display

The UI draws for a display class (size, color depth, insets). If the new display matches an existing class, nothing changes in the UI. A new class needs a gallery entry and a key map pair in the UI host tests (see Testing); ask before adding one, since every class multiplies the screens to review.

The frame buffer is sized to the panel in board.mk MCU_DEFS: GFX_FB_BYTES (width times height times bits per pixel, over 8), GFX_MAX_ROWS (the height) and GFX_INDEXED=1 for a 16-color panel. Without them the build reserves the 40 KB RGB565 default. boards.py check requires the buffer to hold the board's hardware.gallery class.

The drawing

The site, the web control page and the web flasher's update mode steps show the radio as a drawing, site/static/img/radios/src/<b>.svg; until it has one, a generic drawing from board.toml [frame] stands in. Its rules are in Radio images. Once the board's key enum is written, run tools/svg_keys.py tag <b>: it tags the keys it finds by their labels and prints the rest. Tag those by hand, with data-edge on side and top keys, or list them in data-undrawn. tools/svg_keys.py check <b> must pass; the site build fails CI otherwise. Run tag again after any redraw, so the tags follow the new shapes.

The keys held to enter the bootloader go in board.toml [flash.bootloader] hold by key name (["ptt", "sk1"]), beside the prose steps, and only from a documented source (the radio's hardware page). The web flasher rings them on the drawing and names them in a caption, so tag those keys in the drawing when it shows them, and add a flash.key.<name> label to site/i18n/en.json for a key no other radio holds. tools/boards.py check and site/tests/radio_images_test.py fail a key the board doesn't have, one in neither the drawing nor data-undrawn, or one without a label.

Bring-up order

  1. Platform: start-up, clocks, a time base, a UART or USB for logging. Blink something.
  2. board.c with the display and input interfaces. The UI comes up with the built-in channels.
  3. The debug link on the host port, so screenshots and key injection work from here on (Debug link). If the host port is a two-pin K-type programming jack, check whether PTT shares the line that carries the host's data: send back-to-back 0x00 bytes and watch the raw PTT pin. If it goes low, gate PTT on UART traffic (drivers/input/sharedptt, gotchas.md 16.2) before anything transmits. Then run tests/hil/test_ptt_host_traffic.py: host polling must make no PTT press. If PTT also comes through a mic jack, power on with the jack empty and watch the raw pin. If it reads low, count it only once it has read high (drivers/input/plugptt, gotchas.md 16.3).
  4. Flash, settings and calibration reads. Check the foreign-region guard on a radio that still runs the vendor firmware (settings-store.md 5).
  5. RF chip: FM receive, then FM transmit into a dummy load.
  6. DMR modem and the codec: receive, then transmit, checked on the SDR bench. Then the DMR PA key-up on every band with its own PA: tools/bench/pa_cal.py (pa-keyup.md 6).
  7. The air interface, where the modem chip has a physical layer mode (air-interface.md): point air and baseband at the platform glue's provider (above); on a platform whose receive tap is optional, set the glue's air_tap once the tap is wired. The glue reports each mode's fit with AIR_FIT_UNTESTED until the board sets the glue's air_verified, which it does only after P25 and NXDN were checked on air both ways: tests/hil/test_p25.py (test_p25_rx_from_bench, test_p25_tx_off_air) and tests/hil/test_nxdn.py (test_nxdn_rx_speech, test_nxdn_tx_off_air, both rates). Check DMR voice right after each: P25 runs in memory the DMR vocoder lends where the platform has that (hal_vocoder_t.lend). A mode the provider can't fit stays in BOARD_NOT_WRITTEN with the reason.
  8. CPS, so qdmr can program it.
  9. Flashing from where an owner starts:
    • Find every stock build an owner's radio may run before RadioFoundry: every firmware version the vendor and its rebadgers have shipped, for every model the board is sold as (also, looks). Give each a codec map and a [codec] stock entry, so the web flasher and rfoundry find the codec in whatever file or readout the owner has.
    • For each of those models, check the bootloader's USB identity, entry keys and key against [flash].
    • Walk the web flasher through each starting point:
      • the vendor's download as the owner gets it (a zip or a .bin);
      • a readout of the radio;
      • an update of a radio already running RadioFoundry.
  10. The stock codeplug, so the install keeps the owner's channels. Map the vendor layout clean room (CLEANROOM.md), from data only: compare reads of the radio's memory with dmrconf decode of the same codeplug, then confirm each field with reads taken before and after one change in the stock menu. Write it up as the radio's <id>-stock-codeplug.md and convert it in site/static/js/codeplug/. The Codeplug Editor, the Tools page and the install's channel step share the converter.
    • If a channel record holds no talkgroup or TX contact, look for a separate table indexed by channel number: a few bytes per channel, in channel order, holding the contact's number in the contact table. One supported radio keeps its TX contacts this way, and dmrconf 0.15 doesn't decode that table, so an empty TX contact in its output doesn't mean the codeplug has none. Change one channel's talkgroup on the radio and diff the reads to find it. Other vendors' radios (AnyTone's among them) likely do the same.

A bring-up page under docs/testing/ is this list made concrete for one radio.

Bring-up records

What the docs claim for a radio comes from its records, so each step above ends with a recorded run.

  1. Add boards/<b>/board.toml with [status] level = "bring-up", a summary and [docs] hardware. A bring-up page (docs/testing/<b>-bringup.md, [docs] bringup) is optional; with one, the README links the radio to it.
  2. tools/bringup.py list --radio <b> shows the checklist: every feature of tests/hil/features.toml the board builds, n/a for its BOARD_UNSUPPORTED switches and not written for its BOARD_NOT_WRITTEN ones. Each needs a reason in config.mk; a feature built but known not to work yet gets a [features] entry in board.toml (state = "unsupported"), and so does a feature without a switch that the hardware rules out (state = "n/a").
  3. As a step works, tools/bringup.py run --radio <b> --feature F -- <pytest options> runs its tests under the radio lock and writes docs/testing/results/<b>/<date>-<commit>.json. Commit the record with the change it checks; a record with failures is the to-do list (HIL bring-up mode).
  4. A check made before the radio had records (a bench log, a hand test written up in the hardware page) can go in the board's seed record, docs/testing/results/<b>/seed.json (format). A run replaces a seed row.
  5. Raise [status] level to testing, then supported, as the records cover the radio, update summary, and run tools/boards.py docs. --floor in ci.sh fails a change that makes any radio read lower than on main.

Tests and CI

  • Add host tests for each new driver against a simulated chip (tests/host/*Test.c; see the existing driver tests). Tests of the board's own code go in boards/<b>/tests/ with a host.mk (Testing).
  • HIL tests (tests/hil): the health checks' numbers go in board.toml [hil], a pass limit the radio is held to instead of a test's default in [hil.limits] (with the reason), the CPS radio types in [cps], and a check only this radio can use in boards/<b>/hil/test_*.py.
  • tools/ci.sh finds the board by its board.mk and builds its feature matrix when the compiler is installed. A board without its compiler is skipped with a notice.
  • Run tools/boards.py docs: it writes the radio into the README's radio table, the user manual's radio index (23-radios.md), the feature matrix's "Built by default" table and the Port cell of the radio's row in the radio survey. tools/ci.sh fails when that wasn't run. Remove the radio's planned row from the survey, or make it the board's row: a planned row that names a board fails tools/boards.py check. Add the radio to the user manual's introduction.
  • The web site lists the radio from board.toml: order places it, [status] level and summary give its badge and its line for visitors. A survey row that names a board is the board's row, so the site doesn't list it as planned.
  • Before it can be released: its board.toml [flash] and [codec] tables, [status] release = "stable" and the regenerated tools/rfoundry/rfoundry/registry.json (tools/boards.py json --for rfoundry --out ...). The release workflow's job for its toolchain then builds and packages it, with each build option value (release.md); CI and the nightly pick it up from the registry too (ci.md). The jobs are grouped by toolchain (platform.toml [toolchain] id), so neither a new radio nor a new platform on a known toolchain (another Arm SoC, say) needs a workflow edit. Only a new toolchain does.
