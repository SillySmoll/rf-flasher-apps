DM-32UV bring-up checklist

The DM-32UV port (make BOARD=dm32) runs on a radio. This is the order the bring-up follows, what each step proves, and what to change when it doesn't work; the open items at the end are what is still to settle. Every step names the knob in the source that the likely failure points at.

Hardware facts: docs/spec/hardware-dm32.md, docs/spec/modem-hrc7000.md, docs/spec/codec-dm32.md.

The feature checklist, with every feature's required HIL tests and the last recorded result, is tools/bringup.py list --radio dm32. tools/bringup.py run --radio dm32 records a run (tests/hil/README.md). This page keeps the hardware steps and what to change when one fails.

0. Before anything

  1. Back up both flashes with the stock tools (hardware-dm32.md 13.4): the 1 MB program flash and the 16 MB data flash. The port never writes the data flash below 0x700000 (the stock codeplug and the factory calibration live there), and it never touches the bootloader, but a backup is the only way back from a mistake.

  2. Check that update mode works with the stock firmware: hold PTT + SK1 while turning the radio on; the green LED lights (13.2). This is the recovery path for every step below: if an image doesn't boot, take the battery off, enter update mode and load the stock file again.

  3. Build and pack:

    make BOARD=dm32                                   # csky-elf GCC: tools/build-csky-toolchain.sh
tools/serial_loader.py --model dm32 build/dm32/rfoundry_dm32.bin --wrap build/dm32/rfoundry_dm32_BFUV32.bin

    For DMR voice, merge your own stock codec first (never commit or share the result):

    tools/hrc7000_codec.py --stock DM32.01.01.049.bin    # writes build/dm32/rfoundry_dm32_codec.bin
tools/serial_loader.py --model dm32 build/dm32/rfoundry_dm32_codec.bin --wrap build/dm32/rfoundry_dm32_codec_BFUV32.bin

  4. Load the image in update mode: tools/serial_loader.py --model dm32 build/dm32/rfoundry_dm32_codec.bin (a raw image, or the _BFUV32.bin file without --model, over the programming cable; --stock DM32.01.01.049.bin goes back), or the Baofeng updater with the _BFUV32.bin file. To keep the stock codeplug and get it onto RadioFoundry, run tools/dm32_migrate.py all --image build/dm32/rfoundry_dm32_codec.bin instead: it backs the codeplug up with qdmr, flashes, and writes it back once RadioFoundry runs (dm32-migration.md, users: the manual). Both tools are untested on a radio: run them with --dry-run first, and the codeplug part only after step 2 works.

Run the first boots with the antenna on and no PTT. Transmit only into a dummy load, from step 7 on.

1. It boots

Look for Proves If not
Radio stays on after you let go of the knob (power latch) crt0 ran, clocks, board_early_init (latch first) Nothing ran at all: check the image starts with psrclr ie at 0x0300C000 (`csky-elf-objdump -d build/dm32/rfoundry_dm32.elf
Backlight on, then the Home screen RTOS tick (Timer 1), LCD controller, ST7789 init Backlight but no picture: display_dm32.c (LCDC_CFG 0x303, IO_DIPLEX2 hand-over). Picture upside down or mirrored: MADCTL in display_dm32.c (0xC0 now; try 0x00, 0x40, 0x80)
Colors right (black background, not white) inversion on st7789_t.invert
Picture fills the panel, no tearing seams 2x scaling, window st7789_write_rows
Hangs before the screen interrupts or the scheduler platform/hrc7000/irq.c: the PIC may deliver all sources on autovector 10 instead of vectors 32+n (open item); the irq entry then reads the wrong source. freertos/port.c / portasm.S for a hang after the first task switch

2. The debug link on the programming cable

The DM-32 has no USB: the host link (debug link, CPS, MMDVM hotspot) runs on UART0, 115200 8N1, through the programming cable (CH340 or FTDI).

tools/rfoundry_debug.py --port /dev/cu.usbserial-XXXX version
tools/rfoundry_debug.py --port /dev/cu.usbserial-XXXX diag
tools/rfoundry_debug.py --port /dev/cu.usbserial-XXXX screenshot -o /tmp/dm32.png
python3 -m pytest tests/hil -v -rs --radio-port /dev/cu.usbserial-XXXX -k "health or boot or ui"
Look for Proves If not
board=DM-32UV, display=240x320x4, features with HOSTLINK,DEBUGLINK and no USB UART RX interrupt, ring buffer, TX Garbage: baud divisor (uart.c, 46 for 115200 at APB 84 MHz; 45 is the old port's) or APB not 84 MHz (clock.c skipped the PLL because the bootloader left it on: check CLK_MGR_CTRL)
diag lines ticking (uo 0 = no UART overruns) the debug link task

3. Keys, encoder, PTT, LEDs, power

Check If not
Every keypad key moves the UI as its label says (6.1 table); rfoundry_debug.py view --section input shows the physical key bits Rows / columns or the matrix map in input_dm32.c; phantom keys: raise the 5 us settle delay
SK1 (below PTT) = monitor, SK2 = talk target; holding SK1 doesn't kill the column 3 keys' neighbors direct[] in input_dm32.c
Encoder: one step per detent, right direction keymatrix_encoder_step sign; one count per edge of B (6.3): if a detent gives two, count one edge only (hrc_pin_irq in input_dm32.c)
PTT shows as key bit 20 GPIO 0x2B
Red LED on transmit, green on receive PIN_LED_RED / PIN_LED_GREEN in pins.h (settled on the radio: 0x20 green, 0x21 red)
Turning the knob off saves and powers down GPIO 0x10 sense in power_dm32.c
bat line: raw about 600-690 and 7000-8400 mV on a charged pack ADC channel C set-up in power_dm32.c; the scale raw / 8.2 = V x 10
Backlight dimming levels look even set_backlight assumes FP counts against PER (duty = percent x 2); if half brightness is already full, use the percentage

4. Data flash and calibration

diag: flash C84018 cal factory (or 852018 on Puya-flash radios), txc not 128, pa values not 1408.

If Then
flash 000000 or FFFFFF SPI0 set-up in flash_dm32.c (BAUDR 4 = 21 MHz; try 8), CS pin 0x12
cal none The factory page (block ID 2 in the last byte of a 4 KB page in 0x1000..0xC8000) wasn't found: dump the codeplug area through the stock CPS and compare (drivers/cal/baofeng/baofeng_cal.c)

5. FM receive

Tune the FM VFO to a known signal (a NOAA weather station, a local repeater output) and to a quiet channel.

Check If not
Audio from the speaker with the squelch open Works (checked on the radio). FM audio comes from the FD6818's output: GPIO 0x2F high, 0x35 high (radio_dm32.c speaker_source()), FD6818 0x47 = 0x0140. The C7000 fm_play bit stays off
rssi / nz move with the signal; the squelch closes on a quiet channel FD6818 reads (fd6818_read timing). The squelch uses the FD6818 noise byte (0x65): if its scale isn't dB-like, map it in radio_dm32.c status()
RSSI in dBm roughly right against a signal generator the offset in status() (raw - 135 now, a guess)
CTCSS / DCS RX opens only on the right tone With GPIO 0x2F high the C7000 gets no audio, so its sub-audio decoder can't work in FM receive. The FD6818's own detector does the job (0x07 / 0x08 / 0x51 / 0x52, result in 0x0C)
Both bands: 145 MHz and 435 MHz LNA selects 0x22 / 0x24, band words

6. Hotspot / CPS on the cable (optional)

MMDVMHost or a CPS on the same serial port: the host link switches by what it receives (core/hostlink).

7. FM transmit (dummy load, power meter, SDR or service monitor)

Check If not
Carrier on frequency within a few hundred Hz TX center / SIG_CENTER (factory TX center byte)
Power levels 0-8 rise monotonically; level 8 near 5 W VHF / 4 W UHF bf_cal_power_level and the 11.3 fractions; DAC B must be powered (PD_CTRL bit 1 clear)
Deviation about 2.5 kHz (12.5 kHz channel) with normal speech; no distortion hrc7000_fm_tx deviation, mic gain (GCR_ADCL 11 dB)
CTCSS on the air at the right frequency C7000 TX sub-audio; or switch to the FD6818's (fd6818_set_tx_ctcss)
PA off and receiver back on PTT release tx_off()

8. DMR receive

Select a DMR channel with traffic (or let the SDR bench send a call), then diag.

DMR receive needs GPIO 0x2F low: that feeds the FD6818's audio into the C7000's ADC. With it high the modem sees no signal and tk stays at 0. The C7000's PHASE_OUT register (0x128) is a quick check that audio arrives (modem-hrc7000.md). Checked on the radio with an SDR bench call: sync ticks, slot interrupts, voice frames, headers, late entry and the test channel's color code all counted.

Diag line Healthy If not
DMR on+cb tk N ticks climb by about 33 per second once a signal gives the chip timing No ticks: modem interrupts 30 / 31 not arriving (PIC vectors, irq.c), or the modem not in DMR (hrc7000_dmr_enter)
ts a/b si c RX timeslot (b) and system (c) interrupts counting
V H T I voice, headers, terminators counted in a call Bursts deframed but dropped: color code (cc line) or CRC flags
cc 1 ts 1 <RX_TYPE_INFO> the call's color code and slot
Voice heard from both slots of a repeater, and a simplex call HRC7000_RX_NEXT_SLOT_XOR, 0 on the DM-32 (the driver's default since 2026-10-22; it was 1, set to 0 in boards/dm32/config.mk before). With 1 every call decodes to silence: voice.rx_peak about 6, every frame exactly 3 bit errors, all other counters clean (#73)
codec 049 (or 046) and clean audio without a merged codec DMR is silent; garbled audio: PCM byte order (platform/hrc7000/audio_pcm.c), the codec call parameters (platform/hrc7000/vocoder.c: flags 0x1840 / 0x800, E[0x1736] / D[0x1166])

9. DMR transmit (dummy load and an SDR or a second DMR radio)

Check If not
A second radio decodes our call (ID, talkgroup, voice) send types (LCSS on B-E per the user guide; F is 0x58 by the formula, the user guide's example says 0x50: try e->lcss = false if the embedded LC isn't decoded)
Bursts stay inside their 30 ms slot at every power level (SDR waterfall or tools/bench) the DMR PA delay (DMR_PA_DELAY_US, 28 ms, Timer 3)
pa on the tx line about 30 ms; rf counts one per burst PA off rule (20 ms after the RF TX interrupt)
Through a repeater: the repeater keys up and relays both directions repeater timing after TX (tx_finish)
The mic on DMR transmit, no person: pytest tests/hil -k mic_uart_inject --allow-rf --mic-inject on the host the cable is plugged into (its device path, not a network bridge). The tone bursts sent on the cable's line show at the vocoder: voice.tx_mic_spread_db 12 or more, tx_mic_level_db 9 dB over a quiet over (measured 2026-10-22: quiet 3 dB, spread 0; injected 21 dB, spread 18) both overs at the ADC's floor: the mic doesn't reach the codec ADC on DMR

10. Long run

An hour on a busy DMR channel and an hour of FM scanning: uo, ov (event overflow), aud ov / un stay near 0, no stalls (st), no resets.

11. Air band AM and broadcast FM

The design is airband-and-broadcast.md; the open questions are hardware-dm32.md 8.7. tests/hil/test_listen_bands.py checks the view keys without keying.

Check Settles
The stock radio (or a scanner) on the local ATIS; RadioFoundry on the same frequency: AM audio, am=1 in the view, read back FD6818 0x47 / 0x30 which chip demodulates AM, the 0x47 AF type (A1)
No audio: FD6818 0x47 (0x0140 gives FM audio), then the speaker source switch (GPIO 0x2F high) AM audio route (A2)
A strong and a weak station; a generator at -100 dBm with rssi on the link AM AGC and filter (A3), the AM squelch offset (A4)
PTT on an air channel and on a split channel with TX in 108-137 MHz deny screen, red LED off, nothing on the SDR
The RDA5807M chip ID (0x58xx at 0x11) on PTA25 / PTA26 it is there, the SDA pull-up (B1, B3)
A strong local station with each reference clock setting; with and without the headset reference clock (B2), audio path (B4), antenna (B5)
The VFO on 100.1 MHz, then a local station: bcast=1, bcast_fault=0, the signal meter moves; the knob steps 200 kHz on the odd tenths the tuner glue, the squelch threshold

12. GPS

No fix needed: the module talks from about 1 s after power-up, indoors too.

Check Expected If not
The diagnostics line gps ... (Settings > Diagnostics, or the debug link's diag lines) 10 s after start-up gps yes, the good count rising by a few a second, bad near 0, b rising by about 300-600 a second gps no with b0: no bytes on UART1: PTA9's mux (IO_DIPLEX0 bit 9 = 0), the power pin (0x2C low), the module. gps no with bytes but no good sentences: the baud rate (try 115200; stock may have reconfigured the module)
Outdoors, a few minutes Info > Position shows a fix and the satellite count the NMEA talker or sentence set (position_nmea)
Outdoors: restart, or GPS off then on in Settings > Location a fix (pos.gps_fix=1 in the debug link's view) in under 1 minute (17 to 51 s measured, one run each; 45 s after 5 minutes powered off) a view of the sky; if the satellite count stays 0 with NMEA clean, the antenna
Indoors a fix is possible but not reliable: one run had a fix within about 1 minute, another none for more than 5 minutes move outdoors before suspecting the firmware
Bad count rising steadily near 0 UART errors: the divisor (547 at 84 MHz APB) or noise on the line

13. APRS

The HR_C7000 copies its FM receive audio to the CPU (modem-hrc7000.md 8.5). APRS listens on the APRS frequency (144.390 in North America) with the receive setting on.

Check Expected If not
The debug link's aprs view on 144.390 aprs.rx_listening=1, rx_bits rising by about 1200 a second on noise, rx_peak above 0 rx_listening=0: the receive setting (rfoundry_debug.py aprs set rx 1) or the frequency. Bits not rising: SYS_INTERP_MASK bit 14 (0x1100039C) clear, or GPIO 0x2F high
A packet on the air rx_hdlc_frames and stations go up rx_fcs_errors rising with packets present: the half read (FM_ADDR_SW), the level (noise reaches full scale), audio under the tones (below)
An FM signal on 144.390 with the squelch open heard on the speaker, through the C7000's FM playback AUDIO_CONTROL bit 6, the codec line out
A packet sent at level 50, recorded by the SDR bench (aprs.md 13) decodes with a valid FCS, about 3 kHz peak deviation, twist within 2 dB no tones: AUDIO_CONTROL bit 7 during the transmission, Timer 4 (vector 36) not firing. Deviation: amp_per_level in radio_dm32.c

Open items to settle on the bench

  • PIC: vectored (32 + source) works: the DMR slot, RF TX and PCM interrupts all arrive (settled on the radio).
  • L2_STATUS slot polarity (HRC7000_RX_NEXT_SLOT_XOR): 0, settled for simplex on the radio (2026-10-19: AT-D878UV speech, 234 frames with 23 bit errors, voice.rx_peak 4288, clean audio). Both slots through a duplex hotspot are still to check.
  • LED colors: 0x20 green, 0x21 red (settled on the radio). Panel orientation, backlight PWM scale.
  • Sub-audio: the C7000 makes the TX tones, the FD6818 detects the RX tones (settled on the radio and the SDR bench).
  • Codec 049: DMR voice encodes and decodes (the SDR bench modem decodes our AMBE with few FEC corrections); 046 untried.
  • UART divisor 46 (0.9 % slow) or 45 (1.3 % fast).
  • RSSI dBm offset and the noise scale for the squelch.
  • GPS: NMEA arrives on UART1 at 9600 (section 12): gps yes, 291 good sentences and 0 bad 26 s after start-up (on the radio, indoors, no fix). Later (2026-11-18, a local build): outdoors, a 3D fix with 6 to 13 satellites, and NMEA stayed clean (about 200,000 sentences, 1 bad). Time to the first fix outdoors, one run each: 17 s after a software restart, 51 s after Settings > Location > GPS off for 30 s and on, 45 s after the radio first answered following 5 minutes powered off. Indoors the result varied: a fix within about 1 minute of a restart in one run, and no fix for more than 5 minutes after the HIL test_gps_power_switch cycled the module in another; the fix came back once the radio was outdoors. HIL test_gps_nmea, test_position_view, test_position_fixed_settings and test_gps_power_switch pass; test_gps_fix (needs a person) and the restart test were not run.
  • APRS receive (section 13): decodes off air, 12 of 12 frames from another radio at lowest power a few feet away (2026-10-16). The receive audio had peaks about 19000 of 32767 and dropped no halves. Its space tone was 6-8 dB under the mark tone (the FD6818's de-emphasis; the sender was flat within 1.3 dB on the SDR bench), and it carried 320-400 Hz 1-10 dB under the tones. With one demodulator path that cost half the frames; the high passed second path (aprs.md 5.3) fixed it. Still open: where the 320-400 Hz comes from (the FD6818's receive audio filters, REG 0x9B, sub-audio residue, the sender), and whether a hardware setting removes it. REG 0x9B (the receive de-emphasis and filter bypasses) is on the FD6818's page 1: writing 0x7F = 1 over the 3-wire bus didn't select it (page 1 reads matched page 0), so the page switch is still to find. Weak packets below the squelch are untested.
  • FM transmit voice deviation (section 7): the TX limiter (hrc7000_t.fm_tx_limit) is 5 at 12.5 kHz and 0x0F at 25 kHz, the DM-1801 Pro's values. At 12.5 kHz a loud whistle and voice peaked at 1.3 kHz (99.9 %, rms 167 Hz) on the SDR bench (2026-10-16), under the 2.5 kHz target. Still to try: a higher limiter, or more mic gain (GCR_ADCL 11 dB), and a measurement at 25 kHz. The K-plug cable cuts the mic, so the owner keys by hand with the cable out.
  • APRS transmit (section 13): decodes off air at 3.1 kHz peak (settled on the SDR bench). test_aprs.py on air is still to run.
  • Host link lost with the UI running (2026-10-16, after a day of transmit tests): the debug link stopped answering, and the diagnostics page showed ur 0 ut 0 (not one byte received) with the host link task alive (hb climbing) and the receive interrupt enabled (ie 05). The boot stub still worked on the same cable, and an image that had answered that morning failed the same way, so the build wasn't the cause. Power-key cycles didn't help. A battery pull left the radio dead (flat battery); after charging and a cold start the link answered. Cause unknown: the battery or the full power cut. If it happens again, read bat on the diagnostics page first.
  • Boot stub, stubtool.py --attach --boot reset (warm reset into the new image): RadioFoundry came up but its host link never answered, every time on the DM-32 (2026-10-16; 3 of 4 times on the DM-1801 Pro). A power cycle after the write works. Until the reset path is fixed, power-cycle instead.
  • Boot stub LED: after a write finished and was verified by CRC, with no tool on the port, the LED kept blinking fast (the "data moving, don't power off" pattern) for minutes (2026-10-16). The pattern should follow the stub's state.
  • DMR receive degraded after hours of uptime (2026-10-16): one, later two, of the three AMBE frames in every voice burst failed C0 at -68 dBm, and the zone scan, VFO scan and battery-save wake never saw the bench carrier. The errors were the same with the receiver retuned -1.5 to +0.6 kHz, so not RF; the bench's bursts decode clean offline. A power cycle cleared it, and the full radio-only HIL file set plus an SFR run didn't bring it back. If it returns, read voice.rx_bad_at (which frame of the burst fails) and the FD6818 and HR_C7000 registers before power-cycling.
