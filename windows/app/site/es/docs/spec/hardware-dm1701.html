Baofeng DM-1701 hardware (and its STM32 siblings)

The Baofeng DM-1701, the Retevis RT84 and the TYT MD-UV380 / MD-UV390 (5 W and "Plus 10 W") are one board family: an STM32F405VGT6 (LQFP100) MCU, an HR_C6000 DMR baseband/codec chip, one AT1846S RF transceiver covering both VHF and UHF, a 160 x 128 color LCD on an 8-bit 8080-style bus, a 16 MB SPI NOR flash, a 3-row keypad matrix that shares its column lines with the LCD data bus, a rotary channel encoder, a volume potentiometer with a built-in power switch, and USB full speed device on the MCU's OTG_FS core. This file records what the hardware needs. The DM-1701 is the primary target; differences for the siblings are collected in section 17.

1.4 Internal flash layout

STM32F405, 1 MB: sectors 0-3 are 16 KB, sector 4 is 64 KB, sectors 5-11 are 128 KB. The V02.06 CSV codec runs in place from sectors 10 and 11, where the merge puts it (codec-placement.md, "STM32 radios"; codec-dm1701.md): tables at their original address 0x080D19F0..0x080E3A72, code moved from its original address 0x08074714 to 0x080E3A74..0x080F3C90, and the descriptor at 0x080FFF80. The codec from a V02.01, V02.02 or V02.03 CSV file sits 0x40 lower in the same sectors: tables 0x080D19B0..0x080E3A32, code 0x080E3A34..0x080F3C50. The codec from a noCSV file sits higher, still in sectors 10 and 11: V02.06 noCSV tables 0x080D4794..0x080E6826, code 0x080E6828..0x080F6A28; V02.03 noCSV 0x40 lower.

Sector Address Size Holds
0-2 0x08000000..0x0800BFFF 48 KB bootloader: never erased or written
3 0x0800C000..0x0800FFFF 16 KB RadioFoundry (vector table first)
4 0x08010000..0x0801FFFF 64 KB RadioFoundry
5-9 0x08020000..0x080BFFFF 5 x 128 KB RadioFoundry
10 0x080C0000..0x080DFFFF 128 KB codec tables (from 0x080D19F0; V02.01 to V02.03: 0x080D19B0; noCSV: 0x080D4794, 0x080D4754)
11 0x080E0000..0x080FFFFF 128 KB codec tables (to 0x080E3A71), codec code (0x080E3A74..0x080F3C8F), descriptor (0x080FFF80..0x080FFFFF); V02.01 to V02.03: tables to 0x080E3A31, code 0x080E3A34..0x080F3C4F; V02.06 noCSV: tables to 0x080E6825, code 0x080E6828..0x080F6A27 (V02.03 noCSV 0x40 lower)

A flash sector can only be erased whole, so boards/dm1701/memory.ld gives the application sectors 3-9 (0x0800C000..0x080BFFFF, 720 KB in one piece) and asserts that everything it loads into flash ends before 0x080C0000. The image is one .bin from 0x0800C000, and an update erases and writes only the sectors it covers. The bytes around the codec in sectors 10 and 11 are 0xFF after a merge and are never executed. The DM-1701's settings and codeplug live in the external SPI flash, so nothing else writes internal flash.

The manufacturer's firmware, and RadioFoundry builds from before the codec moved, keep the codec code in sectors 7 and 8, which the application now covers. A release or manifest with two ranges (the application and a sector 9 data part) is from before the move and is refused. Moving a radio to this layout writes the codec once, from the manufacturer's firmware file or from a copy the tools read from the radio earlier (release.md, "Codec handling").

rfoundry's keep and merge modes follow from this map (release.md, "Codec handling").

The codec's entry points, as offsets from the code start: encode +0x130, encode FEC +0x4E8, decode +0x5D8. Call with the Thumb bit set when calling through a pointer.

Codec calling convention (the interface to the third-party blob; unverified beyond "it works"):

Call r0 r1 r2 r3 stack words [0], [1], [2], [3]
decode (called twice per 20 ms frame) PCM out (80 samples per call) 80 49 input bits, one bit per 16-bit word 0 0, half index (0 then 1), pointer to decoder state (0x7EC bytes)
encode (called twice per 20 ms frame) 72-word bit buffer out 0 PCM in (80 samples per call) 80 flags (0x1840 first half, 0x0800 second half), half index (0/1), 0x2000, pointer to encoder state (0x2000 bytes)
encode FEC bit buffer same bit buffer 0 pointer to FEC state (0x100 bytes) none

The 72 encoded bits come back one bit per 16-bit word (LSB) and are packed MSB first into 9 bytes. On decode, the 9-byte (72-bit) AMBE+2 frame must first be de-interleaved and FEC-decoded to 49 bits by the caller (Golay(24,12) on C0, Golay(23,12) on C1 after removing the pseudo-random whitening seeded from C0's 12 data bits with x' = 173x + 13849 mod 65536, the standard AMBE+2 3600x2450 FEC; see the codec spec). The state buffers must be initialized by the codec's own init calls (codec-dm1701.md C). Gotcha: a call site that builds the stack arguments must not be optimized in a way that moves the stack pointer (with -Os around the call, DMR TX crashed); calling through a small assembly shim with an explicit frame avoids this.

1.5 RAM

Region Address Size Notes
SRAM1+SRAM2 0x20000000 128 KB general data, DMA buffers. Initial stack pointer must be below the top of RAM: the bootloader rejects SP = 0x20020000, so use 0x2001FFFC (4-byte aligned)
CCM 0x10000000 64 KB CPU (D-bus) only: not reachable by any DMA controller. Not zeroed and not initialized by the startup code: anything placed there starts with garbage and initializers are ignored unless the startup code copies them
Backup SRAM 0x40024000 4 KB battery backed only if VBAT is supplied (unverified on this board); unused

Main RAM and CCM are both nearly full in a full build (frame buffers, flash sector buffer, calibration copy, USB buffers, data-service buffers); plan buffers explicitly.

4.2 Configuration port timing

Mode 3 equivalent: clock idles high; for each bit MOSI is set, CLK driven low, MISO sampled, CLK driven high (the chip latches on the rising edge). No added delays were needed at 72 MHz with GPIO writes (about 1-2 MHz effective). CS low for the whole transaction.

Framing (same as the GD-77 family, see modem-hrc6000.md 1.1):

Transaction Bytes sent
write one register page, register, value
read one register page OR 0x80, register, dummy; data comes back in the third byte
write extended (11-bit) address page OR 0x40, address bits 7:0, address bits 10:8, value
block write page, start register, n data bytes (up to about 130 used)
block read page OR 0x80, start register, n dummy bytes (up to 0x60 used)

The port is shared by task code and ISRs: transactions must be atomic with respect to the HR_C6000 ISRs (mask or lock around each transaction).

4.3 Voice port

SPI2 master, 8 bit, MSB first, CPOL = 1, CPHA = first edge (mode 2), prescaler 8 -> 4.5 MHz, software CS on PB12. Framing: write = page 0x03, register 0x00, then 27 AMBE bytes; read = 0x83, 0x00, then 27 bytes clocked in (the data follows the two header bytes). Up to 32 data bytes per transfer.

4.5 Power and start-up

  1. PWD low (PE6), wait at least 10 ms.
  2. Program the PLL while running from XTALI, switch to the PLL. The datasheet asks for more than 500 us between writing 0x0B/0x0C and switching 0x0A back to the PLL; a driver should wait.
  3. Continue with the init sequence in modem-hrc6000.md section 3.

Power down: PWD high. The microphone power (PA13) is usually switched with the receiver; some external speaker-mics generate false PTT events when their bias is removed, so keep PA13 high during receive power saving.

5. AT1846S RF transceiver

5.1 Bus and part

Item Value

5.6 Frequency setting

The synthesizer word is in units of 1/16 kHz (62.5 Hz): word = f(Hz) / 62.5 = f(MHz) x 16000. Registers: 0x29 holds word bits 29:16 (in bits 13:0), 0x2A holds bits 15:0. Example from the datasheet: 409.75 MHz -> 0x640960 -> 0x29 = 0x0064, 0x2A = 0x0960.

Write sequence (RX or TX frequency):

Step Action
1 0x30 = idle value (5.3)
2 0x05 = 0x8763 ("normal" frequency mode)
3 0x29 = high word
4 0x2A = low word
5 0x49 = 0x0C15 (squelch open/shut thresholds; see 5.9)
6 0x30 = RX on value
7 set the PA DAC: the TX drive value when this was the TX frequency, 0 when RX

TX frequency offset (empirical): with the normal TX sequence (RX frequency written, then TX frequency written with RX on, then TX on) the carrier is about 3 kHz low; RadioFoundry adds +3.00 kHz (12.5 kHz) or +6.15 kHz (25 kHz FM) to the TX word. With a different sequence (frequency written with the receiver off, then straight to TX) there is no offset and adding it puts the carrier +2.93 kHz high (measured on air). The cause is unknown; a new driver should measure the actual offset of its own sequence.

Band selection for the receive front end: VHF band -> PA5 high, PA2 low; UHF -> PA2 high, PA5 low (5.8, section 6).

DCS word: the 9-bit code (octal digits as 3-bit groups, e.g. 023 -> 0x013), with bit 11 set (the fixed "100" marker: word bits 11:9 = 100), and the 11 Golay(23,12) parity bits of the 12-bit value (marker + code) in bits 22:12. Generator polynomial x^11 + x^10 + x^6 + x^5 + x^4 + x^2 + 1 (0xC75). Compute it; no table is needed.

The chip sends the word MSB first (bit 22 first) and compares received bits in the same order, while DCS sends code bit 0 first. So 0x4B/0x4C take the word bit-reversed: 023 -> 0x763813 -> reversed 0x640E37 -> 0x4B = 0x0064, 0x4C = 0x0E37. The unreversed word (0x0076 / 0x3813, as the AT1846S programming guide shows) went out as D023 read backwards on the SDR bench, and the radio accepted no other radio's DCS; with the reversed word it sends and receives D023N.

DCS turn-off tail (radio-features.md 3.3a): 0x4E bits 10:9 from 10 (DCS) to 11 (CTCSS) for the tail. 0x4A already holds 13440, so the chip sends 134.4 Hz as a CTCSS tone; back to 10 (and the polarity in bits 8:6, kept) on PTT again. The chip's own tail elimination (0x30 bit 11, 0x4E bits 15:14 phase shift) is a CTCSS feature and stays off. Not yet measured on the SDR bench.

5.10 APRS AFSK transmit

RadioFoundry's hal_afsk_t (boards/dm1701/afsk_dm1701.c, aprs.md 5) uses the AT1846S tone generator as the voice source, as for the roger beep. TIM6 (APB1 timer clock 72 MHz, prescaler 2, ARR = clk / 2 / 1200 - 1, interrupt priority 5, no RTOS calls) interrupts at every symbol boundary. It writes the next tone to register 0x35 when the tone changes: one I2C write of about 0.1 ms in an 833 us symbol. The radio core keeps the I2C bus free meanwhile. At the end it force-writes 0x35, because the interrupt bypassed the driver's cache. The level (0-100, 50 default) scales the tone deviation register 0x59 around the driver's value.

The tone generator is the voice source only with reg 0x3A bits 14:12 (voice_sel) = 001 and 0x7A bit 14 (single tone) set. An earlier build wrote bits 6:4 and keyed a silent carrier (gotchas.md 3.10, fixed in 694249b). tests/hil/test_aprs.py measured the result on air (aprs.md 13).

5.11 Receiver sleep

RadioFoundry's rx_sleep(true) (receiver battery save, radio-features.md 5.4) puts the AT1846S in idle and switches the receive supply off. rx_sleep(false) retunes. It does the same on a DMR channel (rx_sleep_dmr, a trunked system's power save): the HR_C6000 keeps running and the core restarts its receive on waking. On air at 1:4 the receiver is off 55-60% of the time, the radio stays camped, and traffic for it arrives within one cycle.

5.13 DMR receive offset

In DMR the AT1846S receives UVF_DMR_RX_OFFSET_UHF_HZ / UVF_DMR_RX_OFFSET_VHF_HZ below the channel (62.5 Hz steps). FM receive is tuned to the channel. UHF: 0. VHF: 1250 Hz.

  • Enter TX: both RX supplies off; configure the HR_C6000 for FM TX or DMR; AT1846S reg 0x30 to the TX value; then PA enable 1 high, PA band select, then PA enable 2 high. The DAC drive is set when the TX frequency is written.

  • Enter RX: PA enable 1 and 2 low first; RX supply for the band; AT1846S reg 0x30 to the RX value; HR_C6000 to FM RX or DMR.

  • Burst-by-burst DMR TX (the PA follows the bursts), keyed 1 ms after the RF TX interrupt (it comes about 1.28 ms before the slot boundary; keyed at once, the PA cut the end of the inbound burst an SFR receives in the other slot). Two sequences:

    • Through idle, the normal one: reg 0x30 receiver off, the TX frequency, reg 0x30 DMR TX, both RX supplies off, then the PA. Back to RX, the PA enables low, reg 0x30 receiver off, the RX frequency if it differs, the RX supply for the band, reg 0x30 RX on. Going straight back to RX after a burst entered from idle leaves the receiver about 3 kHz off.
    • Direct, only while an SFR repeats (a channel's or the VFO's role, or the hotspot's SFR mode; the board asks at each burst: hal_radio_t.dmr_direct_query), on a simplex UHF channel whose receive frequency the synthesizer already holds: reg 0x30 straight from RX to DMR TX, HR_C6000 4:0x04 (MOD1 offset) = calibrated value + 42, plus the DMR receive offset in MOD1 steps (5.13), both RX supplies off, then the PA. Back to RX: the PA enables low, 4:0x04 = calibrated value, the RX supply, reg 0x30 RX on. RX straight to TX puts the carrier about 3.07 kHz low and a frequency write can't correct it (the AT1846S applies one only coming out of idle); 42 steps of about 75 Hz put it back on the board measured near 461 MHz (+16..+60 Hz). On two other DM-1701s at 433.45 MHz the same correction left the DMR carrier 178 Hz and 449-554 Hz below the FM carrier, enough for an MMDVM hotspot to reject the call, and through idle they measured +36 and +41 Hz (on an SDR). That is why direct keying is kept to the SFR: there the idle step, which makes the synthesizer settle again each slot, lost the first and last frames of the inbound bursts, about 190 bit errors and 5-10 lost frames per 72 repeated frames against about 60 and none direct (on an SDR). A per-radio correction would make it right everywhere.

    The receiver must work between bursts (an SFR's inbound slot, sfr.md 3). Dropping the PA earlier than the next timeslot interrupt (28.5-30 ms after the RF TX interrupt) did not reduce the inbound errors. The "transmitting" state of the radio must therefore be taken from the HR_C6000 slot state, not from the PA pins: the last burst of a call (the terminator) is still in flight after the PA logic has gone back to RX once.

    Since the receiver is back on the RX frequency after every burst, a voice over through a repeater listens to its outbound between our bursts on a split channel too (the glue's listen_split, dmr-modem.md 2.8): on a trunked site's split channel the radio hears a reverse channel cease while it talks (test_t3_cease).

  • Power-down: PA enables low, both RX supplies low, mic power optionally low, HR_C6000 PWD high, AT1846S reg 0x30 = receiver off value.

Powering both receivers together and powering only the band in use both work; RadioFoundry powers only the band in use.

9.4 Backlight

10.3 Rotary channel encoder

Quadrature, A on PE14, B on PB11 (both pull-up), with detents. The driver interrupts on both edges of B only and counts one step per B edge (-1 if A equals B after the edge, else +1). One B edge per detent means two quadrature steps per detent, resting where A equals B (00 and 11). Measured on the bench (2026-10-10, a76da0d): 10 slow and 10 fast detents each gave exactly 10 detents and 20 transitions, 11 counterclockwise gave -11 / 22, a wobble without a detent gave 0 detents (14 transitions, 12 reversals), never an illegal state.

RadioFoundry interrupts on both edges of both lines (EXTI14 for A, EXTI11 for B, one handler) and feeds every sample of the two levels to the table decoder in drivers/input/quadrature: each sample against the previous one is no change, one step either way, or both lines changed (a missed sample, ignored). A detent counts only when the lines reach a rest state with two steps the same way since the last one. The interrupt clears its pending flags before it reads the pins, so an edge during the read interrupts again.

Why counting B edges went wrong (seen as missed steps and steps backward, 2026-10-10):

  • Going one way, B is the first line to change when the knob leaves a detent. A light touch or a knob that settles back counts a step and then a step back: the focus jumps a row and returns.
  • Contact bounce on B gives several edges. EXTI has one pending flag per line, so edges close together (or while the interrupt is masked or preempted) merge, and the handler reads the level after all of them: a rise-fall-rise reads "high" twice and counts two steps for one, never in step with the detent.
  • Bounce on A was ignored, but A's level was sampled at B edges only, so a sample taken while A was still settling (a fast turn) gives the wrong direction.

The decoder makes all three harmless: bounce is a step and the same step back (net zero), merged edges are a repeated level (no change), and only whole detents count. Clockwise is positive (forward): the next channel on Home, focus down in lists (confirmed on the radio).

10.4 Power switch

The volume knob's switch interrupts the battery sense line. The MCU holds its own supply with the latch (PA7 high). When the battery reading drops below 5.5 V (11.1) the switch is treated as off: the firmware finishes its shutdown and drives PA7 low, which removes power. This also means a deeply discharged battery looks like "switch off" (unverified whether there is a second sense path).

12.4 Reference oscillator offset

offset = (VHF or UHF tune byte) - 128, signed, for the band in use (TX band while transmitting, RX band otherwise). Written to HR_C6000 4:0x47 = offset, 4:0x48 = 0x03 if offset < 0 else 0x00, 4:0x04 = offset. In FM TX, 4:0x48 = 0x00 and 4:0x04 = offset.

The HR_C6000 manual (4.7.2, two-point modulation): MOD1 drives the reference oscillator's control pin and MOD2 the VCO. 4:0x04 is the MOD1 offset in transmit, about +-422 mV in 3.3 mV steps. 4:0x47 and 4:0x48 bits 1:0 are a 10-bit level MOD1 holds in receive, 0-3.3 V (the DAC kept on: 4:0x25 bit 5 = 1, bit 3 = 0). The radio's values are the offset sign-extended to 10 bits, so receive and transmit sit at the same level.

The user's reference trim (radio-features.md 6.1) adds to this offset at every tune: uvf_ref_trimmed turns ppb into steps at 160 ppb a step and clamps to -128..127. The scale comes from the direct keying measurement in section 6 (41 and 43 steps put the carrier 149 Hz apart near 461 MHz, about 74 Hz a step). A step is 0.16 ppm, so the 0.1 ppm trim steps round to it. With a blank band (12.1) the offset is 0 and the trim still applies.

Checked on the radio (2026-10-30): DMR at 438.5 MHz, lowest power, read by an SDR's AFC once settled. +-5 ppm is 31 steps (4.96 ppm, 2175 Hz); the carrier moved +2155 and -2120 Hz from trim 0, after taking out the 86 Hz drift between the trim-0 readings before and after, as linear in time. That is within 3% of the scale, and the sign is right.

14.2 GPS module

No module is fitted at the factory, but the GPS pins are there: USART1 RX on PA10 and the power switch on PA9. Owners fit a small 3.3 V NMEA module (an ATGM336H or a GP-02, reported by users) and wire it like this:

Module pin Board STM32 pin (LQFP100)
TX (NMEA out) PA10, USART1 RX 69
power enable (where the module has one) PA9 68
3.3 V, GND a 3.3 V point on the board, such as the SPI flash's supply

PA9 and PA10 sit next to each other on the side of the package that holds pins 51-75. A module without an enable pin runs from 3.3 V all the time and leaves PA9 unconnected. Nothing goes to the module's RX: the firmware only listens.

RadioFoundry builds GPS by default (CONFIG_GPS). At start-up it drives PA9 high and listens on PA10 in 5 s windows, 9600 first. One checksum-valid NMEA sentence marks the module present. Characters without a valid sentence move on to the next rate (14400). A window of silence means no module: USART1 goes off, PA9 goes low, and the listening task ends and frees its stack. The task runs at low priority in the background, so start-up doesn't wait for it. Once heard, PA9 follows Settings > Location > GPS (hal_gps_t.enable): low and USART1 off while the setting is off. The code is boards/uv380_family/gps_uvf.c, shared with the MD-UV380 G models (hardware-mduv380.md 9). Untested with a module on a DM-1701.

15. Bootloader and firmware images

15.1 Entering the bootloader

Hold PTT + side key 1 (the key just above PTT) while turning the power switch on. The radio enumerates as a USB DFU device, VID 0x0483 PID 0xDF11 (ST's DFU IDs, but the TYT/AnyRoad bootloader, not ST's ROM loader). The device string at index 1 reads "AnyRoad Technology". The screen stays dark. The interface string describes the memory layout in the usual DfuSe "@name/0xADDR/NN*SSKg,..." form.

Normal mode is a DFU device too. The original firmware, switched on normally (the mode the vendor's programming software uses), also enumerates as 0483:DF11. On an MD-9600, a radio with the same bootloader, it shows the bootloader's manufacturer, product and serial strings as well. Only the layout of alt 0 tells the two apart:

Mode Alt 0 Alt 1
Switched on normally @Internal Flash /0x08000000/03*016Kg @SPI Flash Memory /0x00000000/16*064Kg
Bootloader @Internal Flash /0x0800C000/01*016Kg,01*064Kg,07*128Kg (the application area only) the same

Measured on an MD-9600, 2026-11-02. In normal mode the requests of 15.2 don't do what they do in the bootloader. 0x91 0x31 enters a programming mode whose erase and write don't protect the bootloader sectors, so running 15.2 against it can erase the bootloader. Both flashers (rfoundry, the web flasher, and tools/stm32_dfu.py) refuse such a device before any DFU request. A board whose bootloader layout was read on a radio declares it ([flash.dfu] layout, see board-registry.md), and then only that alt 0 string is accepted. Without a declaration, the flashers refuse a layout that shows only the bootloader's sectors: from 0x08000000, at most 48 KB. An MD-380 shows the same alt 0 strings as the MD-9600 in both modes (measured; hardware-md380.md 14.3). The DM-1701's and the MD-UV380's original firmware images hold the same normal-mode alt 0 string, @Internal Flash /0x08000000/03*016Kg (every DM-1701 build examined).

The DM-1701's bootloader, read on a radio (2026-11-02, standard descriptors only): manufacturer and string 1 "AnyRoad Technology", product "Digital Radio in USB mode", serial "00000000010C", bcdDevice 0x0200, alt 0 @Internal Flash /0x0800C000/01*016Kg,01*064Kg,07*128Kg, alt 1 @SPI Flash Memory /0x00000000/16*064Kg: the bootloader row of the table. boards/dm1701/board.toml declares alt 0, so the flashers accept only that device. The MD-UV380's bootloader strings have not been read on a radio (?).

15.2 Flashing protocol (DfuSe-style, as the loader drives it)

Step Request (bmRequestType 0x21 unless noted)
1 wait for idle: GETSTATUS (0xA1, request 3, length 6); while state != dfuIDLE (2) send CLRSTATUS (4) and repeat
2 vendor command DNLOAD (request 1, wValue 0, 2 data bytes) 0x91 0x01; GETSTATUS, 100 ms, GETSTATUS, wait for idle
3 vendor command 0x91 0x31, same handling (meaning of both commands unknown; required)
4 erase: for each address 0x0800C000, 0x08010000, 0x08020000, 0x08040000, 0x08060000, 0x08080000, 0x080A0000, 0x080C0000, 0x080E0000 (the loader also lists 0x08100000), DNLOAD wValue 0 with 5 bytes 0x41 + address (little endian); GETSTATUS must report dnBUSY (4) then dnIDLE (5)
5 per region (same list; sizes 0x4000, 0x10000, then 0x20000 each): set address = DNLOAD 0x21 + address; then DNLOAD data blocks of 1024 bytes with wValue = block number starting at 2 and incrementing (region 0x0800C000 uses blocks 2..0x11, 0x08010000 blocks 2..0x41, the 128 KB regions 2..0x81); after each block GETSTATUS must be dnBUSY then dnIDLE. The last block is padded with 0xFF to 1024 bytes
6 exit: set address 0x08000000, then DNLOAD with zero length; the device resets (it may not answer the final GETSTATUS)

The image is written as one contiguous stream starting at 0x0800C000: byte n of the file goes to 0x0800C000 + n.

Every listed region has the same rule: blocks 2..N, the key applied from the image start, which is block aligned at every sector start (for example 0x080A0000 - 0x0800C000 = 0x94000, a multiple of 1024). rfoundry erases and writes a region only when it has data, so an update leaves sectors 10 and 11 (the codec) out. The loader accepts a sector written on its own, with sectors left out on both sides: a RadioFoundry image that wrote only sectors 3-6 and 9 flashed through rfoundry, booted and passed the radio-only HIL group (2026-10-14).

15.4 Software entry to a bootloader

Goal: re-flash over USB without someone holding PTT + side key 1 at power-on (15.1). There are two possible routes, both reached from the running firmware through the debug link (docs/spec/debuglink.md 3.9-3.11).

Read protection. rfoundry_debug.py chip on a DM-1701 (2026-10-10) reads idcode 0x0009A413 (STM32F405/407), 1024 KB flash, FLASH_OPTCR 0x0FFF55ED: RDP level 1 (byte 0x55), no sector write protection, BOR off, user bits all 1. Assume every DM-1701 is at RDP level 1 until one reads otherwise. RDP level 1 does not stop the application from reading flash (only a debugger, RAM boot and system-memory boot are locked out), so the bootloader (sectors 0-2) can be read with rfoundry_debug.py dump. It is proprietary and is never committed.

Route 1: ST's ROM bootloader (USB DfuSe in system memory). Refused on this radio. The firmware has it: REBOOT mode 1 stores the flag 0xB007DF11 in RTC_BKP19R and resets. A backup register is used rather than RAM because the bootloader runs in RAM before the application. First thing in main(), stm32_sysboot_check() (platform/stm32f4/sysboot.c) finds the flag and then:

  1. clears the flag and checks that it is clear, so a failed entry boots normally next time (and boots normally anyway if the flag won't clear);
  2. sets the power-up pin levels (board_sysboot_prepare: power latch high, transmitter off, HR_C6000 powered down);
  3. turns interrupts off, stops SysTick and clears every NVIC enable and pending bit;
  4. returns RCC to HSI with HSE and the PLLs off at their reset values, sets FLASH_ACR to 0 and resets every peripheral except the GPIO ports;
  5. checks that 0x1FFF0000 holds a plausible vector table, maps system memory at 0 (SYSCFG_MEMRMP), sets VTOR to 0, loads MSP from 0x1FFF0000 and jumps to the vector at 0x1FFF0004.

The firmware and rfoundry_debug.py both refuse this mode unless RDP is level 0. At level 1 the ROM bootloader refuses every flash access, and its only way out, the read-unprotect command, sets RDP to 0 by mass-erasing all of flash, the bootloader included. After that the radio could be reloaded only over SWD. At level 2 the ROM bootloader is disabled. On the bench unit (RDP 1) this route is closed. The code stays in the firmware because it is gated and does nothing unless the flag is set. If a unit ever reads RDP 0, the procedure would be: rfoundry_debug.py chip -> rfoundry_debug.py reboot --rom-dfu -> a DfuSe host that erases and writes only sectors 3-11 (0x0800C000 and up). No such host tool exists in tools/: stm32_dfu.py has no ROM mode.

Untested risks of route 1, found while writing it (they matter only on an RDP 0 unit):

  • Power latch. The volume knob only breaks the battery-sense line (10.4); PA7 holds the supply. While the ROM loader runs, PA7 stays high, so the knob cannot turn the radio off. Getting out of a stuck ROM loader takes a DfuSe leave command or removing the battery. Because the flag is already cleared, the next start is normal.
  • HSE clock. The board feeds an external clock in bypass mode (1.2), not a crystal. ST's ROM needs HSE for USB DFU on the F405 and may set it up in crystal mode. If that doesn't start, USB DFU never enumerates.
  • Interface probing. The ROM also listens on USART1 (PA9 / PA10, wired to GPS power and GPS RX on GPS-fitted siblings) and on USART3 / CAN2. Activity on those pins can capture the loader before USB. The DM-1701 has no GPS fitted from the factory, so PA10 is idle on it. An owner-fitted module (14.2) talks on PA10 from power-up.
  • Leaving. Where the ROM's DfuSe leave command jumps, and with which memory mapping, is unverified. A battery pull always returns to the normal start (bootloader, then the application).

Route 2: a software entry into the bootloader's own DFU mode. This route would leave RDP alone and keep the XOR-keyed DfuSe path that tools/stm32_dfu.py already speaks (15.2, 15.3). It works only if the bootloader checks something besides the PTT + side key 1 combination that firmware can set before a reset: a RAM word it reads before clearing RAM, an RTC backup register, or a backup SRAM location.

There is no such flag. The bootloader decides once, after its own startup has cleared and initialized main SRAM, and there is no timeout. It stays in DFU when either of these holds; otherwise it loads MSP from 0x0800C000 and jumps to the word at 0x0800C004:

  • GPIOE IDR bits 8 and 11 (PE8, keypad column 5 / side key 1; PE11, PTT) both read low, the power-on key combination.
  • The application's initial stack pointer at 0x0800C000 fails (SP & 0x2FFE0000) == 0x20000000, so an erased sector 3 (0xFFFFFFFF) keeps it in DFU. The reset vector is not range checked.

It reads no RAM word, no RTC backup register or backup SRAM, and no reset-cause flag (RCC_CSR), and it doesn't set VTOR (the application sets its own). So nothing firmware can set before a reset makes it stay in DFU, except making the application look invalid. The least damaging way is a single flash word program that clears bit 29 of the word at 0x0800C000 (0x2001FFFC to 0x0001FFFC; programming can only clear bits, so no erase is needed). After that the radio boots into DFU every time until a full image is written again, which tools/stm32_dfu.py does. Sectors 0-2 are never touched, so the bootloader always stays reachable. This is not implemented; it is a candidate REBOOT mode 2 with the same gate plus an explicit confirmation in the tool.

Route 3: no bootloader at all, for updates. A build with CONFIG_STUB_ENTRY=y loads a RAM flash stub over the debug link and the stub writes the application sectors itself (stub-stm32f4.md). It uses the DFU check above as its safety net: it erases sector 3 first and programs the word at 0x0800C000 last, so an interrupted update leaves the radio in DFU at the next power-on with no keys held.

18. Gotchas summary

  1. The bootloader rejects an initial stack pointer equal to the top of RAM; use 0x2001FFFC.
  2. Set VTOR to 0x0800C000; the vector table is not at 0x08000000.
  3. The bootloader leaves HSE/PLL running: switch to HSI before reprogramming HSE/PLL.
  4. CCM RAM is not zeroed or initialized by default startup code and is invisible to DMA. RadioFoundry puts the RTOS heap (every task stack), the slot engine, the radio state machine and the big CPU-only buffers there; .ccmbss (RFOUNDRY_CPU_RAM) is zeroed before main by a .preinit_array entry in board.c, .ccmram (RFOUNDRY_CPU_RAM_NOINIT) is not. DMA buffers stay static in main SRAM, and each stream's set-up checks that (DMA_RAM_OK).
  5. The codec must be at exactly 0x0807537C; the code budget is the space below it. Keep large constant tables above the codec end if the code grows.
  6. PA13 is SWDIO; driving it as mic power breaks SWD (use connect-under-reset).
  7. LCD data lines double as keypad columns: discharge them before reading keys, and leave them low after LCD writes.
  8. HR_C6000 config SPI and AT1846S I2C are touched from ISRs and tasks: make transactions atomic, and never block on I2C in an ISR.
  9. The PA is switched per burst in DMR; "transmitting" must come from the modem's slot state, not from the PA pins.
  10. The HR_C6000 RF_RX_EN / RF_TX_EN pins are not wired to the MCU; RF switching is done by the MCU (I2C + GPIO), about 0.5 ms per switch.
  11. The AT1846S TX frequency offset depends on the write sequence (about -3 kHz with the normal sequence, none with a direct switch); measure, do not copy.
  12. DMR RX needs AT1846S AF gain 1 dB under full (0x44 = 0x07EF; 5.5: full overloads the modem, -2 dB loses under-deviated transmitters) and reg 0x40 bit 0 set; FM needs bit 0 clear.
  13. A volume-knob power-off looks like the battery dropping below 5.5 V; the firmware must then release the PA7 latch.

20. Bench findings (RadioFoundry on a DM-1701, 2026-10-09)

Verified on one radio with the new firmware; they override the unverified notes above where they differ.

  • Keypad: the 10.1 matrix is right. The two "function" keys are labeled P1 (row 0, D6) and P2 (row 0, D5). There is no orange key: the three black side keys are, top to bottom, row 2 D5 (the "top key" position), row 2 D7, row 2 D6; PTT is separate, between the first and the second. The firmware names them SK1, SK2 and SK3 in that order. SK1 (D5), just above PTT, is the key held with PTT to enter the bootloader. A row released while still high stays charged and makes every key also read as the key below it: drive the row low before releasing it and keep idle rows pulled down.
  • Encoder: clockwise counts up with the 10.3 rule, one count per detent.
  • Panel: this radio reports type 2 (security register 3, byte 0x1D). Driving it with the type 2 MADCTL (0xE0) shows the picture mirrored top to bottom; treating it as type 3 with RGB order (as 9.2 says) is correct. The 8 hidden rows are panel rows 0-7 either way.
  • Volume pot: raw 26 at the bottom, 2063 at the top.
  • Battery: raw / 37.5 gives a plausible 7.1 V (not yet checked against a meter).
  • Calibration: the working copy at 0x010000 carries the marker. The FM I gain rows (0x170 UHF, 0x179 VHF) are all 0x00 on both bands while the other gain rows hold values: an all-zero gain row is valid data.
  • Soft volume: HR_C6000 4:0x37 (RX gain) scales FM feed-through audio as well as DMR audio; -31 dB is still audible, so the bottom of the knob must also mute the speaker path. It mutes the amp only: the feed-through (0x36) and the gain (unity at the bottom) stay as for any FM receive, because the I2S copy of the FM audio that APRS receive reads is gated and scaled by both. Before this, a knob at zero turned the feed-through off and APRS heard nothing.
  • Volume override: because the MCU reads the knob and sets this gain itself, the debug link can set the level instead (RADIO op 30, radio-features.md 4.2): a step 0..16 maps to the same 0..100 % scale as the knob, in force until it is cleared (RAM only). The knob has no analog path around the gain, so the override fully takes its place (HW, not yet run on a radio).
  • HR_C6000: 4:0x10 reads back 0x80 after FM RX set-up (the config port works with the 4.2 timing).
  • FM TX (VFO on a UHF test frequency, 12.5 kHz, 1 W, measured with an RTL-SDR, 2026-10-09): with the TX sequence of radio_dm1701.c (frequency written with the receiver off, straight to TX) the carrier is within about 50 Hz of the channel, so no TX offset is added. Unmodulated carrier residual FM 41 Hz RMS, no hum or tone. Voice at normal level: 2.5 kHz peak deviation (99.5th percentile), 636 Hz RMS, about 7 kHz occupied at -26 dB. The FM I calibration row of 0 (Mod2 amplitude) does not stop voice modulation.
  • DMR TX (a UHF test channel, cc 2, 1 W, SDR bench + an MMDVM_HS receiver, 2026-10-10): switching per burst from RX on straight to TX on the already-tuned frequency put the carrier 3.07 kHz low (an ADF7021-based receiver decoded nothing; a wide-AFC SDR decoder still did). Retuning with the receiver off before every burst (as FM TX does) brings it to about +65 Hz, and the MMDVM_HS receiver decodes headers, all superframes with the embedded LC and the terminator. Burst spacing 60.000 ms (sd 0.002 ms), 31 ms PA per burst.

21.2 DMR

The DMR voice path already moves PCM between the MCU and the codec in both directions (core/dmr/ambe/ambeVoice.c): decoded frames are played as 20 ms blocks, and microphone blocks are encoded while transmitting. For a USB voice endpoint the audio router (usb-audio.md 5.1) takes the decoded block for the host as well as (or instead of) the speaker, and feeds host PCM to the encoder instead of the microphone. CPU, codec stack and RAM are what a normal DMR call uses (the AMBE codec runs for one direction at a time; a DMR radio is half duplex). DMR on this board was verified on air in both directions (section 20).

21.3 FM

What the HR_C6000 manual says:

  • The built-in codec's input mux takes MIC_P / MIC_N (differential) or LINEIN1 / LINEIN2 (single ended), then a gain stage, the ADC and a digital filter; its output path is a gain stage (page 4 0x37), the DAC and LINEOUT1 / LINEOUT2 (manual 4.5.1, figure 4.12).
  • Register 0xE0 (manual register table, Chinese section): bit 7 MCU controls the codec, bit 6 LINEIN1 enable, bit 5 LINEIN2 enable, bit 4 LINEOUT1, bit 3 LINEOUT2, bit 2 MIC_N, bit 1 MIC_P, bit 0 I2S slave. Our 0xC9 (DMR, FM TX) is MCU control + LINEIN1 + LINEOUT2 + I2S; 0x89 (FM RX) the same without LINEIN1. So the microphone is wired to LINEIN1, and modem-hrc6000.md 2 calls bit 6 "mic input enable", which is right in effect. On a DM-1701 board photo, pin 8 (LINEIN2) has no trace and pins 6 (MIC_N) and 7 (LINEIN1) share a via; the bench agrees (21.3.1, LINEIN2 loop). FM receive audio plays with 0xE0 = 0x89, both line inputs off, and the HR_C6000 detects the sub-audio tones, so the receive audio reaches its FM chain through the baseband ADC (the path DMR uses), not the codec inputs: section 8's "line in" for FM RX is probably that. Pin 8 is the free analog input for a mod (candidate D).
  • 0xE3 bit 0: "codec internal DAC and ADC pass-through enable, normally 0". The direction is not stated.
  • The FM transmit chain takes the codec ADC's samples; the FM receive chain ends at the codec DAC (manual 6, figure 6.1). The I2S "vocoder interface" carries the codec ADC's samples to an external vocoder and the vocoder's PCM to the DAC (manual pin table, C_SDI / C_SDO; 0x22 bits 2-1 choose I2S and its master mode). Nothing says the FM chains can read from or write to the I2S interface.
  • The chip has "FM data" RAM: two 512-byte buffers in the TX RAM ("can be written externally for FM send; voice data can also come internally from the codec") and two in the RX RAM (manual 5.3 tables), and FM-mode interrupts in 0x82: bit 7 "FM: sending data request", bit 1 "FM: receiving data". Register 0xD7 bit 1 (written 0xDB here before) selects "send FM voice" over MSK signaling. This looks like the MCU can exchange FM audio samples with the chip through its RAM pages, but the format, rate and control are not documented. Our FM RX set-up writes 0x81 = 0x19, which masks both FM data flags.
  • The FM chain can use an external codec instead of the built-in one (0x06 bit 2, appendix A2), over a second I2S port on pins 17-20 with the chip as master. The MCU sits on the other one, the vocoder port (pins 34-37), so this only helps if pins 17-20 reach the MCU, which nothing we have shows. The block diagram's "I2S" next to the FM transmit chain is this port.
  • A "prompt tone" path (0x06 bit 1, appendix A1) lets the MCU write DAC samples over U_SPI without I2S: speaker only, but with 0xE3 bit 0 it is another way into the ADC and so the FM transmit chain if the I2S clock stops in FM. modem-hrc6000.md 8.1 has the details of all of these.

Each bit of 0x25, 0x26, 0xE1, 0xE2, 0xE3, 0xE5, 0x0D, 0x0E, 0x0F and 0x38 flipped for 0.5 s (80 flips, 10 key-ups) with a 600 Hz tone on I2S and a 1 kHz tone in the TX RAM: neither tone on air during any flip. LINEIN2's tone, used as the time marker, came at 2.59-2.61 kHz this time (2.49 kHz before): an oscillation on that input |

So the chip's FM chain takes audio only from its codec ADC (microphone, LINEIN1, LINEIN2) or the external codec port; nothing the MCU writes over U_SPI or I2S reaches it. MCU audio goes on air through the modulator's MOD1 offset (0x04) instead, with the MCU doing pre-emphasis, limiting and CTCSS, at about 6 bits; AFSK can use the chip's tone generator. Full quality needs candidate D (the PC11 to pin 19 wire). The register reference with the manual's details is hrc6000-registers.md.

Candidates, in order of preference:

A, B and C don't work (21.3.1). Receive uses the I2S stream or the RX RAM tap. Transmit uses E, or the MOD1 offset for content above the codec's band; AFSK can also use the chip's tone generator.

The probe experiments, in the order they were run:

  1. Does the I2S clock run on an FM channel? (If not, no FM PCM at all without C. Beeps on FM depend on it too: beep.no_stream in radio-features.md 4 asks the same question.)
  2. Receive: NOAA weather radio in the VFO with the squelch open, then a quiet frequency; for the register settings as set, A, LINEIN1 and B, the RMS of both I2S channels. A setting whose RMS rises clearly with the signal carries receive audio. It also tells which I2S channel the chip fills (audio_dm1701.c assumes the left one, unverified).
  3. Transmit (opt-in RF, SDR bench): key FM with the microphone muted (0xE0 bit 6 off) while the probe sends a 1 kHz tone into I2S; for "no tone", "tone", B and A, the voice band deviation the bench measures.
  4. Candidate C, receive: on NOAA and on a quiet frequency, the rate of the 0x82 FM flags with 0x81 as set and with bits 7 and 1 unmasked, whether the RX RAM buffers change, and their level read as 16-bit (both byte orders) and 8-bit samples.
  5. Candidate C, transmit (opt-in RF): both TX RAM buffers hold a 1 kHz tone, a whole number of cycles in 256 samples, so a chip that replays them sends a steady tone without refills. Keyed with the microphone muted, for the likely source settings (FM flags unmasked, 0xDB bit 1 (meant: 0xD7 bit 1), 0x60 = 0x40 or 0xC0, 0x06 bit 0, big endian samples): the FM flag rate and the voice band deviation against a silent-RAM baseline.

21.4 Running the probe

With the AMBE codec merged as usual:

make BOARD=dm1701 CONFIG_AUDIO_PROBE=y BUILD=build/dm1701-probe   # flash build/dm1701-probe/rfoundry_dm1701.bin
python3 -m pytest tests/hil/test_audio_probe.py -v -s -rs          # stream in FM, the receive variants (NOAA), RX RAM
python3 -m pytest tests/hil/test_audio_probe.py -v -s -rs --allow-rf --allow-service-stop -k tx   # I2S and RAM TX variants

By hand (an FM channel or the VFO):

tools/rfoundry_debug.py aprobe start            # stream with silence out; then:
tools/rfoundry_debug.py aprobe status           # blocks counting up = the I2S clock runs in FM
tools/rfoundry_debug.py aprobe reg 4 0xE0       # 0x89 expected in FM receive
tools/rfoundry_debug.py aprobe wreg 4 0xE0 0xA9 # LINEIN2 on (candidate A); status / samples with and without a signal
tools/rfoundry_debug.py aprobe wreg 4 0xE0 0x89
tools/rfoundry_debug.py aprobe wreg 4 0xE3 0x53 # candidate B (0xE3 is 0x52 at init: bit 0 set); watch status
tools/rfoundry_debug.py aprobe wreg 4 0xE3 0x52
tools/rfoundry_debug.py aprobe samples -o /tmp/blk.raw   # one block of both channels, tone estimate printed
tools/rfoundry_debug.py aprobe stop
tools/rfoundry_debug.py aprobe wreg 4 0x81 0x9B # unmask the FM data flags (0x19 | 0x82)
tools/rfoundry_debug.py aprobe watch 1000 0x82 0x030   # FM flag rates, RX RAM word changes
tools/rfoundry_debug.py aprobe ram 2 0x030 64   # the start of the RX FM buffer

Expected readings: in FM receive with the defaults, both channels near silence (the microphone is off). A candidate works for receive if, with NOAA audible and the squelch open, one channel's RMS rises well above (4x or more) its value on a quiet frequency. For transmit, the SDR bench's voice band RMS deviation with the tone and the candidate setting is well above the "mic muted, no tone" row.

22. Facts moved from the shared specs

  • Settings and storage: the core's map for the 16 MB SPI flash is settings 0x011000 (32 KB, 8 sectors), journal 0x019000, open-firmware EEPROM 0x000000, open-firmware flash 0x020000 up to 0xE00000, native area 0xE00000 (1 MB), TFTP staging 0xF00000 (256 KB), calibration window 0x010000 (512 B). The range 0x011000-0x01AFFF has never been checked on a used radio, for the foreign-region guard of settings-store.md 5.
  • The board's hal_radio has tx_tone, so the MMDVM task keys the 1750 Hz burst (mmdvm-protocol.md).
  • USB: the STM32F405 OTG_FS has three IN endpoints besides EP0, so serial and network are alternatives, not a composite (usb-network.md).
  • board_rf_safe pins: PA_EN1 (TX supply) and PA_EN2 (APC loop) low, PA_BAND low, APC DAC (DAC1 channel 1) 0.
  • GPS: USART1 RX on PA10, with PA9 as the GPS power switch.
  • Crash log (crash-log.md): the backup SRAM kept the record through the bootloader. A trap test gave HardFault with CFSR UNDEFINSTR in the task host; a hang test ("CRASH TEST") was recorded at 3750 ms. The snapshots named radio_task, dmr_task, input_task, the UI task in input_next / ui_task and the USB task in tud_task_ext (2026-10-17/23, test_crash.py). The restart cause after a watchdog reset is watchdog.
  • Roaming (dmr-roaming.md 3): a survey visit relies on the AT1846S RSSI plus HR_C6000 sync acquisition needing well under 100 ms on a continuous outbound (a burst every 30 ms), then four 25 ms readings.
  • On air since 2026-10-10: receiver sleep (test_battery_save*: cycles when idle, monitor and a call wake it), the 1750 Hz burst, the roger beep and APRS AFSK (HIL). VOX was checked in silence only (test_vox_quiet).
  • AFSK TX retunes the AT1846S tone generator per symbol. The AFSK RX audio comes from the HR_C6000 FM audio on I2S (squelch gated, 8 kHz, de-emphasized). DMR LRRP and UDT passed on air on a UHF test frequency, CC 2, 50 mW. An AFSK tone level of 0x1C gives about 3.1 kHz peak deviation (0x40 gave 7.2 kHz).
  • REBOOT mode 1 enters the ROM DFU with a flag in an RTC backup register (15.4). The spare beep PWM pin is PC8 (TIM8 CH3, 72 MHz carrier, DMA2 stream 2), used by AUDIO_PROBE PIN_TONE / PIN_PWM at about 37,000 MOD writes a second.
  • Release and flashing: application sectors 3-9 (720 KB), codec sectors 10 and 11 (1.4), keep supported, profile dm1701-v0206-csv-s11. Releases before the move linked read-only data into sector 9 as a second range, profile dm1701-v0206-csv. An update erases first, then writes in sector order, sector 3 (the vector table) first, so a cut before it leaves the bootloader in DFU; a later half application may crash but never bricks. Enter the bootloader by hand (PTT and side key 1 at power-on) and flash again.

Air interface (CONFIG_P25, CONFIG_NXDN)

Receive past the rated bands
