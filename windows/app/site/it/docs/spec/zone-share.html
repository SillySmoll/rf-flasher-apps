Zone sharing over DMR data

One radio sends a zone, or one channel, to another radio or to a talkgroup over DMR data. The receiver shows it as an offer and imports it only when the user says so. Status: built and host-tested (zoneShareTest, zoneShareSvcTest, zoneImportTest, the UI flow tests; the modes part in zoneShareModesTest and zoneImportModesTest, untested on a radio). On a radio, sending one channel has been checked against the SDR bench; sending a zone, offers and the import are untested there. The opt-in HIL test is tests/hil/test_zone_share.py (feature zone_share).

Sources: ETSI TS 102 361-3 (packet data, the UDP/IP bearer), RFC 768 (UDP), dmr-data.md 11 and 12 (IP over DMR, the TX queue). The record format is ours.

1. Switches and files

Item Where
Switch CONFIG_ZONE_SHARE, on by default where DMR is built (build-config.md). It also builds the TX queue (CONFIG_DMR_AIR_QUEUE)
Record and messages core/dmr/zoneShare.c: encode, strict decode, reassembly. No state but the buffer the caller owns
Service core/dmr/zoneShareSvc.c (zone_share_api.h): sending through the TX queue, offers, the rate limit, directory requests
Import and export core/codeplug/zone_import.c: the only code that writes the codeplug for zone sharing (6)
UI core/ui/ui_svc_zone.c (the glue, the import as a storage job), screens in core/ui/ui_menus.c
Debug link the air view section: zs.* keys (debuglink.md 3.7)

2. Transport

  • UDP, source and destination port 4100, over the data service's IP bearer (dmr-data.md 11). Port 4100 is outside 4000-4099, so the UDP header is compressed on auto (SAP 3).
  • To a radio: confirmed packets. To a talkgroup: unconfirmed packets. Each message is one IP packet.
  • Every message goes through the TX queue (dmr-data.md 12.6). A send puts all its fragments in at once or none of them. Unconfirmed fragments to one talkgroup go out chained in one transmission (12.6.2).
  • A fragment the data service doesn't take within 10 s fails the send. The other fragments of that send are canceled.

3. Messages

Every message starts with the version (1) and the type. Multi-octet fields are big-endian.

Type Octets Layout
1 Fragment 7 to 328 sent, up to 568 taken version, type, transfer number, index (bits 7-4) and count (bits 3-0), offset (2), chunk
2 Request 5 version, type, request number, what (1: the zone of the site the request came in through), options (0)
3 Refusal 4 version, type, request number, code

3.1 Fragments

  • A record of up to 1024 octets goes in 1 to 4 fragments of 322-octet chunks, the last one shorter (ZS_SEND_CHUNK).
  • The chunk size is the sender's. A receiver takes any from 128 octets up to the longest message the air MTU allows with the full IPv4 and UDP headers (ZS_MSG_MAX = DMR_DATA_IP_MTU - 28: 568 octets, a 562-octet chunk, dmr-data.md 12.8). That limit grows with the air MTU. A record in 128-octet chunks takes 8 fragments, the most a transfer may have.
  • We still send 322: the first builds take only that chunk size and messages of at most 328 octets, and would drop larger fragments. Every build since takes chunks up to 562, so the sender can move up to 562 (2 fragments for a full record) once the first builds are no longer in use. A build whose air MTU is larger takes larger chunks, but must not send them while builds that take only 562 are in use. zoneShareTest checks our fragments against the first builds' rules.
  • Every fragment but the last is full, and its offset is index x its length. The last fragment's offset is a whole number of chunks of a size the receiver takes, and it is no longer than one. Every fragment of a transfer must give the same chunk size. A fragment that breaks a rule is dropped (zs.rx_bad).
  • The transfer number is the sender's, one per send.

3.2 Reassembly

Rule Behavior
One at a time one transfer from one sender is assembled. A fragment from anyone else meanwhile is dropped (zs.rx_busy)
Time-out a transfer whose fragments stop for 30 s is dropped when the next fragment arrives, from anyone
Started over the same sender with another transfer number or fragment count replaces its transfer
Duplicates a fragment already in is ignored
Done when every fragment is in, the record is decoded (4) as a whole; one that fails is dropped

3.3 Refusal codes

1 site unknown, 2 site not seen for a long time, 3 no frequency on record, 4 busy, 5 not supported, 255 other.

4. The record

Part Octets Fields
Header 10 + name version (1), length (2, the whole record), zone ID (4, not 0), flags, channel count (1-80), contact count (0-32), name
Contact 4 + name type (bits 1-0: 0 group, 1 private, 2 all call) and slot (bits 3-2: 0 the channel's, 1, 2), ID (3, not 0), name
Channel 6 to 15 + name flags, RX Hz (4), then as the flags say: TX offset (4, signed, not 0), DMR (2), RX tone (2), TX tone (2); name
  • A name is a length (0 to 16) and that many printable ASCII octets. The sender writes ? for anything else.
  • Record flags: bit 0, one channel (the count must be 1); bit 1, a modes part follows the channels (4.2). The other bits are reserved and must be 0. A build without the modes part refuses a record with bit 1 set.
  • Channel flags: bit 0 DMR, 1 25 kHz, 2 TX offset present, 3 RX tone present, 4 TX tone present, 5 receive only on the sender, bits 7-6 power (0 the default, 1 low, 2 mid, 3 high).
  • DMR octets: the color code (bits 3-0), slot 2 (bit 4), direct mode (bit 5), bits 7-6 reserved; then the contact, a 1-based index into the record's contacts or 0. A DMR channel carries no tones.
  • A tone: the type in bits 15-14 (1 CTCSS, 2 DCS, 3 DCS inverted), the value in bits 13-0. CTCSS is Hz x 10 (600 to 2600). DCS is the code as an octal number (023 is 19), at most 0777.
  • Contacts come first, then channels. The record must end exactly where its length says.
  • The decoder checks every length, count, reference and value before use. A record that fails one check is refused whole.
  • Zone ID: the sender's choice, the same each time it sends the same zone. Ours is an FNV-1a hash of the zone name and the flags.

4.1 What a send holds

The sender takes the zone's channels in order, each with its contact, while the record fits 1024 octets and 80 channels. The rest are left out, and the UI says how many go ("Sending 40 of 60 channels"). Nothing else of the codeplug is sent: no scan lists, no RX group lists, no privacy keys.

4.2 The modes part

Channels of a kind (channel-modes.md) go with their tags and the systems they are on. Builds with a mode that has channels of a kind carry them (CONFIG_ZONE_SHARE_MODES, on with CONFIG_ZONE_SHARE and CONFIG_P25 or CONFIG_DMR_TRUNK). A record holds the part only when it has such a channel, so a share of plain channels is the same as before. Every length is one octet. Kinds' and system types' bytes are opaque here: their mode modules read them.

Part Octets Fields
Systems 1 count, 0-8
System 5 + block + name, a whole one 2 + secret more type (not 0 or 0xFF), flags (the system record's, bits 2-3 0), level (1 identity, 2 whole), identity length (at most the block's), block length and block (at most 200; level 1: the identity alone), name; level 2 only: secret length and secret (at most 64), entry count
Entry 4 + body class, group, flags, body length and body (at most 64): a level 2 system's entries follow it. At most 64 in a record
Tags 1 count, 1 up to the channel count
Tag 5 + params channel (1-based, each after the one before), kind (not 0 or 0xFF), system (0 none, 1 up to the systems count, 0xFF on a system the sender doesn't share), flags (the tag's, bits 2-3 0: the fallback channel is never carried), parameter block length and block (at most 64)

What a sender carries of a system follows its sharing level (channel-modes.md 7.1):

Level Carried
Off nothing: its channels' tags say 0xFF
Identity only type, flags, name and the identity
Whole system with key the block and every entry too, and the secret only when the sender turns keys on for that share. A radio has no such switch yet and never sends a secret. A system whose block or entries pass the limits goes as its identity

Never carried: the radio's own ID on a system, a system's or a channel's fallback channel. Targets (channel-modes.md 5.2) are not carried yet: no kind in this tree refers to them.

A channel whose tag's parameter block passes 64 octets is left out. Without the modes part a sender leaves every channel of a kind out: its record is a stand-in that a receiver would take for a plain channel.

5. Receiving

5.1 The setting

Settings > Connections > Accept zone shares: On (the default) or Off. With On, a share is offered to the user, who imports it or not (5.2); nothing is imported without that. With Off, fragments are dropped (zs.rx_off) and nothing reaches the user. The setting is zs_offers in the settings record: 0 (never set) and 1 are On, 2 is Off (settings-store.md). In the service and on the debug link, 1 (ZS_OFFERS_ASK) is On and 0 Off.

5.2 Offers

Rule Value
Offers at a time one. While it waits, other records are dropped (zs.rx_busy)
Rate limit at most 6 offers an hour; more are dropped (zs.rate_limited)
Lifetime an offer not opened within 10 minutes is dropped (zs.expired). Once opened, it waits for the user
Group offers a record sent to a talkgroup the radio listens to is offered like one sent to it

The offer shows as a banner, "Zone from " with "Zone , channels". # opens it. The banner has no timer: it stays until # opens it, Back hides it (on any screen), or the offer ends (it expires, or is answered from Tools, which also hides it). Another banner can take its place. While it waits it is also under Tools > Zones/Chs Received. The offer screen (Zone Share Received, or Channel Share Received) reads "Zone , channels, from " and how many are not in this radio's bands, with three choices:

  • Import imports it (5.3).
  • Preview lists the channels: name, frequency, mode, and "Not in band" for those that can't be received.
  • Reject drops it.

A one-channel offer asks which zone to add the channel to.

5.3 Import

Rule Behavior
Band limits only channels whose RX frequency is in this radio's bands are imported (board_in_band). The rest are counted and left out. None in band: nothing is imported
Receive only every imported channel is receive only, whatever the sender had. The user turns transmit on per channel. The one exception: a channel of a kind on a system the radio has (5.5)
Power the power class maps to this radio's levels: low the lowest, mid the middle, high the highest, default the codeplug's default
Contacts matched by ID and type against the user's contacts; a match keeps the user's name. Only contacts that imported channels use are added, in the lowest free slots. The same contact twice in a record becomes one
New zone added through the zone editor's write layer, as a new zone there is (ui.md 2.2): it takes the lowest free slot, which can be ahead of other zones, and whoever holds a zone index follows the move. An update rewrites its zone in place. A name already in use gets " 2" to " 99", shortened to fit 16 characters
No stored zones the radio's "All channels" zone is stored as zone 0 first, so the user keeps it
One channel added to the end of the zone the user picked (zone_edit_insert)
Failure anything written is undone: no full zone list, no free channel or contact, a flash write error

The import runs as a storage job, not on the UI task. The banner after it reads "Imported " or "Updated " with " channels, receive only".

5.4 Updates

A zone sent again by the same sender with the same zone ID updates the earlier import instead of adding a zone.

  • The radio remembers its last four imports in the settings record (zs_import): a key (an FNV-1a hash of the sender's ID and the zone ID), the name the zone got, how many channels the import wrote and their signature (the XOR of an FNV-1a hash of each channel's number and every field). The oldest is forgotten first.

  • The update finds the zone by that name. If the user renamed or deleted it, the zone comes in as a new one.

  • An update replaces only the earlier import's channels that the user left unchanged. Anything the user added to the zone or changed (a field, transmit turned on) stays in the zone, after the new channels, in its order.

  • Which channels are the import's:

    Case Replaced
    The zone still starts with the channels the import wrote, unchanged (the first count match the signature) those; everything after them is the user's
    Otherwise (the user changed, moved in or removed a channel among them) only channels identical to one the new copy brings. An earlier channel the sender has since changed or dropped stays; the user deletes it

  • Replaced channels that no zone lists any more are deleted. Contacts are never deleted.

5.5 Channels of a kind

With a modes part (4.2), after the import's channels are chosen:

Rule Behavior
Systems matched by type and identity against the radio's own. A match is used as it is: nothing of the radio's system is changed. A whole system the radio doesn't have is added when an imported channel is on it (its own ID 0, no fallback), with its entries and its secret if the record has one. It takes the lowest free system number among those a radio runs (0 to 7); with none free it is missing. Listen only comes as the sender set it: the receiver never forces it
Missing a system sent as its identity that the radio doesn't have, one the sender withholds, or one with no room left: its channels come in with no system, receive only, and the import counts them as unavailable. The Codeplug Editor flags them
Tags written for each imported channel: kind, flags and parameter block as sent
Transmit kept only on a channel whose system the radio has; the system's listen-only flag then rules. Every other channel is receive only (5.3)
Undo a failed import removes the systems, entries and secrets it added with its channels

The offer counts the channels that will come in unavailable, and the banner after the import says how many did.

6. Directory requests

A radio may ask a directory service for the zone of the repeater or hotspot its request went through (zone_share_request, type 2). The answer is a record, taken as an offer even with offers Off (the user asked), or a refusal (3.3). An answer later than 60 s is not taken. No screen sends requests yet.

7. Sending

In a zone's channel list, # opens "Share zone to..." and "Share channel to..." (the focused channel). With the zone editor (CONFIG_ZONE_EDIT), # on a channel opens its Channel actions, where "Share channel to..." is item 5, and "Share zone to..." is item 3 of Zone options (ui.md 2.2). The channel editor has "Share channel to..." after "Tune to this ch" (ui.md 2.1); it sends the stored channel, so unsaved changes must be saved first. The rows carry a share icon, and the offer's title and banner a download icon. Then the contact list (Share To): a private contact gets confirmed packets, a talkgroup unconfirmed ones. Digits that make an ID add two rows after the contacts, "Private ID 9991234" and "TG 9991234", so a station that isn't a contact can be sent to. The send works only on a DMR channel: on another, OK says "Go to a DMR channel to send" and sends nothing. The send's toast names the frequency: "Sending to Q1AAA Joe via 442.375" ("Sending via 442.375" where that doesn't fit). It is the channel's receive frequency, which on a repeater is its output. The banner says "Sent to " or "Not sent to ". One send at a time.

8. Limits

Limit Value
Record 1024 octets, 80 channels, 32 contacts
Names 16 printable ASCII characters
Fragments sent: up to 4 of 322 octets; taken: up to 8, chunks of 128 to 562 octets
RAM about 4 KB on one board's build; the record being sent comes from the RTOS heap while it is made (feature-matrix.md)
