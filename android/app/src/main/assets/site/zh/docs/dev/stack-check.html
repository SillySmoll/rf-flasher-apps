Stack Check

make BOARD=<b> stack-check computes the worst-case stack depth of every FreeRTOS task in a build and fails when a task's deepest call chain doesn't fit its stack. tools/ci.sh runs it on each board's default and maximal configuration, --quick too, so every pull request's firmware jobs check both. It exists because an overflow is invisible elsewhere: the host tests run the same code on large pthread stacks, and on the radio FreeRTOS' overflow hook spins without a word. A 768-byte buffer in codeplug_contact_find once overflowed the start task at boot; the check reported that chain 424 bytes over.

On the radio, the debug link's tasks view section shows what each task has really used: its least free stack since it started (debuglink.md 3.7, CONFIG_TASK_STACKS), and tests/hil/test_task_stacks.py checks every task keeps 64 bytes. The check here is the worst case over every path; the view is what the code that ran so far needed. A task low in the view but fine here points at a call the check doesn't see (a table line).

How it works

Input From
Frames and direct calls GCC's -fcallgraph-info=su, always on (STACK_INFO in the Makefile): a .ci file next to each object, or one per LTO partition next to the .elf. It changes no code: the image is byte for byte the same without it
Tasks Every xTaskCreate(fn, "name", STACK, ...) in the compiled sources. STACK is evaluated with the build's own preprocessor and flags, so #if choices count. FreeRTOS' timer task is found the same way; its idle task is in the table
Calls through pointers The sources, below, then the table
Code without a call graph The disassembly of the .elf (objdump): the C library, the compiler's runtime, assembly. Every stack adjustment in a function is added up and direct calls are followed

For each task the tool takes the deepest chain from the entry function:

free = stack - (deepest chain + port overhead + margin)
Term Value
Port overhead What the RTOS port keeps on a task's stack besides the chain (STACK_OVERHEAD in platform.mk). STM32F4: 208 bytes, the exception frame with the FPU's lazy space and alignment (27 words) plus the context switch's r4-r11, lr and s16-s31 (25 words); interrupts then run on the main stack. HR_C7000: 68 bytes, the 17-word frame of an interrupt or a yield; handlers run on the interrupt stack and don't nest
Margin STACK_MARGIN, 128 bytes by default

A task over its stack prints OVER and its whole chain with each frame.

Pointer calls

A call through a function pointer has no target in GCC's graph. The tool reads the call site's source and works out what the pointer can hold:

Call Targets
Through a struct field, board.radio->tx(...), s->cb(...) The struct's type is followed from the variable's declaration (a parameter, a local, a file-scope or extern variable) through the members. Every function stored into that field of that type: designated or positional initializers, assignments, compound literals
Through a variable or parameter What is assigned to the variable; for a parameter, what callers pass in that position. A call through a struct field passes to the functions stored in that field, and two files' static functions of one name keep their own parameters. Stores of one pointer into another are followed
Inside a macro, LOCK() The macro is expanded first
In an argument, f(x, p->g()) GCC files it at the outer call's position; the tool looks inside the arguments

A pointer the sources store into but that never holds a function of this build is not called: an optional board_t operation the radio leaves NULL, a callback whose setter nothing in the build calls. -v lists these. A pointer with no store in sight is reported as unresolved. Unresolved calls don't fail the check, but each one could hide a deeper chain: add it to the table.

The table

tools/stack_check_edges.txt holds what the sources and the graph can't show, for every board in one file:

Line Meaning
task FUNCTION STACK A task the scan can't find (FreeRTOS' idle task: its entry is a variable)
ptr NAME TARGET... Calls through a field, variable or parameter called NAME
call FUNCTION TARGET... Every pointer call FUNCTION makes
file PATH TARGET... Pointer calls in PATH the sources don't resolve
lib FUNCTION BYTES A fixed stack for a function without call graph; also cuts the disassembly walk there
extern NAME BYTES Code outside the build, a target written @NAME (the codec)
recursion FUNCTION... Recursion known to be bounded

The AMBE+2 codec runs on the audio task's stack: 4046 bytes measured on an STM32F4 radio (codec-<id>.md), so stm32_codec_call counts 4104 with the veneer. The HR_C7000 builds call the same library by address with 4096 bytes assumed (not measured on C-SKY).

A few C library paths need arguments RadioFoundry never passes and are cut with lib lines: newlib's strstr for needles of 32 characters or more, and the floating point conversions of printf. Check the comment in the table before adding a call that breaks the assumption (a long strstr needle, %f).

Limits

  • Recursion is counted once and listed. RadioFoundry has no deep recursion; the cycles found are mutual calls through callbacks (the network stack's n_*, the audio mixer).
  • Interrupt handlers on the main stack (STM32) aren't checked: they nest, and the stack has no size of its own (it may grow down to the end of .bss). Its canary and tasks.irq_free watch it on the radio instead. Where they have a stack of their own and run one at a time (HR_C7000), the platform's STACK_IRQ names that stack (its size, or the two linker symbols at its ends so the size is the one linked) and the function that installs a handler: every function passed to it is a root, and the deepest plus the margin must fit (the irq line). A handler installed any other way is missed. The interrupt stack's canary and tasks.irq_free catch what the check misses on the radio.
  • The code before the scheduler starts (main) runs on the main stack and isn't checked.
  • A pointer call whose target is computed at run time (an address from a table the sources don't spell) needs a table line.
  • The disassembly walk adds every stack adjustment of a function, so a library function with several exit paths counts more than it uses. It doesn't see calls through registers in library code.
