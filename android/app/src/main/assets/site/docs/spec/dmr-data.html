DMR data services

Text messages, packet data answers, CSBK call alert and radio check, ARS registration and LRRP location answers on the DMR call stack; IP packets with compressed headers and confirmed delivery (11, 12). Status: built and host-tested (dmrDataServiceTest, dmrDataChainTest). On air against the SDR bench (measured): text messages, call alert and radio check, both ways, and LRRP immediate answers with and without a position (tests/hil/test_dmr_data.py); ARS not yet (docs/testing/on-air-coverage.md); IP over DMR: 11.4.

Sources: ETSI TS 102 361-1 (bursts, data headers, blocks, CRCs, CSBK), TS 102 361-2 (call alert, radio check), TS 102 361-3 V1.3.1 (packet data, responses, the IP text application of 5.7.1), the public Motorola TMS / ARS / LRRP descriptions (the formats the service already decoded), docs/spec/gotchas.md 3.6-3.9, 5, 7, 14.1.

1. Switches

All default to on with DMR (CONFIG_DMR_TMS follows CONFIG_DMR_SMS). A feature switched off is compiled out of the service (if (!CONFIG_...) guards, the linker drops what is unused); its API calls return false. With all five off nothing of the data path is built, and core/dmr/dmr_data_api.h turns into inline no-ops so UI code needs no #if.

  • The service runs only in the radio task (radio_sm_tick: dmr_call_poll, then dmrDataServiceTick every 10 ms). It never touches the modem: it hands burst lists to its host (dmrDataEnv_t.txStart) and gets the result back (dmrDataServiceTxDone). An accepted start may complete synchronously, including a modem refusal. The service marks the list running before calling the host so that completion is not lost. A start that returns false must not call dmrDataServiceTxDone.
  • dmr_data_api.h may be called from any task. Requests go into a mailbox the radio task empties at its next tick; reads are copies under the lock given to dmrDataServiceSetLock (the firmware: scheduler suspend, a few microseconds).
  • The call stack hands every burst heard on our slot whose kind is CSBK, MBC, data header, rate 1/2 / 3/4 / 1 data or USBD to the data hook. A voice call in progress is unaffected.
  • TX (dmr_call_data_tx): refused while not running, while another transmission (voice or data) is on, while PTT is held, or while a list is already given. Through a repeater it wakes the repeater first (BS activation, as for voice), then sends aligned to its timing. Direct mode: aligned to the station just heard when it was heard less than 300 ms ago (the modem keeps a reception's slot timing for 390 ms; within that window an answer stays in step with the sender), else on our own timing. Access is impolite: the service has done its own listen before talk. One burst per frame; a list ends after its last burst has gone (TX_DONE), or after 10 s plus 60 ms per burst (gotcha 3.9) with DMR_TX_ERR_TIMEOUT. A channel change or the stack stopping drops the list (REJECTED).
  • PTT pressed during a data list: the list finishes first (it is at most a few hundred ms), then the voice call starts if PTT is still held.
  • No reception while transmitting (gotcha 14.1): the modem is half duplex; the service only expects answers after its list is over. The end of a transmission (TX_DONE, or REJECTED) wakes the radio task at once (dmr_call_set_wake) rather than at its next 10 ms tick, so the board has the receiver back before an answer 30 ms after our last burst (a confirmed data ACK).

3. Receive

  • CSBKs and data headers: the service checks the CRC-CCITT with its mask (CSBK 0xA5A5, data header 0xCCCC) itself and counts disagreements with the modem's flag (data.rx_crc_flag_mismatch); its own check decides.
  • Blocks count only within 400 ms of the previous header, CSBK or block (gotcha 5.4); others are dropped (data.rx_blocks_stale). Rate 1/2, 3/4 and 1 blocks, confirmed (serial number and CRC-9 skipped) and unconfirmed; the packet's CRC-32 decides.
  • Addressed to us: our ID, or a group that is the channel's talkgroup or in its listen list.
  • Confirmed data to us gets an ETSI response (ACK with its N(S)) before anything else (gotcha 5.6); bad or lost blocks a selective ACK, a CRC-32 failure with good blocks a NACK, a repeat of the packet we ACKed last (same N(S) and data) an ACK only (12.3).
  • Text to us (any format, 5): kept in the inbox (4 messages, newest first, the oldest replaced). A TMS ACK request is answered with a TMS ACK. The same message again from the same radio within 60 s (sender, format, text; the sequence number may differ) is a retry: answered again, not kept twice (gotcha 5.8).
  • An NMEA sentence from and to UDP port 10110 (a DMR APRS position), whoever it is addressed to (usually the APRS gateway's ID), outside passthrough and not our own; a compressed header's DAID must be 0 (radio) or 2 (group), not 1 (USB network, a host behind the radio): to the host's position hook, for the APRS station list (aprs.md 8.2). The one exception to "addressed to us": nothing else looks at a packet not for us, and it gets no response. The IP gateway still gets the packet, as every other.
  • Control station passthrough (usb-network.md 5.2): IP based packets to us are left to the PC; only the ETSI response above is still sent.
  • Replies (responses, TMS ACKs, CSBK answers) wait in a 4-entry queue; one still queued after 5 s, or not started within 3 s for want of a clear channel, is dropped: the sender has given up (gotcha 5.7).

Formats (10 octets before the CRC; octets 4-6 and 7-9 are 24-bit radio IDs):

radio check request 0x80 | 0x24 0x10 (Motorola) 0x80 the checked radio the checker

  • Received call alert to us: event CALL_ALERT (the UI shows "Call alert from N"), acknowledged when the setting allows. A caller repeats until it hears the ack, so the same caller within 10 s rings once.
  • Received radio check to us: counted; answered (event RADIO_CHECK_ANSWERED) only when the setting allows.
  • Both are answered for FID 0x00 and 0x10, with the request's FID.
  • Our radio check goes with FID 0x10 (Motorola), or 0x00 with the setting radioCheckEtsi (the "ETSI form": the same opcode and octets with the ETSI FID; an assumption, no ETSI text we have names it). An answer is taken with the IDs in either order (octets 4-6 the checked radio as the Motorola answer has it, or swapped).
  • Ours (dmr_signal_call_alert, dmr_signal_radio_check): up to 3 tries, each waiting 1.5 s after the CSBK has gone for the answer; events CALL_ALERT_ACKED / RADIO_CHECK_OK or ..._FAILED. One call alert or radio check at a time.

Three formats. 5.1 Motorola TMS (CONFIG_DMR_TMS)

  • Format: IPv4 / UDP port 4007 to 4007, user data SAP 4. Ours is confirmed data where 5.1.1 needs it (below), otherwise unconfirmed. TMS header 0xE0 (ACK requested) or 0xA0, sequence number in 5 bits (with bit 7 set), encoding 4, the text as UTF-16LE (Latin-1 characters only on the radio side). Header bits as seen on air: 0x80 a sequence octet follows, 0x40 ACK requested, 0x20 set in every TMS packet, the low 5 bits the type (0 text, 0x1F ACK).
  • The TMS ACK: header 0xBF, no address, the sequence number (00 03 BF 00 0A for s/n 10; past 31 a second octet with bits 5-6, 00 04 BF 00 9E 60 for s/n 126), as a MOTOTRBO radio and BrandMeister send it. An ACK with header 0x9F (0x20 clear, seen from other MOTOTRBO gear) is still taken. Radio IDs map to 12.x.x.x, groups to 225.x.x.x (the CAI addresses; a packet from the host may carry others, 11.1).
  • Ours (sms_send): rate 1/2 blocks (gotcha 5.3), 16 preamble CSBKs (12.6.4). Individual with an ACK requested, and the confirmed IP setting not off: confirmed data through the IP packet slot (12), as a MOTOTRBO radio sends it. The link ACK alone doesn't end it: then it waits 8 s for the TMS ACK with our sequence number, 2 tries, then SMS_FAILED. No link ACK after the confirmed tries: SMS_FAILED. The TMS ACK without the link ACK (that one lost) ends it too, and its retries. With the setting off, the same 8 s and 2 tries unconfirmed. To a group or without an ACK: unconfirmed, SMS_SENT once on air.
  • Our TMS ACK: confirmed data when the confirmed IP setting is not off and the IP packet slot is free (BrandMeister ignores an unconfirmed one, 5.1.1), otherwise unconfirmed; 16 preamble CSBKs either way. After a link ACK of ours (the message came confirmed) it waits TMS_ACK_GAP_MS (1.5 s) after that transmission ends.
  • The UDP header of our confirmed TMS and TMS ACK is compressed (SAP 3, 11) only with UDP compression set to all; port 4007 is an application port, so auto keeps SAP 4. BrandMeister takes both compressed (5.1.1), and so did the MOTOTRBO radio of 12.9. Whether every MOTOTRBO radio does, or only with compressed UDP headers enabled in its codeplug, is not known, so auto stays the default. One message at a time, at most 140 characters.
  • Built without CONFIG_DMR_TMS (the TMS builder, decoder and ACK are left out): a TMS heard is not decoded, so it is neither kept nor acknowledged; as confirmed data it still gets its ETSI response (3), and the IP gateway still forwards it to the PC like any datagram. sms_send(..., TMS) is refused; a stored default of TMS (a record written by a build with it) sends ETSI IP text instead. The UI's format list has no Motorola entry. Host test: dmrDataServiceTestNoTms.

5.2 ETSI short data text

  • Format (defined short data, the DD_HEAD PDU of TS 102 361-1 V2.7.1 Figure 8.9 and 9.2.12): data header with DPF 13 (octet 0 bits 3:0), SAP 10 (octet 1 bits 7:4), the blocks to follow in octet 0 bits 5:4 and octet 1 bits 3:0, octet 0 bit 7 group, bit 6 response requested; octet 8 the defined data format in bits 7:2 (bit 1 S, bit 0 F: one complete message), octet 9 the bit padding; CRC-CCITT masked 0xCCCC. Rate 1/2 blocks follow, the last ending with the CRC-32 (B.3.9, least significant octet first).
  • DD formats read (dmrData.h): 0x02 7-bit (ISO/IEC 646, packed, the bit padding gives the length), 0x03-0x11 ISO 8859-x (all read as 8859-1), 0x12 UTF-8, 0x13 UTF-16 (with a byte order mark; big endian without one), 0x14 UTF-16BE, 0x15 UTF-16LE; characters outside Latin-1 become '?'. Binary and BCD are not text: counted, not shown. The codes are TS 102 361-1 V2.7.1 Table 9.50 (9.3.38); the bit padding is 9.3.44. A host test holds one message computed from those clauses apart from this code (dmrDataChainTest, "ETSI TXT 541"); a commercial radio is still to be tried (open point). HIL 2026-10-10: the bench tool sent ISO 8859-1 text marked 0x02 (its bug, fixed), and the radio showed it, correctly for that code, as 7-bit characters.
  • Also read: UDT text (TS 102 361-4, UDT header formats 3 ISO 7-bit, 4 ISO 8-bit, 7 UTF-16BE; CRC-CCITT unmasked, the pad nibbles in octet 8).
  • Received to us: into the inbox with format ETSI (dmrDataMessage_t.format); with the response bit set the ETSI response (ACK: class 0, type 1, SAP 10) goes back. Duplicates: the same source, format and text within the TMS window.
  • Ours: ISO 8859-1, response requested when individual (ack), 16 preamble CSBKs (12.6.4). Done (SMS_SENT) when the response ACK from the destination arrives, waiting 4 s per try, 2 tries, then SMS_FAILED (a NACK response is not acted on: the message fails when the tries run out). To a group: SMS_SENT once on air.

5.3 ETSI IP text

TS 102 361-3 V1.3.1 5.7.1: text messaging over the IP bearer uses UTF-16BE (plane 0) on the default UDP port 5016. The compressed UDP/IPv4 header (5.6, 7.2.4) has a port index for it: SPID / DPID 1 = 5016 (Table 7.17 / 7.18).

  • Ours (dmrDataBuildIPText, dmrDataIPTextUDP): the text as UTF-16BE (Latin-1 on the radio side: one code unit per character, no byte order mark, no terminator), UDP from and to port 5016, the full IPv4 / UDP header with the 12.x.y.z / 225.x.y.z addresses of 5.1, SAP 4, rate 1/2, at most 140 characters. Always the full header, not the compressed one (SAP 3), whatever the compression setting (11): every receiver of the IP bearer reads SAP 4, the compression is an option a receiver may lack.
  • 5.7.1 defines no acknowledgment of its own, so an individual message goes as confirmed data (12: C_HEAD with N(S), the IP packet machinery's tries and response wait), and the ETSI response ACK from the destination completes it (SMS_SENT, the UI says "Delivered to", sms_send_confirmed() true); no response after the tries, or a NACK that ends the packet: SMS_FAILED. It shares the service's one IP packet slot with the gateway (one at a time; the gateway's packet waits, as for any busy slot). Unconfirmed, done once on air ("Sent to"): to a group, and with the confirmed IP setting off (ip.confirmed off).
  • Received (SAP 4 or SAP 3, destination port 5016): the payload decoded as UTF-16BE (dmrDataDecodeIPText; a byte order mark first is honored, either way), into the inbox with format ETSI_IP. No reply of its own; confirmed data gets its ETSI response (3). Duplicates as in 5.2.
  • Through the IP gateway the PC sends and receives the same datagrams on UDP 5016 (usb-network.md 5).

5.4 The default: ETSI IP text

The default for messages the radio sends is ETSI IP text. Why this one of the two ETSI forms:

  • It is the text application TS 102 361-3 defines (5.7.1). Defined short data (5.2) is a bearer with a character set code; no ETSI clause defines a text messaging service around it, and receivers differ in which DD formats they show (open point in 5.2).
  • It rides the IP bearer, which any radio that takes packet data decodes for its other services too (location, registration, the vendor text formats): a full IPv4 / UDP header on SAP 4. A receiver needs no DPF 13 header support, only the UDP port and UTF-16 text. Radios and dispatch software that do ETSI text over IP read it; radios configured for "DMR standard" text in their CPS are expected to (to confirm on air, open point).
  • Individual messages go as confirmed data, so the standard's ETSI response confirms delivery (5.3); group messages are sent once and nothing waits for an answer.

Defined short data stays available (Settings > Connections > Message format: "ETSI short") for radios that only show that form, and it confirms delivery. Motorola TMS ("Motorola") is the format for MOTOTRBO fleets.

6. ARS

  • Off until a server ID is set (dmrDataSettings_t.arsServer). Then: registers 5-15 s after power-up (spread by our ID so radios powered together don't collide), and again when the channel (frequency, slot, color code), our ID or the server has been unchanged for 5 s.
  • Unacknowledged or refused: retried 5 times, 30 s apart and doubling; the state shows no_answer or refused meanwhile and after the last try, until something changes.
  • Registered: again after the refresh time the server's answer gives (never when it says 0), else every 30 min.
  • Power-off deregistration: dmrDataServicePowerOff() sends it and returns true until it has gone (gotcha 7.4). The power-off path calls it through the radio core: radio_req_power_off() (RREQ_POWER_OFF), then core/app/app.c waits while radio_power_off_busy(), at most 3 s, before the settings flush and the latch.

7. LRRP

  • Immediate location requests to us are answered; triggered requests (periodic, distance) start a trigger (2 at most, reports at most every 5 s) with a start response, then reports.
  • The position is the position service's (position.md), through the ownPosition hook the radio core sets (position_report: the board GPS, the host's NMEA or the fixed position, ambiguity applied). It needs no APRS and no GPS receiver: CONFIG_DMR_LRRP builds the service, and hasGps is set in every such build.
  • While there is no position (no fix and no fixed position) an immediate request is answered with result 0x10 (no fix). A triggered request starts its trigger; a report due without a position is skipped.
  • Built without a position source (hasGps false: a platform that sets no hook) every immediate request is answered with result 0x10 (no fix) and a triggered request is refused with 0x10: no trigger is started, so nothing is sent later on its behalf.
  • lrrpReply off: requests are counted, not answered.
  • Positions elsewhere: the ETSI GPS Info LC in voice calls is in dmr-voice.md 3.1, positions to an APRS gateway ID (LRRP triggered report or UDT location) in aprs.md 8. All of them read the same position.
  • Not ported: the UDT location reports and the GPS power management (dmrDataServiceLocationNeededInMs exists for it).

11. Compressed UDP/IPv4 headers on transmit (SAP 3)

Source: ETSI TS 102 361-3 V1.3.1 5.6 and 7.2. Receive was already built (dmrDataGetUDP, the gateway delivers SAP 3 as UDP); transmit is CONFIG_DMR_UDP_COMPRESS.

11.1 Format

The packet is an ordinary data packet with SAP 3 in its header; the first data block starts with the compressed header (Table 7.14), the UDP payload follows:

Octets Field Ours
0-1 IPv4 identification the same counter as our SAP 4 packets; a confirmed retry keeps it
2 SAID (7-4), DAID (3-0) SAID 0 (radio network: the source is the source LLID), DAID 0, or 2 (group network) for a talkgroup
3 opcode MSB (7), SPID (6-0) opcode 00 (the only format defined); SPID 1 = 5016 (UTF-16BE text), 2 = 5017 (LIP), 98 = 4007 (TMS, the manufacturer specific ID MOTOTRBO uses: an over the air capture, dmrDataTest), 0 = in an extended header
4 opcode LSB (7), DPID (6-0) the same for the destination port
5-6 extended header 1 the source port when SPID is 0, else the destination port when DPID is 0
7-8 extended header 2 the destination port when both are 0

Not sent, rebuilt by the receiver: version, IHL 5, TOS 0, total length, flags 0, fragment offset 0, TTL (64, a talkgroup 1), protocol 17, both checksums, the UDP length (from the packet length), and both addresses: the source ID's 12.x.y.z and the destination ID's 12.x.y.z or, for a talkgroup, 225.x.y.z (the ID's 24 bits under the CAI network octet).

IPv4 addresses are carried apart from the DMR IDs (dmrDataEncodeIP, dmrDataServiceSendIP, ipGatewayIPToAir take a source and a destination address and a TTL). The radio's own packets (TMS, ARS, LRRP, text, SNMP answers) use the IDs' addresses, so their bytes are as before. A packet from the host may not: the off-net route sends to a gateway radio's ID with the real destination address (usb-network.md 3.1). So a UDP packet goes compressed only when both of its addresses are exactly the IDs' CAI addresses; any other goes with the full header, whatever udpCompress says. dmrDataGetIP and dmrDataGetUDP return the addresses: from the header for SAP 4, rebuilt from the IDs for SAP 3. On receive a packet is for an ID itself only when its IP destination is exactly the ID's CAI address: an off-net host's address may have the same 24 bits under another first octet. A packet to our DMR ID for another address is passed to the gateway only, never answered by our own services (TMS, ARS, LRRP, text, SNMP).

TTL: a radio's packets go with 64, the host's keep the host's TTL, less 1 on the off-net route. A talkgroup's always go with 1, whatever the host asked: the air is the group's one hop, and a gateway that hears one must not route it on. dmrDataGetIP and dmrDataGetUDP return the TTL: the header's for SAP 4, the sender's default for SAP 3.

The compressed header has no length field, so a datagram goes compressed only when its UDP length agrees with what we have (octets past a shorter UDP length are padding and dropped; a longer one goes with the full header). IP options never reach the air: the gateway strips them for SAP 4 too, so the rule that options need the full header holds. Receive takes opcode 00 only (others are reserved) and SPID / DPID 1, 2, 98; an unknown ID is reported as 0x8000 | ID.

11.2 When (the setting udpCompress)

Value UDP packets sent compressed
off none
auto (default) those whose ports are both outside 4000-4099
all every one, TMS / ARS / LRRP included

The mode decides by the ports only. A packet whose addresses are not its IDs' CAI addresses (11.1) goes with the full header in every mode, all included.

It applies to every UDP packet the radio builds: the gateway's datagrams from the host (dmrDataServiceSendIP) and the service's own (dmrDataBuildUDP: TMS, TMS ACK, ARS, LRRP, dmrDataServiceSendUDP, digital APRS). ICMP and SCTP always go as SAP 4.

Why auto: the receive side of SAP 3 is in the standard every DMR packet data radio implements, and ours reads it, so traffic between our radios and anything new the host sends gains the 19-23 octets. The DMR application ports 4000-4099 are where MOTOTRBO presence, text and location servers listen; whether a given control station or server decompresses depends on its configuration ("compressed UDP data header" in MOTOTRBO CPS), and our TMS / ARS / LRRP worked with the full header before, so auto leaves them as they were. all is for a fleet known to take SAP 3 (the capture above shows MOTOTRBO sending TMS that way).

12. Confirmed data

Source: ETSI TS 102 361-1 V2.7.1 8.2.1.2, 8.2.2.2-8.2.2.4, 9.2.1, 9.3.20-9.3.27, B.3.10, B.21; TS 102 361-3 V1.3.1 5.4 (stop and wait), Annex A. Part of the data core: no switch of its own, since texts to BrandMeister and MOTOTRBO radios need it (5.1.1).

12.1 What already existed

Receive: confirmed packets to us were reassembled (serial number and CRC-9 skipped, the CRC-32 deciding) and ACKed with their N(S) (3). TMS, ARS and LRRP send unconfirmed with their own application ACKs and retries (5, 6, 7); nothing sent confirmed data. The new code reuses the response builder (now dmrDataBuildResponse: ACK, NACK, selective ACK), the reply queue and its 5 s age limit, and the service's TX list and listen before talk.

12.2 Ours (dmrDataServiceSendIP)

  • Packet: C_HEAD (DPF 3, individual, A set, the pad octet count, SAP 3 or 4, F set on the first try, the blocks in this transmission, S clear, N(S), FSN 1000 single fragment), then the blocks: octet 0 the 7-bit serial number and the CRC-9's MSB, octet 1 its other 8 bits, 16 data octets (rate 3/4, 12.9); the last block ends with the CRC-32 of all data octets (pad included). CRC-9 (B.3.10): the block's data octets then the 7 serial bits, x^9 M(x) mod x^9 + x^6 + x^4 + x^3 + 1, inverted, then masked with the rate's mask (0x0F0 rate 1/2, 0x1FF rate 3/4, 0x10F rate 1). At most 64 blocks (one selective ACK block) and the 64-burst list: every packet of the air MTU (596 octets, 38 blocks at rate 3/4, 12.8) goes confirmed. A packet too long for it would go unconfirmed (ip.cnf_too_long); none is.
  • In direct mode the transmission ends with the Data Terminator LC (FLCO 0x30; octet 8: G/I, A, F, S, N(S)) that opens the receiver's response window (TS 102 361-3 5.4.1); through a repeater nothing follows the last block.
  • Then it waits DMR_IPC_RESPONSE_MS (3 s) after the list has gone for a response from the destination with the packet's SAP. The standard recommends 180 ms (2 s on simulcast); ours is longer because our own receiver answers after its listen before talk (120 ms) and a repeater wake-up, and through a hotspot the answer comes from a network service: BrandMeister's link ACK reached the radio after a 1.5 s wait 4 times of 4 (5.1.1).
  • An ACK with our N(S) is also taken before the stack has reported our list done (a fast answer, such as BrandMeister's through a hotspot, can come first: 5.1.1) and while the next try is queued (its retry dropped). A selective ACK or NACK then is not: the try under way answers for it.
  • ACK (class 0, type 1) with our N(S): done; the next packet to that radio takes N(S) + 1 (mod 8).
  • Selective ACK (class 2, type 0): the blocks whose flag is 0 again, with the same N(S) and POC and F clear; flags all 1: done.
  • NACK class 1 type 5 (N(S) out of sequence, status = the receiver's VI): the packet again as N(S) = VI + 1, a first try. Type 4 (undeliverable) and 6 (not allowed): failed at once. Other NACKs (format, CRC, memory full): the whole packet again, F clear.
  • No response in time: as a NACK (TS 102 361-3 5.4.3.1.3), the whole packet again, F clear.
  • ipConfirmedTries transmissions in all (default 4: the first and 3 retries; N_RtryLmt recommends at most 8), then failed. A packet that finds no clear channel we may send on within 10 s fails too.
  • N(S) per destination: the last 4 radios; a radio not in the table starts at a number from the clock, so a receiver still holding our number from before a restart doesn't take the first packet as a duplicate (a strict receiver's out of sequence NACK resynchronizes either way).
  • The gateway's packets and zone sharing's go through one TX queue (12.6). A confirmed packet is always alone in its transmission and the next waits for its end; unconfirmed packets to the same destination share one (12.6.2).

12.3 Confirmed data to us

  • Each block's CRC-9 is checked; a good one is placed by its serial number. A bad one is kept in arrival order on a first try (the CRC-32 may still pass: then it is counted in ip.rx_crc9_mismatch, a sign our CRC-9 disagrees with the sender's) and dropped in a selective retry (its serial number can't be trusted).
  • The CRC-32 decides once every block has a place. A failure with blocks bad or missing: a selective ACK with their flags 0 (ip.rx_sacks_sent); the blocks stay held for the retry (F clear, same source, destination, SAP and N(S)). Every block good and the CRC-32 wrong: a NACK (class 1 type 1, ip.rx_nacks_sent). Blocks that stop coming before the header's count (lost bursts): the selective ACK 300 ms after the last one.
  • A selective retry for a packet we don't hold (another packet came between): a NACK, so the sender sends it whole.
  • The packet again with the N(S) and the data (a 16-bit fold of its CRC-32) we ACKed last from that radio, within 20 s of the last copy: ACKed, not passed on (ip.rx_duplicates). The standard keys on N(S) alone; BrandMeister sends N(S) 0 on every packet, so other data with the same N(S) is a new packet. Any other N(S) is taken as new (no out of sequence NACK: senders restart their numbers).

12.6.2 Chaining

ETSI DMR doesn't need a gap between data packets: each has its own data header, and a receiver syncs on it.

  • When the oldest queued packet is an IP packet, the queue offers it together with the IP packets right after it to the same destination and call type, with the same IP addresses and TTL (dmrDataServiceSendIPChain; the gateway's off-net packets carry their own, 11.1). Anything else stops the chain, so the order stays.
  • The service takes the first as usual. If it goes unconfirmed, the service adds the following ones that also go unconfirmed, up to 8 packets and the 64-burst list (gotchas.md 5.5). What doesn't fit goes in the next transmission. The list is counted with each packet's own header: a full IPv4 header (SAP 4) takes more blocks than a compressed one.
  • Confirmed packets are never chained: a confirmed first goes alone, and a confirmed packet after it ends the chain and waits its turn.
  • On air: the preamble CSBKs once, then each packet's data header and blocks in order. Unconfirmed packets have no data terminator (TS 102 361-3 5.4 defines the Terminator Data LC only after confirmed data in direct mode, to open the response window), so a chain ends after its last block, like a single unconfirmed packet.
  • The preamble count: TS 102 361-2 7.1.2.5 and 7.2.7 define the Pre_CSBK. Its CSBK Blocks to Follow is "the number of Preamble CSBK PDUs and either the following CSBK or data message that will be sent", not counting the CSBK itself. TS 102 361-1 and -3 don't define the preamble. Each data header's Blocks to Follow (TS 102 361-1 9.3.21) counts its own packet's blocks only. Ours: each preamble counts the preambles after it plus every burst of the chain, so a scanning or sleeping receiver that trusts the count stays for the whole transmission (dmrDataBuildPreambles).
  • One transmission, one result: every packet in it ends sent or failed together.
  • A transmission stays within the stack's TX deadline (gotchas.md 3.9), which grows with the list.
  • Receive needs nothing new: a data header resets the receiver, also right after the previous packet's last block (dmrDataRxBurst).

12.6.3 The guard

Between separate transmissions the service waits CONFIG_DMR_DATA_TX_GUARD_MS (default 250 ms) after our own transmission ended before it starts another that isn't a reply. Replies (ETSI responses, CSBK answers) are not held: the sender waits for them. The end is stamped at the first tick after the stack reports it, never before the real end. Lists held back are counted (data.tx_guarded).

The guard is a workaround. On the SDR bench, #154 found receivers lost the second of two packets sent as separate transmissions with no gap, with data.rx_blocks_stale on the receiver: it never saw the second transmission's preamble CSBKs or header. The cause is not known. Candidates: our own re-key (the transmitter's ramp), or the receiving modem's end-of-call state (200-400 ms, gotchas.md 3.6). 250 ms was enough in every trial. Chaining avoids the re-key for packets that can share a transmission.

For finding the cause, the debug link's DMR_DATA op 11 TX_SPACING sets the guard and turns chaining off in RAM (rfoundry_debug.py data tx-spacing MS [chain|no-chain]). tests/hil/test_dmr_tx_spacing.py (opt-in RF) measures delivery chained, separate with no gap, and separate with 250 ms.

12.6.4 Preamble count

A text or IP packet of ours goes with DMR_DATA_TX_PREAMBLES (16) preamble CSBKs where the burst list has room for them, fewer for the longest packets, never fewer than DMR_DATA_IP_PREAMBLES (2, what the air MTU counts on, 12.8). A confirmed packet of the air MTU gets 2. Each try sends them again. ACKs, ETSI responses and CSBK answers keep their own counts. The service builds the packet with 2, then moves its bursts up and rebuilds the preambles (widenPreambles), so no buffer grows.

Why 16: BrandMeister didn't answer data with 1 or 2 preambles (10 sends in a row) and answered the same packet with 15 or 16, the count MOTOTRBO radios send (5.1.1). The standard sets no count (TS 102 361-2 7.1.2.5). The cost is 0.84 s more on air per try; the waits for the link ACK and the TMS ACK start when the transmission ends, so they don't shrink.

12.7 Open

  • A MOTOTRBO radio refuses our rate 1/2 confirmed packets (12.9), whatever their blocks hold. Whether other firmware versions do is not known.
  • The sliding window (TS 102 361-3 5.4.4) is not used.
  • Fragmentation (FSN chains) is not built: one packet per datagram, so a datagram longer than the air MTU (12.8) doesn't go. The gateway drops IP fragments from the host too (usb-network.md 3.2).

12.8 The air MTU

The longest IP datagram we send in one transmission. It is not below the USB link's MTU (586, usb-network.md 3.2), so every packet a host sends to the air fits one transmission, confirmed or not. core/dmr/dmrData.h sizes the burst list and the packet buffer for it:

Constant Value From
DMR_DATA_MAX_PACKET 612 the packet buffer: 51 rate 1/2 blocks
DMR_DATA_IP_MTU 596 60 rate 1/2 confirmed blocks of 10 octets less the 4-octet CRC-32 (612 - 16), when confirmed data went at rate 1/2; unconfirmed, 51 blocks would carry 608
DMR_DATA_IP_PREAMBLES 2 the fewest preamble CSBKs before an IP packet (also SMS); 16 where they fit (12.6.4)
DMR_DATA_MAX_BURSTS 64 the burst list of one transmission: 16 preambles where they fit (12.6.4) and a packet of 596 octets
A packet of 596 octets Blocks Bursts Air time (60 ms a burst)
Unconfirmed, rate 1/2 (12 octets a block) 50 2 + 1 + 50 = 53 about 3.2 s
Confirmed, rate 3/4 (16 octets a block) 38 2 + 1 + 38 + the terminator = 42 about 2.5 s
  • The MTU counts the user data on air: the IP and UDP header as sent (SAP 4: 28 octets; SAP 3: 5, 7 or 9, 11.1) plus the payload. The largest UDP payload is 568 octets with the full header and up to 587 with the compressed one (9 octets: ports outside 4000-4099 in the extended headers). A raw port packet (no header) carries up to 596 through the gateway, the air MTU (the encoder itself takes 608).
  • Confirmed (12.2) takes every packet of the MTU: 38 blocks, under the 64 of one selective ACK block. Longer packets are refused (DMR_REQ_FAILED, ip.failed), nothing goes on air. Build-time asserts in dmrData.c, dmrDataService.c and ipGateway.c keep the four constants and the link MTU in step.
  • The gateway still checks each host packet against the air MTU before the air queue, with the header it will get (ipGatewayAirLength). On the radio none is too long; the check and its ICMP fragmentation needed answer are covered by a host test built with a narrower air (ipGatewayTestAir440; usb-network.md 3.2).
  • Receiving: the receiver reassembles up to DMR_DATA_MAX_PACKET (51 blocks, 608 octets of user data unconfirmed) from other radios. A longer packet ends in a receive error (data.rx_crc_errors) and nothing is delivered. The gateway passes the host what fits its link (586 octets of IPv4); a longer packet, from a radio that sends more than we do, is dropped and counted (net.up_too_big).
  • Keyed time: the stack's TX deadline grows with the list (10 s + 60 ms a burst, gotchas.md 3.9), so a 64-burst list has about 13.8 s. The guard (12.6.3) is per transmission and doesn't change.
  • RAM: one list of 64 bursts (27 octets each, 1,728) in the data service. The air queue builds raw packets in it (dmrDataServiceSendShortData) instead of a list of its own; the hotspot keeps its own list (it runs in the host link's task), placed outside the CPU-only RAM where a board has one. The packet buffers (txPacket, ipPacket, dmrDataRxPacket) are 612 octets each.
  • Not done, follow-up: fragmentation (12.7: a lost burst loses the whole datagram, and a receiver that misses one fragment drops the rest).

12.9 Rates with a MOTOTRBO radio

TMS from our radio to a MOTOTRBO portable on a simplex channel (direct mode), 1 W, each rate confirmed and unconfirmed, each with the full UDP header (SAP 4) and the compressed one (SAP 3). Delivered = the text shown on the portable (confirmed: also its TMS ACK back). Each failing case was sent at least 8 times, the others at least once.

Rate Confirmed Unconfirmed
3/4 delivered not delivered (0 of 8)
1/2 not delivered (0 of 16) delivered
1 delivered delivered

  • SAP 3 and SAP 4 behave the same in every case.

  • The portable sends confirmed data at rate 3/4 and unconfirmed at rate 1/2; BrandMeister sends confirmed at rate 3/4 (5.1.1). We send the same: IP packets confirmed at rate 3/4, unconfirmed at rate 1/2 (IP_CONFIRMED_RATE, IP_UNCONFIRMED_RATE in dmrDataService.c). Text and other packets outside the IP path stay at rate 1/2. A modem that can't send rate 3/4 blocks a receiver decodes (hal_dmr_modem_t.tx_rate34_bad) sends confirmed IP at rate 1/2 instead, which a receiver decodes but this portable refuses (below). The debug link can set either rate for the bench (data.ip_cnf_rate, debuglink.md 3.12 op 12).

  • Rate 1/2 confirmed: the portable answers the first try with a NACK (class 1, type 1, packet CRC failed), each retry with a selective ACK that has only block 0. Our blocks follow B.3.9 and B.3.10, and both CRCs, computed the same way, check on the portable's own rate 3/4 blocks. 14 other block forms got the same answer, block 0 always taken:

    Changed Forms
    CRC-9 serial number least significant bit first; serial number before the data; serial number 0 in every block; the 2006 edition's form (serial number first, no mask); a wrong CRC-9 on block 0
    Octet 0 the CRC-9's MSB and the serial number swapped
    Block 12 octets with no serial number or CRC-9
    CRC-32 the 2006 edition's form (no octet-pair swap, inverted, most significant octet first); without the swap only; over each block's serial number and CRC-9 octets too

    Block 0 taken with a wrong CRC-9 means the portable doesn't check the blocks at this rate. Rate 1/2 confirmed has been in the standard since V1.2.1 (2006), and the portable never sends it itself: likely its firmware.

  • Rate 3/4 unconfirmed: nothing comes back (none is due), and the portable shows nothing.

  • One portable on one firmware version: more radios and versions are needed before calling this MOTOTRBO behavior.

  • The portable's link response comes in the next frame in our timeslot: its first burst starts 60 ms after our data terminator's start, about 29 ms after the terminator's end (measured off air). A radio still switching back from transmit misses it: one that returned to receive only from the radio task decoded it 1 time in about 30 (a receive CRC error instead); returning at the slot engine's TX done, 4 of 4 on the first try. Radios whose burst switch already puts the receiver back after each burst missed it too (0 of 16 each), because the radio task's rx() at the end of the transmission set the receiver up again (idle, synthesizer, receive) just as it came. The modem glue now keeps a back-to-receive flag, and the end of the transmission leaves the receiver as it is on the same channel (dmr-modem.md 6.4): 4 of 4 on the first try on each of five radios, on both glues.

  • Before the glue flag and the TX-done wake, with two of the three HR_C7000 radios tried, the portable sent its TMS ACK a second time 2.5 s later on most sends (9 of 10): it missed our link ACK to the first. With both, one of the two got a single TMS ACK on 8 sends of 8, and a third radio listening decoded our link ACK every time.

13. Privacy

The channel's privacy key (CONFIG_DMR_PRIVACY, dmr-voice.md 5) covers packet data too. Each scheme in core/dmr/dmrPrivacy.c says what it does with data; the data layer (dmrData.c, dmrDataService.c) gets a descriptor (dmrDataPrivacy_t: mode, algorithm ID, crypt callback) and never tests a scheme. A new scheme is a table entry.

Scheme Data
Off, or no valid key clear
Motorola BP encrypted: privacy header, algorithm 0
Anytone BP no data form: every data list is refused

13.1 Privacy header

A data header with DPF 15 right after the first data header (dmrDataBuild* add it; it counts in the first header's blocks to follow):

Octet Content
0 SAP << 4 | 0xF
1 MFID 0x10
2 algorithm (bits 6-4: 0 BP, 1 RC4, 2 DES, 4 AES-128, 5 AES-256), encrypted 1 (bits 3-0)
3 key ID (0 for BP)
4-5 0
6-9 MI, big-endian (0 for BP)
10-11 CRC-CCITT, mask 0xCC

We send the real SAP in the first header. On RX a first header with SAP 9 takes the user data's SAP from the privacy header. A header with MFID 0x10 and SAP 1 is not a privacy header.

13.2 BP keystream

The key (1-255) selects a 16-bit word from the BP key table. The word repeats over the user data octets, high octet first, from octet 0 of the packet's user data (the IP datagram or the compressed header and payload). There is no MI and no restart per block. Pad octets and the CRC-32 stay clear. The CRC-32, and the CRC-9 of each confirmed block, are computed over the ciphertext, so a receiver without the key still checks and acknowledges the packet.

13.3 What is refused, what is dropped

  • TX: queueTx is the one place every list passes (dmrDataPrivacyAllows). With an encrypting scheme every data header except responses and proprietary headers must be followed by a privacy header. With a blocking scheme any data header is refused. ETSI defined short data (5.2) has no privacy header, so it is refused under an encrypting scheme. CSBKs (call alert, radio check, emergency alarm) and responses still go. A refused SMS fails at once; other requests fail or time out as when the channel is busy.
  • Confirmed IP sends one preamble fewer with the privacy header, so the air MTU (12.8) still fits in 64 bursts.
  • RX: a packet with a privacy header is decrypted when the key's scheme takes its algorithm. Otherwise (no key, an MI-based algorithm) it is dropped and never shown; confirmed data is still acknowledged. A wrong BP key gives garbage that the IP checks drop.
  • Counters (debug link section 8): data.privacy_rx (decrypted), data.privacy_rx_dropped, data.privacy_tx (lists sent encrypted), data.privacy_blocked (lists refused).

13.4 Open

  • Not yet checked against a commercial portable on air: whether its first header carries SAP 9 or the real SAP, and octets 4-5.
  • Talker alias and the embedded LC are still sent in the clear.
