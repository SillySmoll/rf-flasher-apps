TYT MD-380 hardware (MD-390, Retevis RT3, and the "G" GPS models)

The TYT MD-380, the MD-390 (the same board in an IP67 case) and the Retevis RT3 are one board family: an STM32F405VGT6 MCU, an HR_C5000 DMR baseband and codec chip, no RF transceiver chip but a Skyworks SKY72310 fractional-N synthesizer, separate receive and transmit VCOs, a GT3136 FM IF receiver, a discrete PA with an analog power loop, a 160 x 128 color LCD on the FSMC 8-bit bus, a SPI NOR flash, a 3-row keypad matrix sharing its columns with the LCD data bus, a 16-position channel switch, an analog volume knob with the power switch, and USB full speed on the MCU's OTG_FS core. Each radio is single band, UHF or VHF. The "G" models (MD-380G, MD-390G, RT3 GPS) add a GPS module on a UART.

Conventions: register values are hex. HR_C5000 registers are written as reg = value on its configuration page (page 0; the driver keeps the HR_C6000's page numbers and maps them, section 4.3). SKY72310 registers are its 4-bit addresses. A value is marked (unverified) where no datasheet and no measurement on a radio confirms it. md380-bringup.md is the order in which a radio confirms or corrects the open facts, and section 17 lists every open question.

1. MCU, clocks, memory

1.1 Part

STM32F405VGT6, LQFP100: Cortex-M4F, 1 MB flash, 192 KB RAM (128 KB SRAM, 64 KB CCM). Read-out protection level 1 on production radios (unverified).

1.2 Clocks

8 MHz crystal on HSE (unverified). RadioFoundry runs the DM-1701's clock plan: PLL M 4, N 72, P 2 (72 MHz SYSCLK), Q 3 (48 MHz USB), AHB 72 MHz, APB1 36 MHz, APB2 72 MHz; If HSE does not start as a crystal, board_early_init retries it in bypass mode (the DM-1701 needed bypass) before staying on HSI. LSE: a 32.768 kHz crystal is assumed (unverified).

128 KB SRAM for data and every DMA buffer (minus 4 bytes at the top, as the DM-1701 keeps them for the boot request word); 64 KB CCM for CPU-only state (RFOUNDRY_CPU_RAM: the task stacks and the slot engine, as on the DM-1701, a76da0d; main RAM use went from 89 % to 68 % of the default build with that move).

2.6 Reset-time levels and the SWD pins

board_early_init sets, before anything slow: the power latch (PA7) high; the HR_C5000 chip select and power down high and its clock low; the SKY72310 clock high; the SKY72310 chip select high; the transmitter supply, APC loop and receiver supply low and VCO select high (the receive VCO); DMR_SW high; speaker muted, amplifier off, FM muted; LEDs off; keypad rows low; the flash chip select high. PD8 and PD9 are left as inputs (section 13). These are safe choices (unverified).

Transmitter safe state (board_rf_safe, crash-log.md 8), at every fault, reset and stub entry and first in main(): APC_EN (PC4) and 5TC (PC5) low, VCO_SEL (PA9) high (the receive VCO), the APC DAC (PA4, DAC1 channel 1) 0 when its clock is on. The SKY72310 and HR_C5000 keep their state until the next start.

PA13 and PA14 are the SWD pins. The radio needs them as the IF bandwidth switch and the microphone supply, so radio_md380.c takes them over at radio init; a debugger then has to connect under reset. Build with MD380_DEFS=-DMD380_KEEP_SWD to leave them alone: the microphone is then unpowered and the bandwidth switch stays as the hardware pulls it.

4. HR_C5000

4.1 Overview

The HR_C5000 is the HR_C6000's predecessor in the same family: DMR layer 1/2 baseband, two-point modulation outputs, an IF input from the receiver, and an audio codec with I2S. RadioFoundry has a driver of its own for it, drivers/modem/hrc5000, which shares only the chip-independent code (drivers/modem/hrc_common: the bus accessors and the DMR slot engine) with the HR_C6000 driver. The shared engine reaches the chip through a description struct (hrc_chip_t); the MD-380 build links no HR_C6000 code. The HR_C5000 user manual (HR_C5000 用户手册 V2.0, Chinese, 35 pages, datasheets/C5000/hrc5000.pdf) is the source for the register names and reset values in 4.6. It has no register map for 0x25, 0x26, 0x37, 0x39, 0x3D, 0x41, 0x45, 0x47, 0x48 or 0xB9-0xBB; those values are (unverified) until a radio confirms them.

4.2 Configuration port and the synthesizer bus

Bit-banged SPI on PE2 (CS), PC13 (clock), PE5 (MCU -> chip) and PE3 (chip -> MCU) bench. Unlike the HR_C6000 on the DM-1701, the clock idles LOW. Per bit: clock high, set MOSI, clock low (the chip samples MOSI on this falling edge), waits, then samples MISO. The chip drives the next MISO bit only after the falling edge: sampled at once, every read comes one bit late (0x10 read back 0x40 after 0x80 was written, and the LC 00 00 00 00 00 63 30 5A 5E read 80 00 00 00 00 31 98 2D 2F) on air 2026-10-18. Register reads in logs taken before that fix (issue 3, issue 66, up to 2026-10-18) are shifted right by one bit. On any other pin choice every read returned 0xFF. A transaction is 3 bytes for a register write (page, register, value) and 2 bytes plus the data for a read (0x80 | page, register), with CS low around the whole frame. A few cycles per half bit is enough; speed is not a constraint.

The SKY72310 has its own clock (PE4) and chip select (PD11); only the data line (PE5) is shared with the HR_C5000 bench. Its clock idles high: the MCU sets the data bit while the clock is high, drops the clock, raises it again, and the chip latches the bit on the rising edge. Because PE5 is shared, a transaction on either chip is one masked section (md380_rfbus_lock), so a modem ISR's register access never lands inside a synthesizer word or the reverse.

4.4 Voice port

Hardware SPI2 (PB13-PB15, AF5) with chip select PB12, commands 0x03 (write) and 0x83 (read) followed by 0x00 and 27 bytes (one voice burst's payload) bench. RadioFoundry uses SPI mode 2 at 1.125 MHz on air 2026-10-18. At 4.5 MHz transmit voice decodes on another radio, but received voice reads back with the first bits of every byte wrong: the C0 words check only two bits off their place and C1 never does. At 1.125 MHz the three frames are in place and C1 checks too; the first data byte after the command still has a few bit errors that the Golay codes correct (unverified).

The voice RAM is 32 bytes: a longer read wraps. A received burst is in it as the three 72-bit AMBE+2 air frames in a row (the HR_C6000 layout, core/dmr/ambe/ambeFec.h), but only while the decoder runs (4.8).

4.5 Reference oscillator

The calibration's reference tune byte t (section 11) sets regs 0x47 = 0x04 = 0x7F - t, 0x48 = 0x00 if t < 0x80 else 0x03, and DAC2 = t x 4 + 0x600 bench. hrc5000_set_ref() and hrc5000_ref_dac(); the stored tune is re-applied by every full mode set-up. The user's reference trim adds to DAC2 (5.2, "Carrier offset"). The 2-2.5 kHz error two radios showed was not this mapping but PC7 held low (5.2) (unverified until a radio confirms the fix).

4.6 Power and start-up

PE6 low wakes the chip; RadioFoundry waits 12 ms before the first access. hrc5000_power_on then programs the clock (0x0A, 0x0B, 0x0C, 0xB9-0xBB) and enters FM receive. After init the driver reads 0x10 back for the diagnostics page (bring-up stage 4).

4.8 I2S clocks and the receive interrupts

Tester logs: issue 3.

Fact Basis
Before any RadioFoundry write the chip's I2S pins toggle (the reset state has the clocks running); after the set-ups they are driven but do not move (ck 0 ws 0) tester logs
Every set-up's 0x11 block writes 0x36 = 0xF0. On the HR_C6000 bit 7 of 0x36 turns the external-codec BCLK / LRCK off; the C5000 has the same pins (17-20, BCLK / LRCK / ADCDAT / DACDAT) HR_C6000 manual

The driver writes 0x36 = 0x00 while a PCM stream runs and puts 0xF0 back when it stops. Clearing bit 7 alone (0x70) left the clocks stopped; with 0x00 they run and DMR transmit voice decodes on another radio (issue 66, 2026-10-17). On receive the PCM doesn't reach the speaker yet: with every value from 0x00 to 0x60 the speaker plays only a faint TDMA buzz, which sounds like the receiver's audio passed through (4.9) (hrc5000_i2s_clock(), called from audio_md380.c); a full set-up re-applies the state, since its block rewrites 0x36. 4.9 DMR receive

The HR_C5000 doesn't report each received burst: there is no voice class report per burst as on the HR_C6000. With the reads fixed (4.2), a call shows as on air 2026-10-18, against an AnyTone AT-D878UV:

Event What the chip gives
Voice LC header, terminator System interrupt 0x08 with 0x51 = 0x12 / 0x22 (type, class 2) and the LC in page 2 from 0x00
Voice Nothing per burst. The voice RAM changes at every tick, the other slot's ticks included
Late entry, information 0x10 and 0x04: the LC of the superframe

The manual's receive flow: with the CPU in charge of the vocoder (0x06 bit 0, which RadioFoundry sets), the CPU starts the decoder after the voice LC header or late entry interrupt by writing 0x22 bit 5 (DecodeStart), and stops it at the terminator or loss of sync (bit 4, DecodeStop). Without DecodeStart the voice RAM never holds received voice (0 of 324 frames checked at any bit offset); with it, the read at the tick after the call's slot holds that slot's burst.

The slot engine does this for chips with rx_voice_read (hrc_chip_t): a header, late entry or information report starts the decoder (0x22 = 0x27, bits 2-0 keeping the 0x11 block's 0x07), the voice port is read at every tick, the first read whose frames check (two of three C0 words with at most one error) locks the slot, and that slot's reads go to the stack as bursts A to F. A read that hasn't changed since the last tick, or has no frame that checks, is a lost burst; six in a row end the reception (0x22 = 0x17). The port is read at every tick, the other slot's too: a silent talker's bursts are the same bytes every time, so only a port that stopped moving is a lost burst. A read compared with this slot's last burst lost every burst of a silent call after the first (gotchas 1.11). That the port moves at the other slot's tick on a direct channel with nothing on that slot comes from the on-air table above; if it doesn't, the same bytes stay lost bursts. The diagnostics line tr c b same bad counts receptions, bursts and lost reads by cause. The chip's voice class reports are ignored, and its 25 ms report delay doesn't count as out of step.

So on this chip an empty drx trace shows only that no read was taken. It doesn't show that the chip went quiet.

A reception lost mid-call costs more than its gap (drx and log times of a bench run, two gaps alike; gotchas 1.12):

Step Time after the last burst What happens
Six lost reads 360 ms DecodeStop. Nothing is read until the next chip interrupt
13 ticks without a burst 420 ms rs l: the receiver restarts, which drops the chip's sync
Hunting for sync about 660 ms The timeslot interrupts stop for about 240 ms, so the tick count falls behind the air
Late entry report about 1 s The chip has assembled the LC. The first read after it is burst F (the trace's slot counts fit that, and the bursts are numbered from A, so they stay one off until the call ends)

A burst is in the port one tick after its slot's report, so the read at a tick holds the burst of the slot that started two ticks before. The engine takes this as fixed: the read is named, and given its slot counter, from the tick before it. It used to learn the relation from the first read that checked after a header, which with traffic on both slots can be the other call's (issue 279). With traffic on both slots both phases hold bursts that check, so the search for the call's phase is limited:

Rule Detail

Repeater channel (rx_lock_slot 1 or 2) Lock only a phase the CACH TC names as the channel's slot, never one with the slot unknown. A header is kept unless the TC names its phase the other slot
A lock whose phase the TC names the other slot Search again, without the header's phase. The burst index goes on counting one per frame, so a lock back on the same phase keeps A-F
The slot unknown while locked (a receiver restart) The lock stays; its bursts carry no slot number until the TC locks again
The call's own bursts skipped while its slot is unknown Counted, so the index stays A-F. After a quiet-period restart that costs the first bursts of a call (two in the host test, about 150 ms until the TC locks)

The embedded LC isn't per slot (page 2, modem-hrc6000.md 5.2). 4.9.1 Receiving between our bursts

Through a repeater, a voice over hears the repeater's outbound between its own bursts (the modem's tx_listen_split, dmr-modem.md 2.8). One synthesizer serves receive and transmit, so the board retunes per burst (radio_md380.c):

When What
After each burst (the engine's rf(false), PA off) The synthesizer to the receive LO, the HR_C5000's receiver input on (4:0x26), the receive tune DAC, the receive path on. No lock wait
RF_TX_INTER, 2.5 ms early 4:0x12 bits 5-0 = 25 (100 us steps) while the transmission listens, restored at its end (only when it was read: a slot where it can't be read or set isn't listened to). Receiver input off, the synthesizer to the transmit VCO, lock detect waited for (at most 2 ms), then the PA at the slot as without the lead

The chip receives the other slot as it does when idle, and its bursts go to the stack as heard while sending. On the SDR bench, 45 key-ups of 45 got through a repeater whose hang ended around the key-up, against 13 of 15 without it.

The HR_C5000's receive tap is one area, page 2 from 0x30, rewritten per burst received: no CACH, and a voice-layout burst's 48-bit sync / EMB / RC field at 0x30-0x35, then the voice bits. A BS's dedicated RC burst lands there too, though it has no sync and the chip reports nothing for it: that is how the engine hears a reverse channel cease while sending (dmr-modem.md, reverse channel).

What the tests showed (on air, 2026-10-19; not authoritative). The full log is in the feature/md380_follow_up pull request. Each test started from a power-on, and register reads confirmed the writes took effect.

  • Tone data works in FM: a 1 kHz square wave (16-bit, MSB first, one sample every 125 us) played cleanly with 0x0E = 0xBD, which needs bit 2 (Mic1En) and bit 0 (Switch1) set.
  • In DMR, no HPOUT-side setting played the MCU's samples, by I2S or as tone data. With 0x0E bit 2 set, DMR mode feeds the codec's input to the speaker (acoustic feedback). FM_SW and FM_MUTE both high plays the receiver's 4FSK as a buzz.
  • 0x06 bit 2 = 1 (external codec) during a call stops the voice decoding until the next set-up.
  • During a received call the chip sends the MCU a slow ramp near 0x55F8 over I2S (the mic converter's level), never the samples the MCU sent.
  • A handheld transmitting a few feet away puts a TDMA buzz into the audio amplifier: faint pulsing in a test can be that, not a routing result.

The fix (our test, on air 2026-10-19; not authoritative). The speaker amplifier is fed from the codec's LINEOUT (pin 10, 0x0E bit 3), not HPOUT. The tests above never had 0x0D bit 4 (Switch2) and 0x0E bit 3 (LineOutEn) set together while a call played. hrc5000_speaker_voice() now writes, when a DMR PCM stream opens the route: 0x0D = 0x9C, 0x0E = 0x4C (HPMute stays set, HPoutEn stays off, Mic1En on) and 0x37 = 0xC2, with 0x36 = 0x00 already written; it writes 0x0D = 0x8C and 0x0E = 0x44 back when the route closes, which should also end the buzz after a call. -DHRC5000_SPK_VOICE=0 leaves it out. On an MD-380 (UHF, D002.032 codec) against an AT-D878UV on a 70 cm test frequency, TS1, with the build at 17d89001 plus the codec move: received speech plays clear from the speaker and transmit is clear (one 10 s call: 498 frames, 10 bit errors, 3 concealed, 0 lost). Why both bits are needed together isn't in the manual (unverified). Not yet checked with it: the buzz after a call or after our own transmit, the key beep in DMR and FM, and FM receive.

5.2 SKY72310 synthesizer

Skyworks SKY72310-11 (unverified as the part fitted to this radio). From the data sheet:

  • Serial interface: 16-bit words, MSB first: 4 address bits then 12 data bits, latched when CS goes high. Write only.
  • Registers: 0 main divider (N_reg = floor(N) - 32, 9 bits, 6..505 in fractional mode); 1 dividend MSB (10 bits); 2 dividend LSB (8 bits); 5 reference divider (R - 1, 5 bits); 6 phase detector gain (5 bits, 0.125-1 mA/rad); 7 power down and Mux_out (bit 0 full power down, 1 synthesizer power down, 2 integer-N, 3 10-bit modulator, 8:6 Mux_out source, 9 tristate); 8 modulation control; 9 modulation data; 14 delta-sigma (0x080, bit 5 signed mode).

  • The driver uses the signed mode (register 14 bit 5): N_reg = round(N) - 32 and a two's complement dividend for a fraction of -0.5..+0.5. Sent unsigned, every channel whose fraction was over one half came out one phase detector step (8.4 MHz) low with lock detect high: at 443.7, 444.0-444.5, 435 and 450 MHz the radio received nothing, at 440, 445 and 446 MHz it did (DM-32UV as the sender, 2026-10-20, issue 108).   • A new ratio takes effect on the dividend MSB write: order divider, LSB, MSB.
  • Lock detect high = locked (on the Mux_out / LD pin, wired to PD10 (unverified)). The pin is the PS output, open collector (unverified): the MCU's pull-up gives the high (5.7).

drivers/rf/sky72310 implements this and tests/host/sky72310Test.c checks it against a model of the chip. The board picks the smallest reference divider that keeps N in the fractional range (2 or 3 at 16.8 MHz), the phase detector gain at its maximum (the loop filter was designed for a value that is unknown) and Mux_out = the oscillator. The lock detect output's configuration isn't in our copy of the data sheet (unverified).

Carrier offset (issue 108).   • DAC2 moves the reference about 16.2 Hz a count at 448.7 MHz (36.1 ppb), higher = higher. The HR_C5000 register moves it about 31 Hz a step.

Cause: CTC/DCS_OUT (PC7) held low [schematic, page 6]. The 16.8 MHz VCTCXO X601 clocks the SKY72310 and, through the Q605 tripler, the second LO, so receive and transmit share it. Its VC pin is driven by U603 (NJM2904) amplifier B:

Any DC on PC7 moves the reference, at -100K / 560K = -0.18 V per volt at the amplifier's output. RadioFoundry used to drive PC7 push-pull low whenever no tone was sent, which raises the non-inverting gain from 2 to 2.18: the same as DAC2 about 0.18 / 2.18 x 0x744 = 150 counts high, about +2.5 kHz at 448.7 MHz, in receive and transmit alike. That fits both radios (+2.0 and +2-2.5 kHz) in size and sign (this is an estimate: the bias divider past R615 isn't fully traced). PC7 now idles released (open drain, high), so the branch carries no current (unverified on a radio).

While a tone is sent the PWM drives PC7 push-pull around 50 % duty (about 1.65 V mean), so a channel with CTCSS or DCS may still transmit off by some hundreds of Hz (unverified; 6.4).

Before that fix, the user's trim corrected it: hal_radio_t.ref_trim (radio-features.md 6.1) adds ppb / 36.1 counts to DAC2 (rounded), at once and at every rx(). A trim of -2000 Hz at 448.7 MHz (-4.5 ppm) put the first radio's transmit within about 150 Hz (hotspot BER 0.05 %, four cold wake-ups on alternating slots). MD380_TX_OFFSET_HZ (radio_md380.c, a build define, default 0) still shifts the transmit frequency alone; with the trim it isn't needed.

The 100 mW level's boost overshoots at these frequencies: the boost drive by itself settles 4.3 dB over the level (445 MHz), and the 506 µs settle time is too short to fall back from it. The first symbol is about 2 dB high and the first 5 symbols are within 0.3 dB (mean). A settle time of 1100 µs takes the overshoot away there (0.2-1.1 dB, first symbol -0.5 dB), but with the 1 W row at 972 the level then sags after the boost: 3.4 dB under its power at the first symbol with 900 µs, 5 dB under and up to 0.12 ms late with 1100 µs. So the constants stay: this level is early and over, never late. Its drive by itself is too slow: at 445 MHz it reaches -3 dB as the first symbol starts.

Key-down at 445 MHz, every level: -3 dB 0.39-0.47 ms after the last symbol's end and 30 dB down by 0.46-0.57 ms, nothing over the floor in the slot between two bursts. The power of the levels over 1 W is not measured.

The lowest level's drive is 56.5 % of the 1 W row's, 0 to 3 counts over the dead zone's edge depending on the row (2 on the radio measured, its 1 W row 972). At 0 it takes the edge's boost (pa-keyup.md 2), within a count of the others'.

The VHF image doesn't use these constants: its PA is not measured, and constants that key the UHF PA just in time could key a slower one late. It keys every level at its own drive at the key timer's first step, 30 µs after the RF TX interrupt (PA_KEYUP_FIXED), as the radio keyed before the rule.

The window used to be 1530 µs: the second level's lead was then just past it, so it was boosted and ran 3.6-4.7 dB past its power, though written alone at the window's start its own drive is up 0.18 ms before the first symbol, 0.7 dB over. An approach drive (ease_pm 304) capped that boost but kept the levels from 1 W up at the approach drive from 2.2 ms ahead: a step 6-9 dB down through the guard, on the air 1.1-1.2 ms before the first symbol. An earlier fixed boost for every level overshot the low levels by 7 dB and more. Keyed at the RF TX interrupt, the PA was up 1.1-1.6 ms before the first symbol (the interrupt taken as 2.53 ms before the first symbol), and the PA goes on with the first drive. A TIM7 timer runs the points from the RF TX interrupt and drops the PA 30 ms after it (gotchas.md 3.4), and the slot engine's PA-off at the next timeslot interrupt stays as the fallback.

The radio has one synthesizer, so it can't receive while it is set up to transmit. The switch to TX (receiver off, the HR_C5000's transmit set, the TX VCO locked, TX_5V up) happens before the first burst, never at it: done in the RF TX interrupt, the first burst went out unlocked and a one-burst wake-up never reached a repeater. When:

Start Switch to TX
Own timing (simplex, the repeater wake-up) at the modem's tx_begin, or at radio tx() if that comes later
Aligned to a repeater's slots at the engine's tx_slot_found, two ticks before the first burst. Until then the receiver stays on: the engine needs the downlink's TC to find the slot (4, the CACH TC row)

The synthesizer returns to RX at the engine's TX done, on every channel. On a split channel the radio then hears the repeater's answer to its wake-up. On simplex the receive LO is 49.95 MHz from the carrier, and a confirmed data response comes in the next frame, 30 ms after our last burst. Left on TX until tx_off() (the radio task), the radio missed nearly every such response (a receive CRC error instead), and the TX VCO kept leaking the carrier about 34 dB below the burst while TX_5V discharged (about 20 ms). rx() then keeps the synthesizer where TX done put it.

5.7 The 5C rail (SAVE)

PA8 ("SAVE") is the enable of U404 (XC6204B502, CE active high), the regulator for the 5C rail; 5C feeds the SKY72310's 3.3 V regulator U602 (XC6204B332, CE tied to its input) and part of the receive chain [schematic, page 4]. PA8 is an output, driven high. board.c drives it high at start-up.

Measured on a UHF MD-380 with no signal: the raw RSSI reading (ADC1 IN8) went from 246 with PA8 left as an input to 640-720 with it high, and the RSSI follows a received carrier. PD10 (PS, pulled up) reads 1 with SAVE low (the synthesizer unpowered, PS floating) and 0 with SAVE high (powered, not yet programmed: out of lock).

6. Audio

6.1 Paths

FM receive audio and DMR voice both reach the amplifier through the HR_C5000 in RadioFoundry's model: FM through its feed-through (0x36) behind FM_MUTE (PE13), DMR through its codec DAC; SPK_C (PB8) mutes the speaker, AFCO (PB9) turns the amplifier on (the routing (unverified)). Measured on RadioFoundry with a pin scan (the 16 levels of FM_MUTE, FM_SW, SPK_C and AFCO, monitor held on an FM channel): noise only with FM_MUTE high, FM_SW high, SPK_C low and AFCO high. With those levels a received FM call plays clearly. The GT3136's discriminator audio also reaches the MCU on PC3, which RadioFoundry doesn't use. Our tests (2026-10-19, not authoritative) found the HR_C5000's codec output reaching the speaker with FM_SW and FM_MUTE low; DMR voice through it doesn't work yet (4.10).

The volume knob sets the level in the analog path; the MCU only sees its position on PA0. The board therefore has no CAP_VOLUME_POT and hal_power_t.volume() returns -1. There is no hal_radio_t.volume either: the MCU has no way to set the speaker level (the HR_C5000's feed-through gain isn't used for it, and the knob acts after it), so the debug link's volume operation (RADIO op 30) answers "unavailable" (radio-features.md 4.2).

6.2 I2S PCM

I2S3 full duplex, slave to the HR_C5000's codec: WS PA15, CK PC10, SD PC12 (chip -> MCU) and ext SD PC11 (MCU -> chip), Philips, 16-bit samples in 32-bit channels, 8 kHz (unverified for the pins; format and directions copied from the DM-1701 (unverified)). audio_md380.c is the DM-1701's driver. Which HR_C5000 port these lines reach (the external-codec pins or SPI2, the codec / vocoder port) is open (4.10).

6.3 Microphone

Bias from MICPWR_SW (PA14), on whenever the radio runs (section 2.6). Mic level on PA3 for VOX (unverified).

6.4 Sub-audio

CTCSS / DCS are decoded in software from QT_DQT_IN (PA2) and generated as PWM on CTC/DCS_OUT (PC7) (unverified). RadioFoundry does the same behind CONFIG_SUBTONE (on by default, 3.3 KB of flash). CTCSS 100.0 Hz works on air both ways (tester, 2026-10-19). DCS receive works on air (D023N, 2026-11-02). DCS transmit went out inverted (D023N decoded as D023I by another radio, 2026-11-02), so MD380_SUBTONE_TX_INVERT is on by default. At MD380_SUBTONE_PERCENT 30 the deviation is 0.60 kHz peak for CTCSS 100.0 Hz and about 0.72 kHz for DCS (SDR, 2026-11-02), inside the usual 0.5 to 0.75 kHz. Without CONFIG_SUBTONE, channels with a tone open on carrier and send no tone. The FM TX tones (1750 Hz, roger beep) and APRS AFSK are not written (CONFIG_FM_TX_TONES, CONFIG_APRS_RX in config.mk).

The DSP is chip independent (drivers/rf/subaudio, host-tested on synthetic signals); boards/md380/subtone_md380.c and power_md380.c are the glue.

Receive. PA2 is one more rank of the ADC1 scan that power_md380.c already runs (IN2 after the temperature sensor, 480-cycle sampling, ADC clock PCLK2 / 8). Seven ranks give a pass every 383 us, so the sub-audio is sampled at PCLK2 / 8 / (7 x 492) = 2613 Hz (computed at run time). The DMA stream's half and full transfer interrupts (DMA2 Stream4, priority 7) hand each new sample to the detector; the ring grows from 8 to 16 scans, so the averaged RSSI and battery readings cover 6 ms instead of 3 ms. The detector (subaudio_rx.h):

CTCSS DCS
Method Goertzel at the tone and 3 Hz either side, over overlapping 0.2 s windows, a result every 0.1 s slicer with peak-tracked threshold, clock recovery on the edges, 23-bit register against the Golay word
Opens tone holds 30 % of the AC power, beats both guard bins by 1 dB, amplitude at least 8 counts; two results in a row word matches with at most 2 bit errors, twice 23 bits (+-1) apart
Closes three bad results in a row (0.3 s); a 150 ms phase reversal at the end of a transmission is ridden out no match for three words (0.5 s)
Tested all 50 standard tones, neighbors rejected, +-1 Hz sender error, noise only for 60 s all 104 codes both polarities, wrong code and polarity rejected, +-1 % bit rate

status().tone_ok is the detector's verdict (true for a channel without an RX tone); the core debounces it and gates the squelch (radio-features.md). An inverted code is the same bits inverted on the wire; if the analog path inverts the waveform, MD380_SUBTONE_RX_INVERT flips it back.

Transmit. TIM3 CH2 on PC7 (AF2) is a 10-bit PWM at 17.6 kHz (the timer clock divided by 4 x 1024). Its update interrupt (priority 6, running only while a tone is sent) computes a new duty every fourth period, 4.4 kHz: a sine from a 65-point table for CTCSS, the 23-bit word at 134.4 baud with a light smoothing for DCS. The level ramps up over 20 ms; MD380_SUBTONE_PERCENT (default 30) sets the swing as a share of the duty range. tx() starts it after the PA is on, tx_off() stops it, and the pin is released again (open drain, high): PC7 sums into the reference oscillator's tuning, so a low there pulls the carrier (5.2). TIM3 and DMA2 Stream4's interrupt are the only resources added (section 3). The DCS turn-off tail (radio-features.md 3.3a) switches the generator to a 134.4 Hz sine at the same swing (subaudio_tx_tail, with the interrupt held off for the switch); not yet checked on a radio.

Unverified, check on a radio (docs/testing/md380-bringup.md 5 and 6):

  • That PC7 reaches the modulator and where (summing into the HR_C5000's modulation input or the VCO line), and the deviation 30 % gives. CTCSS wants 0.5 to 0.75 kHz of deviation.
  • The PWM's own filter: the carrier is 17.6 kHz and the tone at most 254.1 Hz, so any RC corner under about 1 kHz works.
  • The signal on PA2: its level (MD380_SUBTONE_MIN_AMP, default 8 counts of 4096) and its polarity for DCS.
  • That the ADC rate really is 2613 Hz (the 480-cycle sampling is the existing scan's) and that PA2 is not loaded by the longer sampling.
  • A DCS transmission ends without the 134.4 Hz turn-off burst (not written); the receiving squelch tail may be longer than with a hardware decoder.

7. Display

160 x 128 color TFT on the FSMC 8-bit bus (NE1), command at 0x60000000 and data at 0x60040000 (A17 = RS on PD12), chip select PD6, reset PD13: the DM-1701's wiring (unverified). The controller differs between radios and is detected (below). 10. Power and analog inputs

10.1 Power switch and latch

The volume knob carries the power switch. It doesn't switch the supply: POW_C (PA7) is a latch the firmware holds (unverified), and the switch breaks the battery sense line (and the volume pot's supply). Measured on a UHF MD-380 with the radio on USB: the raw battery reading (ADC1 IN1) is 3341-3351 (8.3 V) with the knob on and 3-4 with it off, at once; the volume reading falls from about 130-155 to 2-4. The radio stays on with the knob off, and with switch_on() always on it only showed the battery running down. switch_on() now reads the knob from the battery line (radio-features.md 5.5, core/radio/power_switch.c, as on the DM-1701), and power-off drops the latch.

10.2 Battery

7.4 V 2S Li-ion pack (unverified). ADC1 IN1 through a divider: RadioFoundry assumes 40.3 counts per 0.1 V (MD380_BATT_COUNTS_X10) (unverified). Low 6.2 V and critical 6.0 V are RadioFoundry's choices, as on the DM-1701.

10.3 ADC scan

ADC1 scans IN0 (volume), IN1 (battery), IN3 (mic), IN8 (RSSI), IN9 (noise) and IN16 (temperature sensor) continuously at 480 cycles each into a DMA ring of 8 scans; readings are averages over the ring (power_md380.c).

11. Calibration

11.1 Location

512 bytes in the SPI flash's security registers 1 and 2 (flash addresses 0x1000 and 0x2000, 256 bytes each) 11.1. A third 256-byte block must not be read into a 512-byte buffer 11.1; RadioFoundry reads exactly two. Read only: RadioFoundry never writes them.

11.2 Layout

Single band, 9 points per row:

Offset Content
0x009 Reference oscillator tune t (section 4.5)
0x010-0x018 TX power, high (5 W), per point
0x020-0x028 TX power, low (1 W), per point
0x030-0x038 Receiver front-end tuning, per point
0x130-0x138 / 0x140-0x148 DMR modulation pair (0x45 / 0x46)
0x170-0x178 / 0x180-0x188 FM modulation pair
0x1B0-0x1F7 Frequency list: 9 entries of 8 bytes, two 4-byte BCD frequencies each, least significant byte first, 10 Hz units
0x1B2-0x1B3 Band low end: the upper half of the first frequency, 4 BCD digits in 100 kHz units (0x4010 = 401.0 MHz)
0x1F2-0x1F3 Band high end, the same from the last entry (0x4799 = 479.9 MHz)

Only the even points (0, 2, 4, 6, 8) of a row are used. Each odd point is the mean of its neighbors, rounded down, whatever the flash holds there. That holds for every row from 0x010 to 0x180 except 0x0E0. The rest of the frequency list is not used: on the radios seen, the first frequencies run 401.035, 411.035 ... 471.035, 479.995 MHz, close to the points below but not the same.

calibration_md380.c accepts the table when the power rows are neither erased nor zero and low < high at every point, and no tuning or modulation row is erased. If the band ends are not BCD, out of band or not ascending, it uses 400.0-470.0 MHz (UHF) or 136.0-174.0 MHz (VHF) instead and says so ("factory/grid").

11.3 Interpolation

The nine points split the band by halving, in 100 kHz units with integer halves: point 0 and 8 are the band ends, point 4 the middle of those, points 2 and 6 the middles of the halves, and the odd points the middles between. For 401.0-479.9 MHz: 4010, 4108, 4207, 4305, 4404, 4502, 4601, 4700, 4799.

The channel frequency is taken in 100 kHz units, truncated (TX frequency for the power rows, RX frequency for the tuning row). The value is linear between the two neighboring points, truncated toward the lower point's value, and clamped to the first and last point outside them. Power and tuning bytes go to the 12-bit DAC as (b x 255) >> 4 (b x 255 in its left-aligned register).

12. SPI flash

12.1 Device and bus

Winbond W25Q128FV, 16 MB, on SPI1 (PB3-PB5, AF5) with chip select PD7, mode 0, 4.5 MHz (unverified). Some early VHF radios have a 1 MB part, a W25Q80 (JEDEC EF 40 14). flash_md380.c accepts any W25Q (JEDEC type 0x40) and probes the size.

12.2 Map

On a 16 MB part RadioFoundry uses the DM-1701's map (settings 0x011000, journal 0x019000, open-firmware codeplug 0x000000 and 0x020000-0xE00000, native area 0xE00000, TFTP staging 0xF00000), so the open-firmware CPS works the same. The TYT codeplug at 0 is overwritten by the first open-firmware write, and writing the TYT codeplug again (stock firmware, its CPS) replaces the open-firmware radio ID, zones and first channels while the rest stays, a mixed codeplug (codeplug-port.md 5.2; measured in a backup, 2026-10-21). board.toml [stock_codeplug] gives the TYT codeplug's span, 0x2000-0x3FFFF, decoded with qdmr's md380 driver. Read it out with the manufacturer's CPS first if it matters (md380-migration.md does that, converts it with qdmr and writes it back). There is no calibration window in the main array (11.1). A 1 MB part gets the same map up to its end (map_1mb): settings 0x011000, journal 0x019000, open-firmware codeplug 0x000000 and 0x020000-0x0FFFFF (flash image 0-0xDFFFF: the codeplug, and the DMR ID database as far as it fits), no native area and no TFTP staging. A part smaller than 1 MB gets no areas: settings live in RAM and nothing is written. The CPS still reads the chip (area 1, up to its end) and the radio info gives its size, so a backup saves all of it.

13. GPS

13.1 Module

The G models carry a GPS module whose NMEA output goes to the MCU's USART3 (unverified). 9600 baud is assumed (unverified).

13.2 Detection

The same board ships with and without the module, and PD8 (the module's power switch on G models) is listed as a second flash chip select on others 13.7. So nothing drives PD8 until the module has been heard: gps_md380.c enables USART3 RX on PD9 at start-up and listens for 5 s. One checksum-valid sentence (any talker, up to 82 characters plus CR LF; drivers/gps/nmea_line) makes the module present: PD8 is then held at the level it already had, and every sentence goes to the position service (position_nmea, CONFIG_GPS). Nothing heard: the UART is switched off and board_t.gps reports no module, so board_has_gps() hides the GPS features. UART errors are counted and cleared in the interrupt, so one framing error never stops reception ( 13.7).

Once heard, the module follows Settings > Location > GPS (board_t.gps = stm32_gps): off stops USART3 and drives PD8 to the other level from the one it was found at, on drives it back and restarts USART3 at the same rate. PD8 switching the module off is assumed from its role (untested on a G model).

14.4 The codec

The AMBE+2 codec is inside the manufacturer's application: the same library as the DM-1701's, at other addresses. In the D002.032 file: code window 0x08050C44+0x10884, table window 0x0808FC64+0xAFF8 and four small table windows in sectors 10 and 11. The merge moves the code to 0x080E0000, keeps the table windows at their original addresses and writes a descriptor at 0x080FFF80; the codec runs in place from there. The D35.14 (MD-380) and S35.14 (MD-390) files work too: they carry the MD-UV380 family's codec, placed next to its tables in sectors 9 and 10 (untested on the radio). Entry points, calling convention, state sizes, the placement and the extraction recipe are in codec-md380.md. stockfw.PROFILES has the profiles, the codec maps (rfoundry/codec_maps/md380/, one per build) the rewrites, boards/md380/memory.ld keeps the application out of sector 11, vocoder_md380.c checks and hosts the codec, and make BOARD=md380 merges it when the firmware file is in codecs/. The debug link reports the codec as md380-d2032-s11v2; a release with the codec in sectors 8-11 reports md380-d2032-s11, and a build from before the first move md380-d2032. Without the codec merged the radio is FM only.

20. Facts moved from the shared specs

  • Settings and storage: on a 16 MB part the core's map is settings 0x011000 (32 KB, 8 sectors), journal 0x019000, open-firmware EEPROM 0x000000, open-firmware flash 0x020000 up to 0xE00000, native area 0xE00000 (1 MB), TFTP staging 0xF00000 (256 KB). There is no calibration window.
  • Roaming reads the IF chain level on an ADC as the site signal (dmr-roaming.md 3).
  • USB: the STM32F405 OTG_FS has three IN endpoints besides EP0, so serial and network are alternatives, not a composite (usb-network.md).
  • board_rf_safe pins: APC_EN and TX_5V (5TC) low, VCO_SEL high (receive VCO), APC DAC (DAC1 channel 1) 0.
  • The G models use USART3 RX on PD9, so there is no UART for the fault trace. Store and restart cause of the crash log are unverified on the radio.
  • The volume knob's switch only breaks the battery sense line: raw ADC reading 3345 at 8.3 V, 3 with the knob off.
  • The DCS turn-off tail is the generator's 134.4 Hz sine (subaudio_tx_tail), not yet measured. There is no FM TX tone path yet, so AFSK TX is not written (boards/md380/config.mk). Without a calibration the board refuses to transmit.
  • Release: [status] release = "stable", both band images (rfoundry-md380-<version>.bin UHF, rfoundry-md380-vhf-<version>.bin). Application sectors 3-10 (848 KB), codec sector 11, so an update keeps the codec. Profile md380-d2032-s11v2 (md380-d2032-s11 from releases with the codec in sectors 8-11, md380-d2032 from a build before the first move). tools/md380_migrate.py flashes it and keeps the codeplug.
