Anytone AT-D868UV / AT-D878UV / AT-D578UV hardware

Status: facts only. RadioFoundry has no Anytone board. This page collects what is known about the family, what a RadioFoundry port would need, and what is still missing. The survey entry is in radios.md. The AT-D868UV pin map in section 4 is not confirmed on a radio (unverified).

Summary. These radios are a GD32F303 (or, on late D578UVs, an Artery AT32F43x) MCU driving a Sicomm SCT3258 DMR baseband over an 8-bit parallel host port. The SCT3258 runs DMR layers 1 and 2 and the AMBE+2 vocoder itself, and voice audio goes codec ↔ SCT3258 over I2S without passing through the MCU. The RF chip is the AT1846S (or a compatible QA4818N), which RadioFoundry already drives. On the AT-D868UV, every bus (the SCT3258 host port, the LCD, the SPI NAND, the AT1846S and I2C) is bit-banged on GPIO: the vendor firmware uses no SPI, I2C or EXMC peripheral. Loading our firmware looks possible: native USB, a documented vendor update mode, and SWD pads with no read-out protection on the units documented so far. The cost is the baseband. RadioFoundry's burst-level modem and vocoder interfaces don't map onto it directly, and features that need the AMBE bits (privacy, the hotspot voice bridge) aren't possible unless a vocoder bypass is found.

A value marked (datasheet) is from the Sicomm CT3258 / SCT3258 datasheet and "Packet Interface of CT3258" v1.0 (2015), copies of which are mirrored on hackaday.io; their license is unclear, so cite them, don't copy them into this repository. (unverified) is not confirmed on a radio or in a datasheet.

2. SCT3258 baseband

2.1 Chip

Item Finding
Package QFN64. Core 1.2 V, I/O 2.5–3.3 V (datasheet)
Clock 12.288 MHz input; on-chip PLL up to 110.592 MHz (datasheet)
Host port (HPI) 8-bit asynchronous parallel bus, Intel or Motorola timing. PIO1 at reset selects which (low = Intel). HOBIB is a handshake line for the host. 64-word FIFOs (datasheet)
Audio Two serial ports: one for the codec (I2S, 16-bit stereo, 24 kHz), one for an optional external vocoder (AMBE-3000 timing modes) (datasheet)
Firmware Held in the chip's own flash: application ("UserFlash") and several vocoder images (the vendor tool loads "Vocoder1, 2, 4, 5"). The vocoders are enabled per chip by separate "Activation" and "Voice Activation" files
Slot timing PIO3 can output a 60 ms slot signal (high = slot 1) (datasheet)

2.2 Boot

After every reset the chip waits for exactly 1024 16-bit words over the HPI (16-bit mode, low byte first). It runs them at once. That block normally holds a second-stage loader, which starts the application from the chip's flash. DMR and dPMR use different boot blocks, and the block chosen sets the chip's mode. On success the chip sends the packet 84 A9 61 00 02 20 17 01 (datasheet).

So the MCU firmware must hold this 1024-word block and send it at every power-on. It is Sicomm's code. RadioFoundry can't ship it, so like the AMBE codec on other radios, it has to come from the user's own radio.

The vendor firmware keeps it in the application image (internal flash), not in the NAND. The 2048 bytes are the same in every image examined (868 V1.40 and V2.40, 878 and 878UVII 3.08n, 578 GD 2.08). SHA-256 of the block: 743515b9f7cd90737c1fff29b652b7558bc5a56487ec38df4fdea8877e7a619a. A mode setting (0–3) makes the firmware replace one or two bytes while sending it (offsets 0x34C and 0x352, or 0x45C–0x45D); mode 0 sends it as stored. What the modes select isn't known yet. An extraction tool can find the block in any vendor image by its hash.

Reset sequence on the 868: two enable outputs go high, the PIO1 strap line is driven low (Intel mode), RSTN is pulsed high for 100 ms and then held low for at least 500 ms. RSTN then goes high, the strap line is released to a pulled-down input, and the boot block follows over the host port.

2.3 Packet interface

Commands and reports are packets with a header (84 A9 61 ...), a TYPE byte and fields. TYPE bits: 7 external vocoder bypass, 6 codec bypass (the bytes go straight to the codec), 5 read/write, 4 near/far end, 3–0 packet type. Fields cover vocoder selection (VOCODER_SEL: 4 = AMBE+2, 16 = analog), mode (PROCESS_MODE), color code, call options, slot, work mode (RX / TX / duplex), gains, BER test, tones, record and playback, and calibration (datasheet).

Two DMR modes (DS, packet interface 2.3):

Mode The chip does The MCU does
Easy mode (layer 3) Layers 1–3 per TS 102 361: dialing, ID and group matching, call setup DMR_CALL_START, CALL_STOP; reacts to match reports
Layer 2 mode Layers 1 and 2: FEC, burst building, 4FSK, sync, slot timing Layer 3 and up, through DIGC_DATA_FRAME: LC headers, terminators, the LC for voice superframes, data blocks. Frames must go to the chip every 60 ms, no more and no less often

Voice in layer 2 mode: the MCU sends the full LC (9 bytes, without CRC) for the voice header, terminator and voice bursts. The AMBE bits come from the chip's own vocoder (datasheet). Encoded voice passes over the packet interface (CHAN_D, 36 bytes per 80 ms) in dPMR mode only (datasheet). The manual also has base station activation (continuous outbound with CACH) and listen-before-transmit (DS 2.3.4–2.3.5).

2.4 Fit with RadioFoundry

RadioFoundry's hal_dmr_modem takes bursts and gives burst events. hal_vocoder converts PCM frames to and from 49-bit frames. On the SCT3258:

RadioFoundry function Layer 2 mode
Voice calls, group and private, talker alias, embedded GPS Yes: the stack builds the LC; the chip does the bursts and voice
CSBK, data headers, rate 1/2, 3/4, 1 data (SMS, IP over DMR, LRRP, ARS) Likely, through DIGC_DATA_FRAME data types. Needs confirming per data type
Basic privacy (Motorola, Anytone BP) Not by RadioFoundry: it XORs the AMBE bits, which the MCU never sees. The chip may have its own scrambler (not checked)
Hotspot / MMDVM voice bridge, voice relay from the network Not unless AMBE frames can be passed through in DMR mode
RadioFoundry's own FEC and burst code (core/dmr/fec, ambeFec) Unused: the chip does it
Split duplex, the hotspot's BS outbound Maybe, through base station activation; voice still needs the AMBE bits
The software vocoder (hal_vocoder) Not needed. A stub reports the vocoder as hosted by the modem

A port therefore needs a modem driver that turns the burst queue into DIGC_DATA_FRAME commands, plus a way for the core to know that voice frames don't pass through the MCU on this radio, so the features above are hidden (a board_t capability, so other radios are unaffected).

2.5 What the vendor firmware does

Item Finding
DMR mode Layer 3 easy mode for voice: the firmware sets DMR_FLC, DMR_CC, DMR_CALLED_ID_BCD, DMR_OWN_ID_BCD, DMR_CALL_OPTION, DMR_CALL_SLOT, DMR_OFFSET and starts calls with DMR_CALL_START. DIGC_DATA_FRAME is used only in a small group of functions (data services)
Encoded voice to and from the MCU Used in DMR mode for call recording and playback. VOCODER_IO_SET is sent with values 0x04, 0x08, 0x10, 0x20 and 0x40 (0 to end), and voice moves in CHAN_D fields with 36-byte payloads, stored in and read back from the NAND. 0x40 feeds the modulator from the MCU, so a recorded call can be transmitted. So the v1.0 manual's "dPMR only" note doesn't hold for the chip firmware these radios run. 36 bytes per 80 ms fits four 72-bit (FEC-coded) AMBE+2 frames (unverified)
Codec Programmed through the SCT3258: about 20 small codec-bypass packets (TYPE bit 6), plus CODEC_SELECT, SET_I2C_ADDRESS and I2C_OPERATION. The MCU has no direct link to the codec
Scrambler SCRAMBLER_SEED is used (the radio's basic privacy, unverified)
Other fields Gains (MOD_GAIN, DEMOD_GAIN, DIGI_MIC_GAIN, DIGI_SPEAKER_GAIN, MISC_GAIN), ANALOG_CONFIG, CTC_PARAM, ANALOG_SUBAUDIO, DC_OFFSET, IQCOMP_COEF, AFC_CONFIG, MODOUT_CONFIG, EQUALIZER_FILTER, SQ_LEVEL, BER_REPORT, PARITY_ENABLE. Two field IDs, 0x2B and 0x3B, aren't in the v1.0 manual

This changes the fit in 2.4: if CHAN_D carries the AMBE frames in DMR mode, privacy and the hotspot voice bridge are possible on this baseband, either in easy mode with the vocoder routed through the MCU or in layer 2 mode. To confirm on the radio: the CHAN_D frame format in DMR mode and its timing against the 60 ms slots.

3. Update and recovery

Item Finding
PC link Native USB on the MCU, a CDC serial port (/dev/ttyACM*). The cable is a plain USB cable; the baud setting makes no difference
MCU update mode, 868/878 Hold PTT + PF3 (top key) at power-on; the red LED blinks
MCU update mode, 578 Hold MENU + EXIT at power-on (or while switching off); the status LED blinks. The radio stays in update mode until an update is written
Vendor tool CPS → Tool → Firmware and Icon Update ("QX_Firmware_Update"): opens a .spi file, shows model and version, 921600 baud, a "Duplex" option and a grayed-out "Encrypt" option
Update files Three per update: .spi (14 or 51 bytes, the file the user opens), .CDI (278 bytes for firmware, about 11 KB for icon sets), .CDD (the payload). The icon (graphics) update uses the same tool and file set
Image sizes (.CDD) D878UV 3.08n: 939,168 bytes. D878UVII 3.08n: 939,240. D578UV2 GD 2.08: 1,020,408. D578UV2 AT 2.08: 1,040,008. Icon sets: 3.7 MB (878), 2.1–7.3 MB (578)
Model check The 578 has separate GD and AT images, and the CPS refuses the wrong one, so the files carry a model / MCU identity
Transfer The host sends "UPDATE", then the .CDD in 32-byte packets with an additive checksum. The image is staged in the external flash and installed on the next boot
After the update "MCU reboot": PTT + PF1 at power-on (578: P2 + channel knob), confirm, set the date and time. This initializes the radio and erases the codeplug
Encryption, signing None on the images examined: each .CDD is a plain Cortex-M image starting with its vector table. The tool's grayed "Encrypt" option shows the format can carry encryption
Bootloader Anytone's own, internal flash 0x08000000–0x08003FFF; application from 0x08004000
SWD Pads marked "AF" beside the MCU. A documented 868 → 878 conversion read and wrote internal flash with an ST-LINK, so read-out protection was off on those radios. Recovery from a bad write: hold NRST (MCU pin 14) low
SWD while running The vendor application turns SWJ off early in its init (AFIO remap: SWJ fully disabled) and reuses PA13/PA14 as inputs. A debugger must connect under reset (NRST held low)
SCT3258 update Separate "Boot Mode for Sct": hold # + the top key at power-on. Sicomm's SCT_PORT tool talks to the chip through the radio's COM port (9600 shown) and writes an Intel-hex file (SCT3258TD_UpdateFlash_V2_01_07BF.hex in the 578 package)
SCT pass-through In that mode the MCU is a transparent bridge: USB OUT data is written to the host port unchanged, and whenever HOBIB signals data the MCU reads the FIFO and returns it over USB. The PC tool speaks the SCT3258 packet protocol itself
MCU ROM bootloader Whether BOOT0 is reachable on the board is not known (GD32F303 and AT32F43x both have a ROM USB/UART loader)

4. AT-D868UV pin map

On the 868 (V2.40). V1.40 drives the same buses on the same pins; it differs in a few key inputs (pull-down instead of pull-up, not yet confirmed) and adds outputs PC10 and PC11. All buses are bit-banged: the firmware sets and clears pins one at a time. RadioFoundry can do the same, or move a bus to a hardware peripheral where the pins allow it (the NAND, LCD and host port pins don't match the GD32F303 SPI or EXMC pin options).

The audio codec is not on the MCU's I2C bus. The SCT3258's PIO0/PIO1 are an I2C master in its preloaded firmware (datasheet), so the codec is probably set up by the baseband (unverified, not confirmed).

4.2 Display

The vendor init sequence is an ST7735S-class controller: reset low 100 ms, then 500 ms; SLPOUT, 120 ms; frame rate B1/B2/B3 = 01 01 01; inversion B4 = 03; power C0 = 28 08 84, C1 = C0, C2 = 0C 00, C3 = 8C 2A, C4 = 8A EE; VCOM C5 = 0C; MADCTL = 0x88; gamma E0/E1; COLMOD = 0x55 (16-bit RGB565); column 0–0x80, row 0–0xA0. That is a 128×160 panel addressed in portrait. RadioFoundry's st7735 driver covers the controller; it needs a parallel-bus transport instead of SPI.

4.3 Other I/O

Pin Use
PA4 DAC channel 1 (12-bit): TX power level. Value from the calibration tables (4.4) by power level and frequency
PA5 DAC channel 2 (configured, use not seen)
PA6 12-bit PWM (TIMER2 channel 0)
PB0 12-bit PWM (TIMER2 channel 2) or plain output
PB9 PWM (TIMER3 channel 3), switched off to analog when idle; probably the tone output
PC0, PC1, PC2 ADC channels 10, 11, 12 (battery voltage and others)

The two PWM outputs (PA6, PB0) are probably the LCD backlight and a tuning voltage; not checked (unverified).

4.4 Calibration and settings in the NAND

The radio's calibration is in the SPI NAND: a primary copy at byte address 0x02F60000 and a fallback at 0x02F80000, used when the primary fails its check. It is about 1.5 KB of small blocks at fixed offsets. Two of them match the bands: four 81-byte tables (one value per MHz, 400–480 MHz) and four 39-byte tables (136–174 MHz), one of each per TX power level. The TX power DAC value is taken from them. The radio settings are a 34-byte record with an A/B pair at 0x02501000 and 0x02521000.

A port must read this calibration from the radio's own NAND and never overwrite it. If the vendor programming protocol addresses the NAND directly (the public flash-tool notes use 32-bit addresses in this range), the calibration can be read over USB before RadioFoundry is installed. Not yet confirmed.

4.5 AT1846S setup

The vendor firmware programs the AT1846S with a common table, two band and bandwidth tables (each with two variants) and the AGC gain table on register page 1. TX and RX switch through register 0x30. The values are kept in the reference directory notes, not here. RadioFoundry's AT1846S driver already covers the chip; the per-radio values come from the user's radio and its calibration.

6. Open questions

  1. Board version: the 868UV's version and MCU (VET6 with 64 KB RAM, or VGT6). Read the MCU marking, or read the ID code over SWD. The 868 images of both lines fit 64 KB RAM.
  2. The unidentified 868 outputs (4.3) and the DAC and PWM roles. Next step: confirm on the radio with a meter.
  3. 878 and 578 pin maps: not yet recorded. The 878 has a larger display.
  4. The .CDD format: plain, a Cortex-M image linked at 0x08004000 (868/878) or 0x08006000 (578). Still open: the 878 trailer after the stated length, how the identity check works, and whether the vendor update mode loads any image. The update protocol lives in the bootloader, which isn't in the update files.
  5. Boot block modes: what the four patch modes select (DMR or dPMR, clock, HPI options).
  6. AMBE pass-through in DMR mode. The vendor firmware uses VOCODER_IO_SET and CHAN_D in its DMR build (2.5). Still to confirm on the radio: the 36-byte CHAN_D format and timing in DMR. It decides whether privacy and the hotspot voice bridge are possible.
  7. Data types that DIGC_DATA_FRAME accepts in layer 2 mode (CSBK, rate 1/2, 3/4, 1, UDT) and whether the chip filters any of them. (The vendor firmware uses easy mode for voice, 2.5.)
  8. Calibration over USB: whether the vendor programming protocol reads NAND addresses directly (4.4).
  9. Read-out protection on current production radios, and whether BOOT0 is reachable for recovery.
  10. 878UVII MCU, and the AT32F43x pin map on late 578s.
