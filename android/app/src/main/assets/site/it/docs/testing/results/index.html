Bring-up results

The records of bring-up runs, one directory per board (<board>/, the id in boards/). Every run record is written by tools/bringup.py run --radio <board> (tests/hil/README.md). Don't write or edit one by hand: a radio's support claims are generated from these records. The one hand-written file is a board's seed record (below). Commit a record with the change it checks. A record with failures is still a record: the failures are the to-do list.

File

<board>/<YYYYMMDD-HHMMSS>-<commit>.json, the date in UTC and the first 8 hex digits of the commit. A run of one feature (--feature F) adds -<feature>.

Key Content
format The record format, 1
kind run (a record without kind is a run)
board The board id, the same as the directory
commit The full commit hash the firmware and the tests were run from. Main is squash-merged, so a branch's commit may later be gone from history; the record still holds
dirty true when the tree had uncommitted changes
sources Feature id to {path: object id}: the git blob or tree id of each of the feature's spec and source paths as run (null for a path that wasn't there). With uncommitted changes, the ids are of the working tree's tracked files
date The end of the run, ISO 8601 in UTC (2026-10-22T19:01:33Z)
features The checklist ids the run covered
granted The needs the run allowed (radio, rf, bench and so on)
tests One object per test case: id (node id, with parameters), features (those it gates), optional (those it is optional for), required, outcome (passed, failed, skipped), and for a skip skip_kind, excused and reason
firmware The radio's VERSION keys proto, view, git, board, features, codec, display
options The run's flags and frequencies (allow-rf, dmr-freq and so on)
tools The Python and pytest versions

A record holds no serial port, host name or serial number: the reasons are scrubbed before they are written, and tools/bringup.py check (in tools/ci.sh) fails on a record that names one. It also fails on a record that doesn't parse, lacks a key or sits in the wrong board's directory. A missing or stale record never fails CI: it shows in status as "built, not yet recorded" or "needs re-run".

Seed record

<board>/seed.json holds the evidence for the board from before its first recorded run: what the spec, the hardware page or an earlier test log says works on the radio. It keeps the generated claims from understating a board that works but hasn't been through tools/bringup.py run. A board has at most one, and it is the only file here written by hand.

Key Content
format 1
kind seed
board The board id, the same as the directory
source The doc the evidence came from, a path in the repository
date When the seed was written, ISO 8601
features Feature id to row: result (pass or fail), and optionally commit (the commit the check ran on, where known), source (a doc for this row, when it isn't the record's) and note

tools/bringup.py check fails on a seed that isn't named seed.json, names a feature the checklist doesn't have, has a row without a pass or fail result, or names a doc the repository doesn't have. A row's commit may be one the repository no longer has.

Status

A feature's status never understates the board. For a feature the board builds:

Status When
pass, fail The newest run record that ran the feature passed or failed it
partial That run had excused skips, and no seed row covers the feature
needs re-run The feature's source paths (tests/hil/features.toml, else the files its switch builds) differ in the tree (tracked files, uncommitted changes included) from the record's sources ids: staleness is by content, not by commit ancestry. The spec is hashed too but not compared: a doc edit doesn't change what ran. The mark isn't downgraded; the feature needs a run
pass (seed), fail (seed) No run passed or failed the feature, and the seed record has a row for it
built, not yet recorded No record covers the feature yet, or it has no HIL test

A run's row replaces the seed's row for each feature the run passed or failed. A seed row whose commit the repository has needs a re-run when the feature's paths differ from that commit's; a row without a commit, or with one that is gone, stands until a run replaces it. Only a failing record shows a failure. The feature matrix's Checked on each radio table is generated from these statuses (tools/boards.py docs), so a new record goes with a tools/boards.py docs run. tools/bringup.py list --radio <board> shows one board with details; tools/bringup.py status shows every board and feature and marks with * each status that rests on a seed record.
