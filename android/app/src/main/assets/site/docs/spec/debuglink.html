USB debug link

A small framed protocol on the radio's host port (USB CDC-ACM on radios with USB, a UART otherwise) for bench automation: read the firmware version, the diagnostics counters and the radio's state, reset counters, take screenshots, press keys, key PTT with a firmware time-out, send radio requests, read a log ring, read the chip's identity and option bytes, read internal flash and the other read-only memories, and reboot. It lives beside the MMDVM hotspot and the open-firmware CPS protocol on the same port (core/hostlink), and it never changes the host link's mode.

  • Firmware: core/debuglink/ (switch CONFIG_DEBUGLINK, default on with CONFIG_HOSTLINK), key injection in core/input/input_task.c, the hook in core/hostlink/hostlink.c.
  • Chip commands: the portable checks in core/debuglink/dl_chip.c (host tested), the platform side in hal/hal_system.h (board.system) and the platform's implementation (platform/stm32f4/sysboot.c, platform/hrc7000/system.c).
  • Host: tools/rfoundry_debug.py (command line and Python module), tests/hil/ (pytest hardware-in-the-loop tests).

1. Coexistence on the host port

The host link sends each request to one protocol by its first byte (hostlink.h):

First byte Protocol
0xE0 MMDVM: enters hotspot mode
ASCII letters (R, W, X, C, D, ...) open-firmware CPS (open-firmware-cps.md 2)
0xA5 followed by 0x5A the debug link
0x7E PPP (CONFIG_NET_PPP): the port goes to PPP, ppp.md 4; the debug link then answers over UDP

0xA5 is not printable ASCII and not 0xE0, so it can't start a request of the other two. A debug frame is recognized where a request may begin:

  • Idle (no session): always.
  • CPS session: only after the 3 ms of quiet that starts a new CPS request (bytes inside a CPS write may be anything).
  • Hotspot mode: only between MMDVM frames, when the MMDVM framer is waiting for 0xE0 and would discard the byte as junk anyway. MMDVM frames before and after a debug frame in the same USB packet are handled as usual. The debug link answers in hotspot mode; its replies go out between MMDVM replies (one task writes both, so they never interleave). Debug frames do not count as MMDVM traffic: they don't keep hotspot mode alive and don't enter it. In practice only a test tool that speaks both protocols on one open port sees this (the port has one owner).

Once A5 5A has been seen, the following bytes belong to the debug frame until it is complete or until 200 ms pass without a byte (the partial frame is then dropped and counted as a time-out). If the byte after 0xA5 is not 0x5A, only the 0xA5 is consumed and the next byte goes to the normal dispatch.

Commands run in the host link task. Each is short: no command waits for another task (radio requests are queued to the radio core, key holds are timed by the input task), and a reply is at most 1032 bytes on the wire.

2. Framing

Both directions use the same frame:

Offset Size Field
0 1 0xA5
1 1 0x5A
2 1 command; replies: command | 0x80
3 1 sequence number, chosen by the host, echoed in the reply
4 2 payload length, little endian. Requests at most 64, replies at most 1024
6 n payload
6+n 2 CRC, little endian

The CRC is CRC-16/CCITT-FALSE (polynomial 0x1021, initial value 0xFFFF, no reflection, no final XOR; the check value of 123456789 is 0x29B1) over the bytes from the command to the end of the payload.

Every reply payload starts with a status byte:

Status Meaning
0 OK
1 unknown command
2 bad argument (wrong length, value out of range)
3 busy: try again shortly (an injected key is still held, the 40 ms gap after it, or the radio request rate limit)
4 unavailable: not built in, or nothing to act on (no display, no key for that action)
5 bad CRC (error frames only)
6 request too long (error frames only)
7 refused: a safety check said no (READ_MEM outside the readable ranges, the REBOOT gate; 3.11)

A request that can't be decoded gets an error frame: command 0xFF, the request's sequence number as far as it was received, payload = status (5 or 6) and the command byte received. A request longer than 64 bytes is answered as soon as its length field arrives; the parser then resynchronizes on the bytes that follow (they are not skipped, since they may belong to another protocol).

All multi-byte numbers are little endian. Text is ASCII, lines end with \n.

3.1 VERSION

Example from an STM32F4 radio (<profile> stands for the codec profile id):

proto=1                 protocol version (this document)
view=5                  GET_VIEW record version (3.7)
git=5277f73a            firmware git hash
git_time=1761840000     the commit's time (a dirty build's: the build's), Unix seconds; absent without git
release=v26.11          release name; only in a build of a release tag
board=XR-100UV
features=FM,SUBTONE,DMR,DMR_PRIVACY,...,USB,HOSTLINK,DEBUGLINK
codec=<profile>-s11  the codec profile found in flash (below)
display=160x120x16      panel width x height x bpp
inset=5,5,5,5           safe area insets: top, bottom, left, right
uptime_ms=123456
req_max=64
reply_max=1024
inject_max_ms=10000     longest hold of an injected key, PTT included
tone_burst_max_ms=10000 longest tone burst (RADIO op 23); only in builds with CONFIG_FM_TX_TONES
start=en                the language the radio starts in until the user picks one (ISO 639-1)
preset=amateur          the build's preset: full, a release variant, or custom
off=AUDIO_PROBE,FONT_AA  the switches the radio could have that this build left off; may be empty

release= is the release name (RFOUNDRY_RELEASE, release.md), present only when the image was built from a release tag; git= is always the commit. A host shows the release name when there is one. git_time= is the commit's committer time (RFOUNDRY_GIT_TIME), so a clean build stays reproducible; a build with local changes (-dirty) carries its build time instead, since its code is newer than the commit. A host compares it with a release's git_time to tell whether a build that isn't a release is older than that release.

features= names only some of the build's switches. P25 is in it only where the board runs P25 (a build with CONFIG_P25 on a board whose air interface receives it, p25.md 7.1), so the Codeplug Editor offers P25 channels only for such a radio. NXDN likewise: a build with CONFIG_NXDN on a board whose air interface carries it at either rate (nxdn.md 6). off= lists every switch in config/features.mk FEATURES that the build left off, except those the board can't have or hasn't written (BOARD_UNSUPPORTED, BOARD_NOT_WRITTEN). With it a host knows the whole build: the web installer's update keeps a custom build's choices by it. preset= is the release variant the image was built as (VARIANT, full without one), or custom when a switch was set on the make command line. The build service sets every switch on the command line; when they equal a variant's, the start language aside, it also sets RFOUNDRY_PRESET to that variant, so the build says it. start= is the build's start language (CONFIG_LANG_DEFAULT_<CODE>, en without one): the language shown until the user picks one in Settings. off= can't carry it, since a start-language switch added after the build is in neither list, and an update keeps it; builds before it don't send it. preset= and off= come last, so a list too long for the reply drops only itself. Older builds send neither. All three come from core/hostlink/build_info.c, as does features=, and a build without the debug link sends them too, from the stub entry's listener (stub-entry.md 2).

codec= is the board's own check of the codec in flash, the same one that decides whether DMR voice runs: a profile id (<profile>-s11 on an STM32F4 radio: the descriptor is valid and the signature word and the CRC-32 of every codec window match the codec as the merge places it, code in sector 11, as codec-placement.md "STM32 radios" describes; <board id>-<build> on an HR_C7000 radio: the codec slot is valid, and the build is the version of the stock file it was carved from), absent (the board has a vocoder but the check failed: erased, another stock version, damaged), present (a valid codec whose board names no profile) or none (built without DMR). It describes flash, not whether voice can run at that moment: after the HR_C7000 stub entry has stopped the codec (its RAM is the stub's), the profile id is still reported. The first request after boot may take some 20 ms longer while the board computes the CRCs. It reads flash only. tools/rfoundry asks for it before flashing to decide whether the codec sectors can be left alone (docs/dev/release.md). A build from before the STM32 codec moved reports the stock id (the profile without -s11) for the codec at its stock addresses, so the flashing tools know the new layout doesn't hold it.

Unknown keys must be ignored by hosts; keys may be added without a version change.

3.2 GET_DIAG

The diagnostics as text lines, numbered from 0, with the firmware's millisecond clock at the time of reading, so a host can compute rates between two reads:

Lines Content
0, 1 the radio core's summary: radio FM MEM ch 12 'Name' 462.56250 RX, radio rssi -95 nz 30 sq 3 pw 1W tx 0ms
2-5 (DMR builds) the DMR voice path: call rx= play= late= tx= deny=, call vb= lost= dup= enc= txu= evq=, voice in= play= conc= sil= und=, voice ovf= bad= lost= bits= q= calls= (the same counters with full names are in the dmr_stats view section)
then the board's diagnostics lines (board.diag_line(0..), the radio's diagnostics page)

The reply holds as many whole lines as fit from first; next is the line to ask for next, 0xFF when the last line was sent. The board lines are each board's own. On the HR_C6000 boards they start with the slot engine counters (V<voice> H<headers> T<terminators> I<idle>, C<csbk> D<data> crc<errors> rc<rc>, ...) and end with the readings and the audio counters (aud blk ov dr).

3.3 SCREENSHOT

Two forms. The packed form sends the frame buffer at the panel's own depth, LZ4 packed: a tenth to a thirtieth of the RGB565 form's bytes on the UI's screens. A 160 x 128 16-color frame is about 2.3 KB instead of 40 KB, and one read is enough: 0.2 s instead of 7 s at 115200 baud. The RGB565 form is the original one. Firmware before the packed form answers a packed request with BAD_ARG, and the host falls back to the RGB565 form.

Packed form

Request: offset u32 into the stream, format u8 = 3. Reply after the status:

Offset Size Field
1 2 width (the whole panel, insets included)
3 2 height
5 1 bpp: 1, 4 or 16, the frame buffer's own
6 1 format: 3
7 4 insets: top, bottom, left, right
11 4 stream length
15 4 offset of this chunk in the stream
19 4 frame buffer bytes the stream decodes to
23 4 frame count: frames the UI has started drawing
27 1 flags: bit 0, a frame is being drawn
28 32 bpp 4 only: the palette, 16 RGB565 colors (0 for an entry not set)
28 or 60 n the chunk, at most 1000 bytes

The stream is one LZ4 block (the public LZ4 block format) of the whole frame buffer, encoded again for each request by the encoder of the fast codeplug protocol (cps-fast.md 5). The frame buffer is rows of stride bytes, top row first:

bpp Stride Pixels
1 (width + 7) / 8 MSB left, 1 = ink
4 (width + 1) / 2 high nibble left, a palette index
16 width x 2 RGB565 little endian

The host asks for offset 0, then each next offset until it has the stream length. The chunks are one frame when the frame count is the same in the first and the last reply and neither says a frame is being drawn. Otherwise the host reads again (rfoundry_debug.py screenshot, --tries, default 4). It also starts over when the frame count or the stream length changes between replies, or when an offset past the end of a new frame's stream answers BAD_ARG. A frame buffer over 65535 bytes (no panel today) answers UNAVAILABLE, and the host uses the RGB565 form.

RGB565 form

Request: none (header only), or offset u32 and length u16 (at most 1000 bytes per reply). Reply after the status:

Offset Size Field
1 2 width (the whole panel, insets included)
3 2 height
5 1 bpp (16 for a 16-color panel too: it is sent as RGB565)
6 1 format: 1 = RGB565 little endian, row-major; 2 = 1 bpp rows of (width + 7) / 8 bytes, MSB left
7 4 insets: top, bottom, left, right
11 4 total frame buffer bytes
15 4 offset of this chunk
19 n the chunk

A 16-color frame buffer (bpp 4) is converted through its palette as each chunk is read, so the host sees an RGB565 frame of width x height x 2 bytes. The chunks carry no frame count, so a host reads the whole buffer twice and repeats until two reads agree, which gives a consistent image unless the screen changes continuously (a running timer).

Both forms

The chunks are read live from the UI's frame buffer, without a lock (the UI task owns it, and a 38 KB copy would not fit in RAM). While a capture is read the UI does not redraw: every SCREENSHOT request holds redraws for 1 s, and the request that returns the last chunk for 250 ms, long enough for a second read to start. A key or radio request in that time changes the UI's state (ui.screen in GET_VIEW) at once, but its screen is drawn only when the hold lapses, so a host that captures a new screen waits for the hold to end (tests/hil/rfoundry_hil.py: Radio.screenshot and shot_until). Firmware before this rule held for 1 s after the last chunk too.

3.4 KEY

Injected keys go through the same path as the radio's own keys: their physical key bits are ORed into the input task's scan, so debounce, the gesture engine (PRESS / LONG / REPEAT), the PTT and MONITOR edges to the radio core, and the UI's idle and backlight time all behave as for a real key. input_last_source() tells the UI that the last activity came from the host.

Kind Arguments Effect
0 action u8, gesture u8, value i8 a logical action (below) with a gesture: PRESS holds the key that gives it for 80 ms, LONG for 720 ms (released after the LONG event), REPEAT for 720 ms + value x 120 ms; DOWN / UP hold and release a raw-edge key (MONITOR; PTT goes to the PTT slot with the 10 s time-out); enc with DOWN adds value detents. An action no key gives (e.g. left / right on a radio without those keys) goes straight to the UI's event queue
1 mask u32, hold ms u16 hold the board's physical key bits for hold ms
2 none wake: counts as key activity without an event, so the backlight comes on (the UI drops the first key after the backlight went off)
3 action u8, hold ms u16 hold the key that gives the action for hold ms, whatever gesture that makes

Actions (hal_input.h): 1 up, 2 down, 3 left, 4 right, 5 select, 6 back, 7 quick, 8 context, 9-18 digits 0-9, 19 ptt, 20 monitor, 21 talk target, 22 emergency, 23 enc (encoder step), 24-27 user 1-4. Gestures: 0 PRESS, 1 LONG, 2 REPEAT, 3 DOWN, 4 UP.

Rate limit: one injected key at a time. While one is held, and for 40 ms after its release (two scans for the debounce to see it released), KEY answers busy (3). Every hold is capped at 10 s. Both also count key scans: a hold ends only after three scans have seen the key, and the next starts only after three scans have seen it released. A scan can run late (a key matrix on the LCD data lines is busy for a whole redraw), and a hold measured in ms alone ended before the debounce saw it: the press was lost.

3.5 PTT

down = 1 holds the PTT key, 0 releases it. The optional max ms (default and maximum 10000) is a time-out kept by the input task: the PTT is released when it expires even if the host never sends down = 0 (the host crashed, the cable was pulled). Sending down = 1 again while held re-arms the time-out. The reply carries the time-out applied. PTT goes through the radio core like the real key, so every transmit check applies (band, RX-only channel, TX time-out, hotspot mode). The PTT slot is separate from KEY's, so KEY presses work while PTT is held.

3.6 GET_LOG

Firmware code logs with dlog(fmt, ...) (core/debuglink/dlog.h: %d %i %u %x %X %s %c, width, 0 flag; no floats). Lines go into a 2 KB RAM ring as <ms> text; when it is full the oldest lines are dropped and counted. GET_LOG takes whole lines, oldest first (the read removes them), and reports the lines dropped since the last read and whether more remain. Built without the debug link, dlog() compiles to nothing.

The DMR stack's lines (core/dmr/call/dmr_call.c): crx @<slot> ... the RX trace (on by default; dmr_call_set_rx_trace), and for each burst list sent without PTT ctx <tag> n<bursts> when it starts and ctx <tag> end <err> <ms> when it leaves the air (tag: ars sms signal reply emergency ip udp other from the data service, roam a roaming probe; err a dmr_tx_error_t, 0 sent whole). The TX lines are logged with the RX trace off too. On a busy channel the RX trace fills the ring in minutes: read it soon after the event. The view's last_tx_ms, tx_auto and data.tx_last_* keep the last transmission when the lines are gone.

3.7 GET_VIEW

The radio's state as key=value lines, one section per request, so each fits a reply. next is the following section, 0xFF after the last. Every section starts with section=<name>; a section cut short ends with truncated=1. Hosts ignore keys they don't know; keys may be added at any time, and view= in the core section (and in VERSION) is bumped only when a key changes meaning or goes away. View 3: net.air_busy counts the host's packets dropped after waiting in the TX queue; in view 2 it counted packets refused because the service was busy. View 4: the ppp.* keys moved from hotspot to net_link (26), which also has the new MTU keys, as a hotspot section with them outgrew a reply on radios with PPP; the mdns.* and tftp.* keys moved from net to net_svc, which a full net section had cut short. View 5: the cps.* and cpsf.* keys moved from storage to cps (27), as storage with codeplug.accepted outgrew a reply. Each request takes a fresh snapshot (radio_get_view()), so sections may be a few ms apart: compare serial= in the core section when that matters.

3.10 READ_MEM

Request: address u32, length u16 (1 to 1000). Reply after the status: the address u32, then the bytes. The readable windows are the platform's (hal_system_t.mem_window); the core checks that the whole range lies inside one of them (dl_mem_allowed), otherwise the answer is refused (7). Firmware without windows for its chip answers UNAVAILABLE (4). Only memory, and register blocks where a read changes nothing, are windows. A read elsewhere can have side effects: clearing a status flag or an interrupt (read-to-clear registers), popping a FIFO.

A window is either memory (any address and length inside it) or registers. A register window takes only whole aligned 32-bit words (address and length multiples of 4); anything else is refused. The firmware reads it one 32-bit load per word: a byte or unaligned access to a peripheral can fault the bus.

STM32F4 (INFO_CHIP family 0; platform/stm32f4/mem_window.h):

Range Contents
0x08000000 up to the flash size (at most 0x080FFFFF) internal flash, the vendor bootloader at 0x08000000-0x0800BFFF included
0x1FFF0000-0x1FFF77FF system memory (ST's ROM bootloader)
0x1FFF7800-0x1FFF7A0F OTP and its lock bytes
0x1FFFC000-0x1FFFC00F option bytes
0xE000ED00-0xE000ED3F the core's system control block, aligned words only: CPUID (0x410FC241 on every STM32F405/407: Cortex-M4 r0p1), interrupt control, VTOR, the fault status and address registers (none clears on a read)

RAM, CCM and the other peripheral addresses are always refused on the STM32F4 (CHIP_REG reaches the peripherals, 3.24). The UID and the flash size register come through INFO_CHIP instead.

HR_C7000 (family 1; platform/hrc7000/mem_window.h). READ_MEM works before INFO_CHIP has a UID:

Range Kind Contents
0x03000000 up to the program flash size (1 MB, or the board's HRC_XIP_FLASH_SIZE) memory program flash through XIP: loader, application, codec slot
0x00010000-0x00057FFF memory main SRAM: data, stacks, the interrupt table, the codec and stub windows
0x18000000-0x18007FFF memory SRAM shared with the modem: PCM buffers, the codec's tables
0x11000000-0x1100005F registers system block: soft reset, clock manager, IO mux, XIP mode (not the modem registers above it)
0x14020000-0x1402007F, 0x14100000-0x1410007F, 0x14110000-0x1411007F registers GPIO A, B, C: levels, directions, interrupt enable, mask, type, status (the EOI register is write-only)
0x17000000-0x17000033, 0x1700003C-0x1700003F, 0x17000044-0x1700004B, 0x17000060-0x1700008F registers PIC, only its documented registers: modes, polarities, masks, priorities, the request record (cleared by writing 1, not by a read); the gaps are refused

Refused on the HR_C7000: the timers and the watchdog (their EOI registers clear on read; CHIP_REG reaches the timers, 3.24), UARTs, SPI, I2C, the modem registers and the modem buffer RAM at 0x16000000 (FIFOs, read-to-clear status), and the LCD and USB controllers.

rfoundry_debug.py peek ADDR[:LEN] prints LEN bytes (default 4) at ADDR as little-endian words, four to a line, when both are word aligned, else as bytes. For example peek 0x14100040 is GPIO B's INTSTATUS and peek 0x17000000:0x34 the PIC's first set of registers.

RDP and reads: read protection level 1 does not stop the application from reading flash. Level 1 blocks flash access only while a debugger (SWD/JTAG) is connected and when the chip boots from SRAM or system memory (the BOOT pins). After a normal boot from user flash, user code reads every flash address, whether it runs from flash, as this firmware does, or from SRAM, as the flash stub does (stub-stm32f4.md 2; the stub's first bench run confirms it). So READ_MEM works at RDP level 1, and that is how the vendor bootloader is read.

The web flasher and rfoundry read the bootloader sectors this way to find the bootloader key by its SHA-256 so updating a radio that runs RadioFoundry needs no stock file. The bytes stay in memory; only the key is kept.

rfoundry_debug.py dump --addr A --len N -o FILE reads in 1000-byte pieces. It refuses to write inside any git work tree. The vendor bootloader is proprietary: a dump of it is never committed or published.

3.11 REBOOT

Request: mode u8, token u32. Reply: the status and a reason byte.

Mode Effect
0 normal reset (NVIC_SystemReset; on the HR_C7000 a watchdog reset, transmitter off first (watchdog.md 3)): the vendor bootloader runs, then the application
1 ROM DFU: reset, then straight into ST's system-memory bootloader (USB DfuSe, 0483:DF11). Only at RDP level 0

The token must be the low 32 bits of the chip UID (INFO_CHIP offset 7), so a stray frame can't reboot the radio. The checks, at the request and again just before the reset:

Reason Refused when
1 the token is not the UID's low word (both modes)
2 mode 1 on a chip other than the STM32F4 (INFO_CHIP family), or mode 1 and RDP is not level 0. At level 1 the ROM bootloader refuses flash access, and its read-unprotect command mass-erases all of flash, the vendor bootloader included, which would leave the radio unable to load firmware without SWD. Level 2 disables the ROM bootloader
3 transmitting: radio state TX, or the hotspot sending (both modes)
4 the chip info could not be read
5 (logged only) the ROM DFU flag could not be stored in the backup register

On OK the reply goes out first and the firmware resets 250 ms later. If a check fails at that point (a PTT came in), it logs debuglink: reboot ... aborted and stays up. Mode 1 stores a flag in an RTC backup register that survives the reset, and the start-up code jumps into the ROM bootloader when it finds it.

rfoundry_debug.py reboot [--rom-dfu] reads INFO_CHIP first, refuses --rom-dfu itself unless RDP is level 0, sends the token and prints the radio's reason when it refuses.

3.18 STUB

Load the host's flash-access RAM monitor into a free RAM span and hand the SoC to it at run time, no power cycle (CONFIG_STUB_ENTRY, its own feature: stub-entry.md; a build without the debug link answers this command with its own listener, byte for byte the same). Two platforms have it: the HR_C7000 (the "C7 stub", stub-entry.md) and the STM32F4 (stub-stm32f4.md). Built without the switch, or on a board whose platform has no hal_system_t.enter_stub, every operation answers DL_ST_UNAVAILABLE. All u32 are little endian. The guard is a 32-bit magic key 'C7SB' (0x42533743) on BEGIN and ENTER, plus the exact length and a CRC-32 of the whole image checked before the jump.

Op Request Reply / effect
0 INFO none magic u32, load_addr u32, region_size u32, max_chunk u16, armed u8, received u32: the span and transfer state. load_addr / region_size are the board's HRC_STUB_BASE / HRC_STUB_SIZE (a board's span depends on CONFIG_DMR: the build with DMR reports a smaller one)
1 BEGIN magic u32, total_len u32, crc32 u32, entry u32 received u32 (0): zero the span and arm a transfer. Bad magic: refused; total 0 / over the span or entry outside it: bad argument
2 DATA offset u32, bytes (<= max_chunk) received u32: write a chunk (the frame's CRC-16 guards it). Not armed, or past total_len: bad argument
3 ENTER magic u32 ok then (after the reply) quiesce and jump; the monitor answers next. Bad magic: refused; incomplete or the CRC-32 mismatches: bad argument; the radio transmitting: busy (the image stays loaded, ENTER again later); the platform's image check says no: refused with reason byte 1 (STUB_REFUSE_WATCHDOG: the STM32's IWDG runs and the image header doesn't say the stub feeds it: no header, a version before 3 or no feed flag, stub-stm32f4.md 3.1, watchdog.md 3.1)

The CRC-32 is the standard (zlib) CRC-32. Per-chunk integrity is the debug link frame's own CRC-16, so DATA carries no second checksum; the span is zeroed at BEGIN, so a dropped chunk leaves zeros that fail the ENTER CRC-32. After an ok ENTER the firmware sends the reply, draws a static banner on the display ("PC Loader Connected" / "Power-cycle to exit", flushed synchronously so the panel does not sit on a stale or hung frame while the monitor runs) with the backlight at full, then quiesces and jumps and stops answering; the host then speaks the monitor's own protocol (02 op len chk 03, the stub's PROTOCOL.md) on the same UART at the same baud. Recover the radio with a power cycle.

Where the image runs: INFO's load_addr is the address the image is linked for, and the host builds BEGIN's entry from it. On the HR_C7000 that is the span itself. On the STM32F4 the span is a staging buffer in RadioFoundry's own RAM and load_addr is the SRAM base (0x20000000, hal_system_t.stub_run_addr): enter_stub stops the DMA controllers, copies the buffer there and jumps with a handoff flag in r0 (stub-stm32f4.md 3). The STM32F4 stub then answers on the USB serial port, with the same framing as the C7 stub. ENTER is answered busy (3) while the radio transmits.

The monitor never touches the RF chips, so the transmitter stays as RadioFoundry left it for the whole session. ENTER is refused while the radio core is transmitting, the entry is dropped if PTT went down in the 100 ms between the reply and the jump, and the firmware calls board.radio->tx_off() just before the jump in every case.

On the HR_C7000 the host sends the universal monitor: its entry is position independent, copies the image from load_addr to its run address (0x30000) and runs there, with .bss and stack after it (stub/README.md, RAM placement). The firmware does not check where the image will run (it only checks the length, the CRC-32 and that entry lies inside the span); the host does: stubtool.py reads INFO first and refuses a span whose copy would overlap the run address or leave SRAM. The older position-dependent monitors (--legacy-stub, --rfoundry-stub FILE) must be linked for exactly load_addr; the host refuses one whose linked data and stack lie outside the span or that does not end its text and data at load_addr plus its length. On the STM32F4 the host checks instead that the image starts with the STM32F4 stub's entry code and that load_addr is the SRAM base. INFO is the whole discovery protocol, so firmware built before a board moved its span keeps working with the same tool.

2 READ addr u32, offset u16 addr u32, format u8, length u16, CRC-32 u32, offset u16, up to 1000 stream bytes

A refusal (DL_ST_REFUSED) carries a reason byte: 1 outside the image or a protected area, 2 the flash can't be written, 3 no staging area, 4 staging full, 5 staging busy, 6 out of order, 7 CRC, 8 bad stream, 9 flash failure. tools/cps_fast.py info | read | write | verify drives it.

3.21 WATCHDOG

The hardware watchdog's bench tests (CONFIG_WATCHDOG, watchdog.md 6). Every test ends in a watchdog reset. Built without the switch, every operation answers DL_ST_UNAVAILABLE.

Op Name Arguments Effect
0 CLEAR_GAP none restart the longest idle gap measurement (watchdog.max_gap_ms)
1 TEST kind u8, token u32 after the reply, about 100 ms later, the feeds stop for good: kind 1 STARVE (the idle task stops feeding; everything else runs, the link answers until the reset), 2 SPIN (the host link's task spins with interrupts on), 3 IRQ_OFF (it spins with the kernel's interrupts masked)
2 LOAD three u32 (platform defined), token u32 after the reply: the watchdog re-armed with a raw load, then STARVE. HR_C7000: OT_LOAD_H, OT_LOAD_L, RST_LOAD (0xFFFFFFFF leaves it). Elsewhere status 4

The token is 'WDOG' (0x474F4457, little endian in the payload); another value, or a transmitting radio, is answered refused (7). A test is dropped if PTT went down between the reply and its start. During STARVE and LOAD the view's watchdog.starved_ms counts from the last feed; its last value before the link goes quiet bounds the timeout. rfoundry_debug.py watchdog [show|clear-gap|test starve|spin|irq-off|load H L [RST]].

3.22 RX2

The second receiver's SoC, on a radio with two (board.rx2, the GD-88; rx2-link.md). Always built. On a radio with one SoC, INFO answers no flags and the rest DL_ST_UNAVAILABLE.

Op Name Arguments Reply / effect
0 INFO none flags u8: bit 0 a second receiver, 1 it answers, 2 the update bridge is there, 3 so is RESTART
1 BRIDGE token u32 about 100 ms after the reply: the second SoC is sent to its first stage, and the cable is bridged to it (rx2-link.md 4). Never returns; the radio restarts when the host has been quiet for a while
2 RESTART token u32 the second SoC restarts

The token is 'BRDG' (0x47445242, little endian in the payload); another value, or a transmitting radio, is answered refused (7). The bridge is dropped if PTT went down between the reply and its start. rfoundry_debug.py rx2 [info|restart]; stubtool.py --board gd88b uses BRIDGE.

3.24 CHIP_REG

One register, read, or written and then read back, for bench work: comparing a register with another firmware's value, trying one on the air, or poking a peripheral without a new build. No driver knows about a write: its next set-up of that register overwrites it.

Request Reply after the status
chip u8, page u8, register u8 the value u32
chip u8, page u8, register u8, value u32 the value read back u32 (a write-only register: the value written)
0xFF, address u32 the value u32
0xFF, address u32, value u32 the value read back u32

Chips below 0xFF are the radio's RF chips, through the board's board.chip_reg. The chip and page numbers are the board's, listed on its hardware page. A chip, page, register or value the board doesn't offer answers bad argument (2); a board without the hook answers unavailable (4).

Chip 0xFF is the SoC: a 32-bit register at a 32-bit address, through the platform's hal_system_t.reg. Only aligned words inside the platform's register windows; any other address is refused (7), as READ_MEM refuses one. A write is refused (7) while the radio transmits, a call or the hotspot, as REBOOT is. The read has the register's side effects (reading a timer's EOI acknowledges it), so the windows can include blocks READ_MEM leaves out. A platform without the hook answers unavailable (4).

Platform Register windows
HR_C7000 (platform/hrc7000/mem_window.h) READ_MEM's register windows (3.10: system block, GPIO A-C, PIC), plus the timers 0x14000000-0x14000077
STM32F4 (platform/stm32f4/mem_window.h) the peripheral buses 0x40000000-0x5FFFFFFF, the FSMC control registers 0xA0000000-0xA0000FFF and the Cortex-M4 private peripheral bus 0xE0000000-0xE00FFFFF (SCB, NVIC, SysTick, DWT, DBGMCU). The access runs with bus faults ignored: a reserved address that faults is refused (7)

Writes are logged. rfoundry_debug.py reg CHIP REG [VALUE] [--page N], or reg soc ADDR [VALUE] for the SoC.

3.26 T3

A DMR Tier III trunked system (dmr-trunking.md), staged in RAM until the codeplug has keys for it. Stage it with RESET, SYSTEM, CTRL (and CHAN, TG, SITE, PLAN), then START: the radio hunts for the control channel on the channel it is on. STOP, or another channel, leaves the system. Built with CONFIG_DMR_TRUNK; otherwise every op answers unavailable (4). Each op answers OK or bad argument (2), with no reply bytes. Little endian.

Op Name Arguments
1 RESET none: the staged system back to empty
2 SYSTEM own ID u32 (0: the radio's), model u8 (0 tiny .. 3 huge), net u16, category u8 (1 A, 2 B), opts u16 (T3_OPT_*), color code u8, talk ID u32 (0: the first talkgroup with the talk flag), talk private u8; then optional: DMRLA u8 (0 when absent), leave threshold dBm s16 (0: the radio's roaming threshold), Vote Now sample ms u16 (0: 360), flags u8 (bit 0: IP through the system's gateway, IPI)

4 CHAN a channel of the plan, as CTRL (8 channels at most)
5 TG talkgroup u32, flags u8 (1 listen, 2 talk)
6 SITE a SITE the radio may use, u16 (none staged: any)

8 START select the staged system
9 STOP leave it: back to the channel or VFO
10 DEREG de-register, staying on the system (CONFIG_DMR_TRUNK_TX)

12 STATUS send a status: to u32 (an MS, or a talkgroup), group u8, status u8 (0-126; 127 polls an MS) (CONFIG_DMR_TRUNK_TX)
13 SDATA send UDT short data: to u32, group u8, UDT_Format u8 (4: ISO 8-bit text, 0: binary), then 1-46 octets (CONFIG_DMR_TRUNK_TX)

15 PS power save: PowerSave_RQ u8 (0 off, 1-7 = 1:2 to 1:128), T_Awake ms u16 (0: default 2 s)
16 DIVERT call diversion: mode u8 (0 clear the radio's own, 1 set, 2 clear every one to the radio), services u8 (8 voice, 4 packet data, 2 short data, 1 status), to u32 (set), group u8 (set: to a talkgroup)

21 LOAD stage system n u8 of the codeplug (dmr-trunking.md 12) in place of the staged one, not started; bad argument when it is absent or has no control channel

3.28 AIR

Bench access to the air interface (hal/hal_air.h): the board's receive tap (board.baseband, hal/hal_baseband.h) as raw samples, and a session on its provider (board.air, hal/hal_air.h) with a profile the host sends: its receive chunks, and a transmission of the host's symbols. One tap or one session at a time. CONFIG_AIR_RAW builds only (it needs CONFIG_AIR and CONFIG_DEBUGLINK); other builds answer unknown command (1). A board without a tap or a provider answers unavailable (4). Little endian throughout.

The radio core hands the radio over through debuglink_air_core_t (core/debuglink/debuglink_air.h): enter (the DMR call stack and P25 stopped, the radio receiving in DMR on the channel's frequency; refused while transmitting or in hotspot mode), leave (the channel is tuned again, P25 restarting on a P25 channel), and transmit on / off. While the bench holds the radio, the core view's state is tx when keyed and idle otherwise: no squelch, scan or reception runs. Without that hook the tap and a receive session still open while the radio is idle in DMR (busy (3) otherwise), and TX_KEY answers unavailable (4).

Op Name Arguments Reply after the status
0 STATUS none key=value text: air.built, air.provider, air.tap, air.core (1 = the hook is set), air.state (idle, tap, open), air.keyed, air.rx_chunks, air.rx_dropped, air.tx_started, air.tx_started_us, air.tx_underruns, air.tx_space_events, air.tx_done, air.tx_done_us, air.tap_gaps, air.tx_chunk_syms, air.tx_queue_depth; while open air.tx_space, air.now_us, and from a provider that counts its receive load air.rx_work_us, air.rx_span_us (hal_air_t.rx_load: work / span is the share of the CPU)

2 TAP_READ none seq u32 (the first sample's number), t_us u32 (its time), gaps u32, n u16, then n samples: int16, or int8 after an arithmetic shift right by shift, clipped
3 TAP_STOP none none

5 CLOSE none none. Ends a transmission first (PA off)

The profile is air_profile_t packed: sym_rate u16, levels u8, shape u8, shape_param u8, dev_outer_hz u16, timing u8, bw u8, slot_syms u16, sync_every_syms u16, idle u8, nsyncs u8 (15 bytes), then per sync 11 bytes: id u8, nsyms u8, max_errs u8, flags u8, frame_at i8, syms 6 bytes. A request carries at most 64 bytes, so at most 4 syncs.

A receive record: t_us u32, nsyms u16, flags u8 (AIR_CHUNK_*; bit 7: soft values follow), sync_at i16, sync_id u8, the hard symbols ((nsyms + 3) / 4 bytes, packed as hal_air.h says), then nsyms soft values (int8) when bit 7 is set. The session keeps about 1.3 kB of records, from the RTOS heap while open: 18 chunks of 48 symbols with soft values, 58 without. At 4800 symbols/s the records come at about 7 kB/s with soft values and 1.8 kB/s without; a 115200 baud host link carries about 11 kB/s.

The tap's gaps counts reads whose first sample was not where the previous read ended by the clock: samples the board dropped because the host read too slowly. 16-bit samples at 8 kHz are 16 kB/s: on a 115200 baud host link use 8 bits.

A transmission: TX_DATA until the queue is full or the symbols end, TX_KEY, then TX_DATA as space comes, the last chunk with AIR_TX_LAST (or TX_END). The core keys the transmitter at the lowest power level after its transmit checks (inhibit, the test TX limit, band, battery) and then calls board.air->tx_begin. At AIR_EV_TX_DONE the session asks the core for TX off; the core's own time-out and max_ms end it otherwise. Nothing here keys the transmitter by itself.

4. Safety

  • PTT: a firmware time-out on every injected PTT (10 s maximum); the host tool refuses longer holds; the radio core's own TX time-out and transmit checks still apply.
  • Every injected key hold is capped at 10 s, one injected key at a time, 40 ms between them.
  • Radio requests are rate limited (20 ms).
  • INFO_CHIP and READ_MEM only read. READ_MEM reads only the platform's windows (3.10): flash, ROM, OTP and option bytes on the STM32F4 (never RAM or peripherals); program flash, SRAM and a few register blocks without read side effects (system block, GPIO, PIC), in aligned words only, on the HR_C7000. Nothing in the debug link writes or erases internal flash or the option bytes.
  • STUB ENTER is refused while transmitting, and the transmitter is switched to receive before the jump (3.18).
  • CRASH TEST needs its token and is refused while transmitting (3.19).
  • WATCHDOG TEST and LOAD need their token and are refused while transmitting; each ends in a reset (3.21).
  • RX2 BRIDGE and RESTART need their token and are refused while transmitting. The bridge keeps the transmitter off and ends in a restart (3.22).
  • HWOPT SET is refused while transmitting (3.25).
  • AIR (bench builds only) keys the transmitter only through the radio core, which applies its transmit checks and the lowest power level; without the core's hook TX_KEY is unavailable (3.28).
  • REBOOT needs the chip UID's low word as a token, is refused while transmitting, and the ROM DFU mode is refused unless RDP is level 0. The host tool checks RDP too.
  • Memory dumps are never written inside a git tree (the vendor bootloader is proprietary).
  • AUDIO_PROBE (diagnostic builds only) writes audio chip registers as asked, and CHIP_REG writes the RF chip registers the board offers and the SoC registers in the platform's windows (3.24); nothing else in the debug link writes chip registers. A CHIP_REG write can move the transmitter's frequency or power (the radio's band and power limits don't apply to it) or stop a timer or an interrupt; a SoC register write is refused while transmitting.
  • STUB (bench builds only) writes arbitrary RAM and then runs it, giving the host full control: it is gated by a magic key, the exact length and a CRC-32, loads only into the platform's declared free RAM span, is refused while transmitting, and never returns (recover by a power cycle). Off in a release. The stub, not the debug link, is what writes flash (stub-stm32f4.md 6 for the STM32 one's rules).
  • CODEPLUG writes only codeplug blocks of the open-firmware image, never the settings ring, the journal, the native area, the staging area or the calibration window, through the journal or a staged commit (3.20).
  • The debug link never enters hotspot or CPS mode, and never takes bytes that belong to an MMDVM frame or a CPS request (section 1).

5. Counters and resets

RESET_COUNTERS zeroes: the board's diagnostics counters (board.diag_reset, whatever the board counts; on a board with an HR_C6000 the slot engine counters, the RF switch counters and the DMR audio counters), the DMR call stack counters (dmr_call_reset_stats), the AMBE voice counters (ambeVoiceResetStats), the beep counters (beep_reset_stats), the DMR data service counters (dmrDataServiceResetStats) and the P25 counters (radio_p25_reset_stats, p25VoiceResetStats). States and "last" values (last CC, last sync, engine TX state) are kept. The resets are not atomic with respect to the tasks and interrupts that count: an increment racing the reset may survive it; a test that resets, waits a moment and then starts its traffic is not affected.
