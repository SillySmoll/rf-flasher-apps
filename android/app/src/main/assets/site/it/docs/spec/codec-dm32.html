DM-32UV: hosting the AMBE+2 codec

Rule: the radio runs exactly the codec its own vendor firmware shipped. The user's machine extracts it from a firmware file the user supplies. No codec bytes go in this repository or in released binaries. The shared mechanism is in codec-placement.md; this page is the format of the DM-32UV's codec in those files.

The files aren't encrypted. The image is linked at 0x0300C000 (XIP GD25Q80 at 0x03000000), so file offset = address - 0x0300C000 + 0x100.

Where the codec is

The firmware's start-up copies a RAM code block from flash to RAM 0x10000 (049: flash 0x030BFBA0, length 0x1F098; 046: flash 0x030BF904, length 0x24490). The codec is part of that block. Its data tables are in the modem RAM image, which the start-up copies to 0x18000800 (049: from flash 0x03071F80, 0x43FC bytes; 046: from 0x03071D60, 0x439C bytes).

The table window holds two codec object groups (049: 0x18000EA8..0x18001198 and 0x180013C4..0x18003E20) with other data between them. Copying the whole window verbatim is simpler than splitting it, and it does no harm.

The ECC and FEC init offsets differ between versions because 049 links extra code before them.

Self-containment and position dependence

  • 152 functions are reachable from decode, encode and ECC. They make no calls outside the codec range and have no literals pointing at app RAM, flash or peripherals. The only indirect calls are jsr r12 and jsr r2, and those use pointers the codec stores itself.
  • The codec does reference the modem RAM tables above (049: 58 distinct addresses at 107 sites).
  • Branches and calls are PC-relative. Exactly 3 literal-pool words hold absolute codec addresses. In 049 they are the pool words at RAM 0x187B0, 0x187B4 and 0x19B68, holding 0x19540, 0x22754 and 0x26CAC. 046 has the same 3.
  • So the code runs unmodified only at its run address, with the tables at their modem RAM addresses. To move the contiguous block by a constant delta, patch those 3 words; RadioFoundry does (Hosting, step 2). To move the tables, you would patch every modem RAM literal.

Calling convention

C-SKY V2 ABI: arguments in r0-r3, then the stack; r4-r11 and r15 are callee-saved; the return value is in r0.

  • decode(r0 = wave out (80 samples), r1 = 80, r2 = bit buffer (49 x u16), r3, sp+0, sp+4, sp+8 = decoder state)
  • encode(r0 = bit buffer, r1, r2 = wave in, r3 = 80, sp+0, sp+4 = 0/1 (first/second half), sp+8, sp+12 = encoder state)
  • ECC(r0 = r1 = bit buffer, r2, r3 = ECC state)

The vendor wrapper passes values it keeps in the state blocks:

  • decode: r3 = D[0x1166], sp+0 = a flags word.
  • encode: r1 = E[0x1736], sp+0 = the flags word (a literal 0x800 in three calls, E[0x172E] = 0x1840 in the other three), sp+8 = E[0x173A] (0x2000 after init).
  • ECC: r2 = E[0x1738].

The encode flags word is a set of feature bits, one value on every call of a transmission (0x800, or 0x1840 = 0x1000 | 0x800 | 0x40). "0x1840 on the first call, then 0x800" behaves as 0x800: no noise suppression and no tone frames.

platform/hrc7000/vocoder.c (the HR_C7000 boards) passes one word on every call from drivers/vocoder/ambe2_flags.h: 0x800, plus 0x40 for noise reduction, 0x1000 for tone frames and 0x2000 for AGC (0x1840 by default).

Vendor firmware versions

Every DM-32UV build from 01.01.032 to 01.01.049, and the NRFB 050 build, carries the same codec: the same length (0x14600), the same run address (0x16CDC), the same entry points (the 049 column above) and byte-identical tables (10684c33...). Inside the codec ranges the code differs only in its table pointers. The rest of the differences fall in the other code that lies inside the window but isn't codec. Each version links the codec to its own flash addresses, so tools/hrc7000_codec.py keys each file by its SHA-256 and finds the codec in a program flash read by content, then by address. The NRFB build is known only from a program flash read, so its profile is keyed by the SHA-256 of the code window.

Rules for the addresses:

Value Rule
Run address The three self-referencing pool words (section "Self-containment and position dependence") give it. Every build has 0x16CDC
Table RAM address Every table literal in the codec ranges moves by the same constant against 049: none for 032 to 049, +8 for the NRF and fanti builds, +0x18 for NRFB 050 (69 literals in the reachable code). Everything else in the reachable codec code, the three self references included, is byte-identical to the NRF build's
Table window The 64-byte head CRC (TABLES_HEAD_CRC), then the SHA-256

The NRFB tables end at 0x18003E38, 0x10 above the NRF and fanti ones (0x18003E28) and 0x18 above the 049 window, so the DM-32UV linker script reserves modem SRAM up to 0x18003E38. A RadioFoundry build with the older limit refuses an NRFB slot (its table window check fails): the radio needs a build with this limit to use the codec. The slot's version tag is the build number (32 to 50), and the host reports it as dm32-<three digits>.

C. Codec state init tables

The codec has no precomputed state arrays in the file: the state is built at run time with the codec's own init functions. The 049 init routine (RAM 0x162A8) uses a decoder state D (049: 0x456C0) and an encoder state E (049: 0x48160), with the ECC state at E+0x16E0 and the encode bit buffer at E+0x1898. It runs these steps in order:

  1. It sets these 16-bit parameters:

    field value
    E[0x172C] 0x1840
    E[0x173A] 0x2000
    E[0x173C] 128
    E[0x173E] -20
    E[0x1740] -22
    E[0x1742] 20
    E[0x1744] -10
    E[0x1746] -40
    E[0x1748] 0x4000
    E[0x174A] 3276
    E[0x174C] 3276
    E[0x174E] 1310
    E[0x1750] 10
    E[0x1752] 20
    D[0x1152] 0
    D[0x116A] 128
    D[0x116C] -20

  2. It calls the init functions:

    • encoder init(E, 1, 1)
    • FEC init(E+0x16E0, 1)
    • encoder set(E, E[0x173C], E[0x173E])
    • decoder init(D, 1)
    • FEC init(D+0xFD0, 1)

  3. It runs one decode with r0 = D+0x12AE, r2 = D+0x1354, r3 = 0, sp = {8, 0, D}.

  4. It calls decoder set(D, D[0x116A], D[0x116C]).

046 does the same (D = 0x4AAA8, E = 0x4D548). RadioFoundry calls these functions (platform/hrc7000/vocoder.c). The state blocks can live anywhere, because they're passed by pointer. Minimum sizes from the accesses are about D >= 0x1400 and E >= 0x1900; the exact sizes are open.

Hosting

How RadioFoundry runs it (codec-placement.md, "HR_C7000 radios"):

  1. At the user's machine, tools/hrc7000_codec.py (or the web flasher) checks the sha256 of the vendor firmware file, carves the code and the table window, and writes them unchanged into the codec slot at 0x030E8000..0x03100000, after a 128-byte version 2 header and before the relocation list: the offsets of the 3 self-referencing words, from the build's codec map. The slot is load-only data in XIP flash after the application.
  2. At boot, platform/hrc7000/vocoder.c copies the code to the board's codec window at the top of SRAM (0x43A00..0x58000), adds (window start - run address) to each listed word, checks the first two words, and copies the tables to their modem RAM address (049: 0x18000EA8).
  3. Memory map (boards/dm32/memory.ld): one RAM region for RadioFoundry from 0x10000 to the codec window. The modem RAM window 0x18000E48..0x18003E38 (the union of the builds' tables) is reserved.
  4. Versions: every DM-32UV build with a codec map (eight maps in tools/rfoundry/rfoundry/codec_maps/dm32/) runs in the same window, since only the 3 words depend on the run address.
  5. State: one 0x1C00-byte block in main RAM holds the encoder's state (E) or the decoder's (D), never both. Voice is simplex, and each half of the init sequence above touches only its own block, so the first encode after a decode runs the encoder's steps (its parameters, encoder init, FEC init(E+0x16E0), encoder set) and the first decode after an encode runs the decoder's (decoder init, FEC init(D+0xFD0), the first decode, decoder set). P25 borrows the block while it runs (hal_vocoder_t.lend).

Open items

  • On the radio (2026-10-19) the 049 codec in the window decodes on-air speech with every frame (234 of 234, 78 of 78 bursts) (measured). Audio quality against the vendor firmware has not been compared.
  • Exact sizes of the D/E state blocks; whether the codec writes to its modem RAM tables (the boot copy covers both cases).
