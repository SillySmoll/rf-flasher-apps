Build configuration

Features that cost flash, and values that differ per radio, are chosen at build time. Defaults live in config/features.mk. A platform changes them for every radio on it in platform/<p>/config.mk, a board changes them in boards/<board>/config.mk, and the make command line overrides all of them. The Makefile reads the board's file before the platform's: both use ?=, which keeps the first value set, so the board wins over its platform:

make BOARD=<id>                          # the board's defaults
make BOARD=<id> CONFIG_DMR=n             # FM only
make BOARD=<id> CONFIG_VFO=n             # programmed channels only
make BOARD=<id> CONFIG_DISPLAY_INSET=3   # smaller screen margins
make BOARD=<id> BAND=vhf                 # a build option, on a board that has one: build/<id>-vhf

Each switch reaches C as CONFIG_<NAME> = 0 or 1, always defined: test it with #if CONFIG_X, never #ifdef. core/config.h holds the same defaults (all on) for host tests and checks the dependencies. Switches can also leave whole source directories out of the build (Makefile, platform/*/platform.mk). A sub-feature follows its parent unless it is set: CONFIG_DMR=n turns off every DMR feature, and asking for a sub-feature without its parent is an error. Changing a switch rebuilds everything (the build keeps the flags in build/<board>/flags, checked when make starts). make BOARD=<b> print-config lists the resolved switches.

Every feature is on by default wherever the radio has what it needs. A board turns a feature off only for hardware it lacks, for board code not written yet, or when the image doesn't fit, and then the most obscure large features go first. Bench diagnostics such as CONFIG_AUDIO_PROBE stay off.

A feature that needs a part only some radios have (a vibration motor, a GPS receiver, SPI NAND) is a hardware switch: hardware = "..." on its entry in tests/hil/features.toml. Each board then builds it, lists it in BOARD_UNSUPPORTED or BOARD_NOT_WRITTEN, or names it in board.toml [hardware] unconfirmed, and tools/boards.py check enforces that. The accelerometer is the next one: today its driver (drivers/sensor/lis3dh) only feeds a board's diagnostics page under CONFIG_DIAG, so it has no switch. The first feature that uses motion brings a hardware switch with it. A real-time clock driver is the same: none exists yet, and it arrives as CONFIG_RTC, a hardware switch (radio-features.md 5.6).

Unsupported, not written, unconfirmed

A feature a radio's default image leaves out is in exactly one of these. ✕ is only for what no firmware can change, so the docs never understate what a radio can do.

Mark Meaning Where Example
✕ The hardware can't: a part is missing, or the chip or the board lacks something config.mk BOARD_UNSUPPORTED += X # <the reason> GPS on a board without a receiver, SFR on a modem lacking the register the glue uses, FONT_XL on a 160 px panel
… The hardware can, but this radio's driver or glue isn't written yet config.mk BOARD_NOT_WRITTEN += X # <what isn't written> TX tones and DTMF on a board whose tone path isn't written, a broadcast receiver whose glue isn't written
? Not known yet whether the radio has the part board.toml [hardware] unconfirmed a vibration motor no source confirms
● Written, built, not yet checked on the radio no list: on by default. The bring-up records and board.toml [status] hold its test state

Both config.mk lists take one switch a line with the reason in its comment (tools/boards.py check fails on one without a reason, or on a switch in both). Either one turns the switch off by default (the Makefile does it: no CONFIG_X ?= n needed), keeps it out of ci's maximal configuration, and satisfies a hardware switch's check. A platform's config.mk can list switches for all of its radios, and config/features.mk lists the ones a build rules out by itself: FONT_BIG on a panel under 220 px wide, the width taken from the hardware.gallery class in board.toml, so a new small-panel board needs no line for it. The feature matrix and the web site show the mark. Say "untested" in bring-up records and pull requests, never in config.mk.

Variants

A variant is a named preset of switches for the prebuilt release images and the web flasher's build picker (website.md): config/variants/<name>.mk, read after the board's board.mk and before its config.mk, so it wins over the board's defaults and the command line wins over it. A variant only turns switches off (CONFIG_X ?= n); the board's own limits still apply. Without VARIANT the build is the full default.

make BOARD=<id> VARIANT=amateur          # build/<id>-amateur/
make BOARD=<id> VARIANT=commercial       # build/<id>-commercial/
Variant Leaves out
(none: full) nothing
amateur basic privacy, Motorola TMS, ARS, LRRP, control station mode, SNMP
commercial the MMDVM hotspot (and split duplex), APRS (and KISS, APRS-IS)

Each variant file starts with ## title: and ## summary: lines, and the comment above each switch says why it is left out; the site shows both. The lists are a draft for the project lead to settle.

The firmware version (RFOUNDRY_GIT) is the commit plus -dirty when the tree differs from it (tracked changes, or untracked sources in the built directories). The release name (RFOUNDRY_RELEASE, for example v26.11) is the release tag on that commit, empty for a dirty tree or an untagged commit; make RELEASE=<tag> sets it and RELEASE= leaves it out (dev/release.md). Only the few files that use either are rebuilt when it changes.

CONFIG_CONTACT_EDIT = CHANNEL_EDIT and DMR the contact editor: a new contact from Find's Create contact or Save as contact in actions (docs/spec/ui.md 2.4). Needs CONFIG_CHANNEL_EDIT and CONFIG_DMR; without it contacts come only from a CPS
CONFIG_KEY_ASSIGN y key assignment: Settings > Keys and the codeplug's quick-key slots say what the board's programmable keys do (docs/spec/ui.md 3.1)

CONFIG_DUAL_WATCH y (with SCAN) the dual watch screens: Home with both channels, the channel picker and the dual watch actions (dual-watch); in the radio core, channels of other zones and the VFO, and PTT on the selected channel without ending the watch (docs/spec/radio-features.md 2.1). Off: dual watch stays reachable only from the debug link (two channels of the current zone)
CONFIG_BEEP y key, TX permit / deny, call end, time-out warning, battery and scan beeps (docs/spec/radio-features.md 4)
CONFIG_SIG_TONES = BEEP Settings > Signaling tones: a chain of up to ten tones (frequency and length) for the start of a transmission, its end and a reception's end, on the speaker, on air or both, in DMR and FM (docs/spec/radio-features.md 4.3). Needs CONFIG_BEEP; an FM tone on air also needs CONFIG_FM_TX_TONES. Off: the radio's own talk permit, end and roger sounds
CONFIG_FONT_XL n (y on a 240 px color radio) 16x32 font, for 240 px and wider displays
CONFIG_FONT_AA n (y on a color radio) the fonts from 6x12 up anti-aliased (JetBrains Mono Bold, 2 bits a pixel) on color panels instead of the bitmap ones; a mono panel would draw them as plain ink, so mono radios leave it off. Glyphs: 15.6 KB with FONT_XL (8.2 KB without) in place of 9.2 KB (5.3 KB) of bitmap ones (core/ui/fonts.c). On a 4 bpp panel (every color board) the edge grays share the 16 palette entries with the screen's own colors; a screen that already uses many colors loses some of them, and some font sizes or colors can then be slightly harder to read (docs/spec/ui.md 5)
CONFIG_FONT_BIG n (y on a 240 px color radio) larger text on 240 px and wider color panels: lists, labels, the status strip and hints in a 9x18 font instead of 8x16 (24 characters a line instead of 27 on a 240 px panel; the 8x16 one takes the small print). Needs FONT_AA; 3.5 KB of flash. Unsupported on a panel under 220 px wide (the board's hardware.gallery), and so off in its maximal build

The first language also brings the accented letters of every font (CONFIG_LANG_ANY); each further language adds only its text. Off: Spanish is listed but dimmed. One switch per language, translating.md
CONFIG_LANG_IT n Italian on the radio (core/ui/lang/it.po), as CONFIG_LANG_ES. Off: Italian is listed but dimmed
CONFIG_LANG_FR n French on the radio (core/ui/lang/fr.po), as CONFIG_LANG_ES. Off: French is listed but dimmed
CONFIG_LANG_ZH n Chinese on the radio (core/ui/lang/zh.po), as CONFIG_LANG_ES, plus what Chinese needs and the Latin-1 languages do not: a 16x16 glyph for every character its catalog uses (core/ui/cjk_font_data.c, built by tools/cjkfont.py; 480 characters, 15.4 KB) and UTF-8 text the text layer decodes (core/ui/gfx.c). 32,856 bytes with Spanish on (measured 2026-11-04). A line must be at least 16 px high: the glyph is the height of the 8x16 font. A 240 px color radio draws its words in 8x16 (and its text pages move up to it in a CJK build), so Chinese shows on every screen; a layout that draws its words in the 5x8 or 6x12 font (a 128x64 display, and the 160x128 class) has no room for 16 px lines, so Chinese must stay off there. Off: Chinese is listed but dimmed

CONFIG_LANG_DEFAULT_FR n The radio starts in French, as CONFIG_LANG_DEFAULT_ES. Needs CONFIG_LANG_FR
CONFIG_LANG_DEFAULT_ZH n The radio starts in Chinese, as CONFIG_LANG_DEFAULT_ES. Needs CONFIG_LANG_ZH
CONFIG_UI_COLOR y (n on a monochrome radio) color screen settings: Theme, Highlight color and Filled status bar in Settings > Display (docs/spec/ui.md 5, 8). Off: no such rows, the dark theme's colors. About 600 B; off for radios whose only screen is monochrome
CONFIG_AUDIO_PROBE n diagnostics: debug link command 0x10 reads / writes the audio chip's registers and measures the PCM stream, for the USB audio bench tests (docs/spec/debuglink.md 3.14); needs DEBUGLINK and DMR; about 2 KB RAM and 2.2 KB flash. Never for a release; CI builds it in one board's audio-probe configuration (with LTO=1: the default image has no room for it without), not in maximal. A bench image without LTO: add CONFIG_SNMP=n
CONFIG_UI_SETTINGS y the Settings menu on the radio; off: settings keep their stored values and are set with qdmr (docs/spec/ui.md 5)

Derived (not set by hand): CONFIG_DMR_DATA_CORE, the shared packet data / CSBK code, on when any data feature is; CONFIG_DMR_AIR_QUEUE, the data service's TX queue (docs/spec/dmr-data.md 12.6), on with CONFIG_DMR_IP_GATEWAY or CONFIG_ZONE_SHARE. CONFIG_DMR_AIR_QUEUE_BYTES 2048 octets in the data service's TX queue: each queued packet takes its length plus a 36-octet record header, rounded up to 4 (docs/spec/dmr-data.md 12.6.1). At least 1296 (two longest packets)

Board build variables

Not feature switches: they pick the hardware variant or set bench knobs, and print-config doesn't list them.

Variable Board Meaning
BAND boards with a band option A build option (board.toml [[build_options]], board.mk BUILD_OPTIONS): a band such as uhf (the default) or vhf, which picks the band table, the frequency plan and the board name. Given on the command line, it adds its value to the build directory (build/<id>-vhf)
bench defines a board's board.mk A board may take extra -D defines for the bench (panel type, switch polarity, battery divider, keeping the debug pins); they are listed in its bring-up page under docs/testing
LTO 0 (STM32F4 platform: 1) link time optimization (-flto=auto at compile and link): about 17 KB smaller (20 KB with LTO_3P=1). The STM32F4 boards needed it while their application areas were small; since the codec moved (codec-placement.md) they have 464 KB or more, and it stays on for the smaller image. The csky builds don't use it
LTO_3P 0 (a board turns it on to fit) with LTO=1, the third-party code too (HAL, CMSIS, FreeRTOS, TinyUSB): about 3 KB more. FreeRTOS marks what its port's assembly reaches portDONT_DISCARD; the vectors are referenced from the assembly start-up. LTO_EXCLUDE lists files kept out (file-scope assembly: platform/stm32f4/codec_call.c)
TCP_CONNS HR_C7000 platform TCP connections in all states (core/net/tcp.h, 4 elsewhere): 3 by default on the HR_C7000 platform, about 1.5 KB RAM each across TCP, HTTP and rigctld
MAXIMAL_VARS a board's own set in a board's config.mk: make variables tools/ci.sh adds to that board's maximal build (make print-maximal-vars)
BOARD_UNSUPPORTED a board's own set in a board's or platform's config.mk, one switch a line with the reason in its comment: switches the radio's hardware can't do (above); the maximal build leaves them off (make print-unsupported)
BOARD_NOT_WRITTEN a board's own the same form: switches the hardware can do but whose driver or glue isn't written for the radio yet; the maximal build leaves them off too (make print-not-written), and every switch that needs one of them
BOARD_DEFAULT_OFF a board's own the same form: switches that work but carry a risk on this radio. The switch stays off by default (CONFIG_X ?= n next to it) and stays selectable in a custom build; the web flasher shows the comment by its checkbox, so write it for users
BOARD_REQUIRED a board's own set in a board's config.mk: switches the board can't build without; ci.sh builds no no- configuration for them (make print-required)
MAXIMAL_SKIP a board's own set in a board's config.mk: switches that work on the radio but that it doesn't need, which the maximal build leaves off too (make print-maximal-skip). NET_PPP stands in for the USB network adapter on UART-only radios. The maximal build also leaves CONFIG_AUDIO_PROBE off on every board (MAXIMAL_SKIP in tools/ci.sh); one board's audio-probe build covers it

Board defaults

A board's config.mk (and its platform's) turn switches off where the radio differs from the project defaults, each with its reason in a comment. Two lists carry the reasons that matter to the docs: BOARD_UNSUPPORTED and BOARD_NOT_WRITTEN (above). To see them for a board:

make BOARD=<id> print-config            # the resolved switches
make BOARD=<id> print-unsupported       # what the hardware can't do
make BOARD=<id> print-not-written       # what is not written yet

feature-matrix.md shows the result for every radio ("Built by default on each radio") and its notes give the reasons; a radio's hardware spec (hardware-<id>.md) holds the facts behind them. The switches off on most boards are CONFIG_AUDIO_PROBE (a bench diagnostic) and the ones that need a part the radio lacks.

Adding a feature

  1. Add the switch with a comment and its default to config/features.mk, to FEATURES, and to the dependency checks.
  2. Add the default and the checks to core/config.h.
  3. Guard the code, and leave a directory out in the Makefile when the whole directory belongs to the feature.
  4. Add a row here and in feature-matrix.md (the web site takes the feature's group, title and size from it; site/build.py --strict fails without the row), and check the build links with the switch off (make BOARD=<b> CONFIG_X=n BUILD=build/test-x). tools/ci.sh builds every board with each default-on switch off alone, an FM-minimal and a maximal configuration, all with zero warnings, and reports the image sizes (docs/testing/README.md). The maximal configuration leaves out the switches a board lists in BOARD_UNSUPPORTED (its config.mk: what its hardware can't do, such as SFR on a modem chip lacking what the glue uses) or BOARD_NOT_WRITTEN (what its code doesn't do yet). Leaving the not-written switches out keeps the maximal build to code that runs on the radio: built on, they can fill a radio's memory (one radio's maximal build reached 99% of its CCM RAM), and any shared addition would then fail CI on unrelated pull requests. A switch that needs a left-out one is off too: tools/ci.sh drops each switch the checks in config/features.mk name until the set passes them (DMR not written takes all of DMR's family with it).
